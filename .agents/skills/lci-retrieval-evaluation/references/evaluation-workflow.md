# Evaluation workflow

Use the checked-in portable definitions and supply local workspace mappings at runtime. This is the procedure that has produced trustworthy before/after evidence in this repository; follow it unless the human asks for something else.

Scope: the embedder-plus-reranker sets (`evaluations/core.toml`, the mined sets) are regression checks only. Use this workflow to show that a change to the shipped pipeline did not hurt; do not add new embedder or reranker comparison arms. Measurement of the traversal engine and the metric tiers: [docs/spike/multimap/evaluation.md](../../../../docs/spike/multimap/evaluation.md).

## Procedure

1. Record the baseline commit, configuration overrides, model names, and whether indexes were created or reused.
2. Run the deterministic automated tests with the fake services first (`cargo xtask test --suite Filter` / `Evaluation` / `Indexing` as relevant).
3. Freeze the binaries. Build the baseline, copy `target/debug/local-code-intelligence(.exe)` to a scratch path such as `lci-base.exe`; apply the change, build again, copy to `lci-new.exe`. Later rebuilds then cannot disturb a running comparison, and on Windows the running copy does not lock the build output.
4. Give each scratch configuration its own short `data_dir` (for example `<short-root>/lci-eval/base`; `cargo xtask env scratch_area` resolves the scratch area, and on Windows a path under it can already be too long, so choose a short root when it is). On Windows LanceDB fails with `os error 3` when the data directory is long, because table names are `ws_<16 hex>` plus Lance's internal paths; keep it under 150 characters (`/ready` flags a longer one as `data_dir_path_length`). Never point a scratch run at the running server's data directory.
5. Run the smallest live evaluation that exercises the changed stage against 8766/8767, once per binary:

   ```bash
   <bin> --config <cfg> evaluate ./evaluations/core.toml \
     --workspace self=<repo> \
     --output test-results/<name>.json
   ```

   Keep self and external-repository results separate; absent optional workspaces are skips, not failures.
6. For a change to priors, source-role classification, fusion, or candidate counts, also run both binaries with the reranker switched off (`[channels]` `reranker = false` in the scratch config; it yields the same fusion-order shortlist as a failed reranker, with zero `reranking_ms` and no warning). The reranker masks fusion-order changes on small fixtures; the fusion-order run is where such a change shows.
   - Other arms: grep-only (`semantic = false`, `lsp = false`, `reranker = false`) and semantic-only (`lexical = false`, `lsp = false`, `reranker = false`); reports do not record the switches, so name the output files after the arm.
   - Config sections use `deny_unknown_fields`, so a binary older than a key (for example `[fusion] max_chunks_per_file`) rejects a scratch config that sets it: give each binary a config it understands, and set new keys only for the binary that has them.
   - The default fusion weights are plain RRF (`[fusion] semantic_weight = lexical_weight = lsp_weight = 1.0`), and the default caps a file at two chunks ahead of other files (`[fusion] max_chunks_per_file = 2`). An arm that must match a report made under other defaults sets them explicitly: see "Reproducing older reports" at the end.
7. Compare hit@1, hit@3, hit@8, MRR, nDCG@10 (`mean_ndcg_at_10`), recall@3/@8 (`mean_recall_at_3`, `mean_recall_at_8`), file acc@5/@10 (`mean_file_acc_at_5`, `mean_file_acc_at_10`), first expected ranks, disfavored results above expected results, role failures, fallbacks, the index lifecycle counts including `index_refreshed` (created + reused + waited + refreshed should equal the executed count), and per-stage latency from the aggregate `stage_latency` block (p50/p95/max and `n` for query embedding, LanceDB, lexical, LSP, fusion, reranking, and total; nearest-rank p95 hides the worst query at small `n`, so read `max`). The `@10` metrics are bounded by each query's `top_k` (8 in `core.toml`, 10 in the mined sets), so treat them as @8 unless `top_k >= 10`.
   Pair the two reports instead of eyeballing the aggregates: `<bin> compare baseline.json candidate.json` (offline, no services or config) matches queries by workspace and query text and prints, for MRR, nDCG@10 and hit@1, both means, the mean per-query delta with a seeded 95% paired-bootstrap interval, and reciprocal-rank wins/losses/ties; it also counts unpaired and skipped queries and, for tagged definitions, repeats the table per tag (`--output <file>` saves the JSON, `--seed`/`--resamples` change the bootstrap). Read the interval before claiming a win: a delta whose interval contains zero is not evidence, and `core.toml`'s eleven required queries will rarely clear it. Report the interval and the W/L/T with any claimed gain, and check the unpaired counts are zero. `evaluate ... --baseline <report.json>` embeds the same comparison in the new report.
   Lanes and tokens (a docs arm also sets `[index].prose = true`; the default index holds no Markdown): a query is scored on the code `results` list unless it carries the tag `lane:docs` (scored on the separate `docs` list; the gold `to-evaluate --set instructions` emits it) or `lane:union` (code list then docs list, renumbered). The other list is kept as `unscored_evidence`. The docs list is never longer than `[docs_lane].top_k` (default 2) and is reranked only when `[docs_lane].reranker` or a profile `docs_reranker` is on (default off; `[channels].reranker` does not apply): a docs arm sets `docs_lane.top_k` at least as high as the query `top_k` (a query whose list the setting cut short carries a note), and `replay` refuses `lane:docs` and `lane:union` queries (`non_code_lane`) because dumps hold code candidates only. `returned_tokens` per query (and `mean_returned_tokens`, plus a `tokens` row in `compare`) is the snippet characters of both lists divided by four, a proxy for what the agent has to read; a report that predates the figure is compared from its evidence.
   Before trusting a paired difference, check that both arms had the same channel coverage: count per-query `lsp_search_ms` at the `lsp_search_budget_ms` cap (or the LSP note in `notes` in a dump) in each report. Fusion-only runs can lose the LSP channel on a long run of queries while reranked runs do not, and that once made a weight grid look significant when an exact replay with the LSP channel present showed no effect (the numbers are in `docs/decisions.md`). When coverage differs, decide from an E0 dump replayed with `replay` instead of from live arms.
8. Inspect path, line, role, and bounded source evidence for every failure; aggregate metrics alone do not prove correctness.
9. Save reports under `test-results/` and keep them out of commits. Name them so the pair is obvious (`<change>-baseline-rerank-on.json`, `<change>-after-rerank-off.json`).

## Replaying a dump instead of running live

For a live service rather than an evaluation run, `LCI_CANDIDATE_DUMP=<file>` (README) appends the same pool per search to a JSON Lines file.

`evaluate --dump-candidates` records every query's whole fused candidate pool, the dumped configuration (`arm`), and the reranker's scores; `<bin> replay dump.json --output <file> [options]` then scores other settings from that file in seconds, offline (no services, config, or index), through the unchanged metrics. Its output is an evaluate-shaped report, so `<bin> compare dump.json <file>` pairs it with real reports and with other replays. Run one dump live; replay the grid.

Replay when the question is a pure function of the dumped pool and scores, so both arms share identical candidates (which also removes run-to-run LSP coverage differences):

- the rerank window (`--window`), the per-file cap and where it runs (`--cap`, `--cap-stage shortlist|results`);
- fusion weights, `rrf_k`, and the source-role prior (`--semantic-weight`, `--lexical-weight`, `--lsp-weight`, `--rrf-k`, `--prior`) with `--rerank-mode off`, which is fusion order alone;
- how the reranker's scores are used (`--rerank-mode replace|vote|off`, `--vote-weight`).

Run live when anything the dump cannot hold changes: `rerank_document_max_bytes`, the reranker model or instruction, the query template (`embedding_query_template`), chunking, embedding, a window or channel depth larger than the dump took, or a new channel. Run live too for the final acceptance of a replayed winner (one live run of the adopted setting, compared with `compare`) and for every latency claim: replayed `reranking_ms` and `total_ms` are labelled cost-model estimates (`replay.latency`; the fit and its R^2 are reported), the measured timings stay under `replay.original`.

Taking the dump: use a frozen binary and a scratch configuration with `rerank_candidate_count` as large as the largest window you will replay (at most 200) and, to replay either cap stage or other caps, `[fusion] max_chunks_per_file = 0`; a replayed window can only be scored where the dump sent the candidates to the reranker. Before trusting a grid, check determinism: `<bin> replay dump.json --output same.json` (every setting left out keeps the dumped value) must reproduce the dump's evidence and metrics, so `compare dump.json same.json` shows all ties, zero refused queries, and zero `replay.past_window_queries` (production returns at most the window, so with a window smaller than `k` replay returns more rows and counts those queries). A failed determinism check is a defect in replay, not a result.

What is exact: any window up to the dumped shortlist; the per-file cap at either stage; any weights, `rrf_k`, or prior under `--rerank-mode off`; and `replace`/`vote` over candidates the dump scored (the reranker scores each query-document pair independently, so a score does not depend on its neighbours). What is refused, per query and never approximated: a reranked window holding an unscored candidate (`unscored_window`), a reranked arm over a dump whose reranker failed or was off (`rerank_not_scored`), a dump whose fusion or cap does not reproduce at its own arm (`fusion_mismatch`, `shortlist_mismatch`), and a query with no dump (`not_dumped`). Refused queries are written as skipped with a `replay_refusal`, counted in `replay.refused`, and listed in `replay.refused_queries`; `compare` excludes them from every pair, so read its `paired` and skipped counts and report the refused counts with any replayed result. If a refusal differs between the arms you are comparing, the pairs are different query sets: compare each arm against the dumped arm replayed over the same queries.

Pre-register the grid before looking at results, select on one half of the queries, confirm on the other, and apply the decision rule below to the paired intervals as for live arms. Replay does not replace the checks in steps 6 to 8 for the adopted setting; it decides which settings deserve a live run.

## Operating constraints

- Run live evaluations sequentially, never in parallel. The reranker is the latency bottleneck (a reranked query sends up to `rerank_candidate_count` documents, 24 by default), so a reranked run is far slower than a reranker-off run and `evaluations/core.toml`'s self set can take minutes per binary. Latency depends on the serving setup and the machine; measure it on yours (dated measurements: `docs/decisions.md`).
- Do not compile, run the test suite, or start another indexing pass while a timed live evaluation runs. Heavy CPU/GPU load distorts reranker timings and makes the before/after latency comparison meaningless.
- Freeze the evaluated tree. The self set indexes the working tree, and a search refreshes a stale index, so any edit to an indexed source file during a run (one of the code extensions in `lci-core/src/language.rs`; Markdown such as the roadmap is not indexed) changes the candidate pools of later queries, which has confounded a reranker comparison before (numbers: `docs/decisions.md`). Make no edits in the evaluated tree while a run is going; for multi-arm work, evaluate a frozen copy (a `git worktree` at a fixed commit, indexed once) instead. Compare top-24 fused-pool identity per query before attributing a difference to a reranker or weight change.
- Neutrality checks ("this slice changes no result") compare each query's ranked `evidence` (`relative_file_path`, `start_line`, `end_line`), never metrics alone, and a helper that reads rows must fail on an empty list. The semantic channel is not bit-reproducible: the same binary run twice with the reranker off can differ on a few core queries (batch composition under concurrent indexing load shifts the query embedding; measured numbers: `docs/decisions.md`). So prove identity on a lexical-only configuration (`[channels] semantic = false`, exact) and with the reranker on, and use a same-binary rerun as the noise floor for the reranker-off semantic arm.
- Scratch fixtures and decoy evaluation TOMLs live outside the repository (or under `test-results/`), never in `evaluations/`, which holds only portable, path-free definitions.
- `evaluations/core.toml` has eleven required self queries, so one query is about nine points of hit@1. Treat small metric moves as noise; look at which queries moved and why, and prefer a larger scratch decoy set when the change targets a specific role or language.

## Latency work

Separate first indexing, query embedding, LanceDB, lexical, LSP, fusion, reranking, and total time. Warm the relevant model once when startup latency is outside the question. Use a small number of representative runs unless the human asks for extended benchmarking.

## Decision rule

Accept a ranking change only when the intended metric or latency improves without material regressions in required queries or fail-open behavior, in both the reranked and the fusion-order runs where both apply. Never insert evaluation paths, symbols, snippets, or queries into production ranking logic, and never tune a prior or threshold to a specific evaluation query.

## Reproducing older reports

A report made under other defaults is reproduced by setting the then-defaults explicitly in the arm's scratch config. Commits: `79138e4` (`semantic_weight` default 2.0), `92a7060` (`max_chunks_per_file` default 2), `bb6589d` (reverts the semantic weight default to 1.0; the reason is in `docs/decisions.md`).

| Report made | Defaults then | Arm settings that match it (today's defaults: weights 1.0, cap 2) |
| --- | --- | --- |
| before `79138e4` | weights 1.0, no cap | `max_chunks_per_file = 0` |
| from `79138e4` to `92a7060` | `semantic_weight = 2.0`, no cap | `semantic_weight = 2.0`, `max_chunks_per_file = 0` |
| from `92a7060` to `bb6589d` | `semantic_weight = 2.0`, cap 2 | `semantic_weight = 2.0` |
| after `bb6589d` | today's defaults | none |

## Candidate dump and replay reference

The commands and when to use them are in "Replaying a dump instead of running live" above; this is the exact format and semantics.

- `evaluate --dump-candidates` records, for every query whose search ran, the whole post-filter fused candidate pool (before the per-file cap and shortlist cut) so other settings can be scored without services. Each such query carries `candidates` (one row per chunk in fused order); `arm` (the configuration the dump was taken under: `rrf_k`, `fusion` weights and per-file cap, `rerank_candidate_count`, `rerank_document_max_bytes`, the three channel depths, `channels`, the query's result window `k`, the embedding identity, the reranker model, `rerank_mode`); `rerank_outcome` (`scored`, `failed` = fusion order with a warning, `off`, `not_run`); and `notes` (so queries whose language-server channel was cut short can be excluded or stratified).
- A row holds path, language, line range, content hash (empty in older dumps), source role; the semantic, lexical and language-server ranks (one-based, as fusion consumed them) with semantic and lexical scores and the lexical match count; the source-role `prior`; `fusion_score`; `fused_rank` (before the cap) and `capped_rank` (after the cap, before the cut), both one-based; `shortlisted` (`capped_rank <= rerank_candidate_count`); for shortlisted rows `document_bytes` and `est_tokens` (`document_bytes / 4`); `rerank_rank` and `reranker_score` when the outcome is `scored`; and the bounded `snippet`.
- In `f32` arithmetic `fusion_score` is `0.0 + semantic_weight / (rrf_k + semantic_rank) + lexical_weight / (rrf_k + lexical_rank) + lsp_weight / (rrf_k + lsp_rank) + prior`, adding only the channels that returned the chunk, in that order, so rows reproduce it bit for bit. The flag changes nothing else (without it none of these keys is written; MCP, REST and CLI `search` never emit them). A dump takes roughly 100 KB or more per query. Take it with `rerank_candidate_count` as large as the largest shortlist you want to score (up to 200).
- `LCI_CANDIDATE_DUMP=<file>` on a process makes each search that returns a report (a failed search appends nothing) also append one JSON line (`ts`, `workspace_path`, `query`, `search_profile` when named, `filters`, `channels`, `rerank_candidate_count`, `rerank_outcome`, `timings`, `candidates`; with a profile, `channels` and `rerank_candidate_count` are its resolved values) to that file, leaving every response unchanged. The variable is read once at startup, a failed write only logs a warning, and each append logs its own cost (`dump_ms`, not in `timings`).
- `replay` per dumped query first checks, at the dumped arm, that every `fusion_score`, the fused order and the cap's `capped_rank` and `shortlisted` reproduce bit for bit; then re-sorts under the replayed weights, applies the cap (`--cap`; `--cap-stage shortlist`, the default, caps before the window cut as production does, `results` caps the whole list after reranking), cuts the first `--window` rows, orders them with the dumped reranker scores, appends the rest of the fused order, takes the query's own `k`, and runs the unchanged metrics.
- `--rerank-mode`: `replace` (production: reranker score descending, then window position), `vote` (re-sort by `fusion_score + --vote-weight / (rrf_k + reranker rank)`, rank within the replayed window), `off` (fused order). Settings left out keep the dumped value: `--window`, `--cap`, `--cap-stage`, `--semantic-weight`, `--lexical-weight`, `--lsp-weight`, `--rrf-k`, `--prior` (the prior of `source` chunks; 0.004 in production), `--rerank-mode`, `--vote-weight`. Example: `<bin> replay test-results/dump.json --output test-results/replay-w12.json --window 12 --cap 2 --cap-stage results`, then `<bin> compare test-results/dump.json test-results/replay-w12.json`.
- `--output` writes an ordinary evaluation report that `compare` pairs with real ones, plus a report-level `replay` block (source file, dumped and replayed arm, query counts, refusals, latency model, original timings). At the dumped arm the evidence and metrics equal the dumped ones whenever the window is at least `k`; production returns only the window, so for a smaller window replay returns more rows and `replay.past_window_queries` counts them.
- A query replay cannot score exactly is refused, counted and listed (`unscored_window`, `rerank_not_scored`, `fusion_mismatch`, `shortlist_mismatch`, `batch_mismatch` (a scored replay of a System One dump whose shortlisted batch membership or order changed), `not_dumped`; written as skipped with `skipped`, `replay_refusal` and the cause in `reason`). It cannot replay a larger window or channel depth than dumped, another `rerank_document_max_bytes`, reranker, query instruction, chunking or embedding: run those live.
- Replayed latency is an estimate (`replay.latency`): `reranking_ms` is `a + b * tokens` over the `est_tokens` of the replayed window, fitted by least squares over the dump's reranked queries (`a`, `b`, R^2 reported), falling back to 400 ms plus 290 tokens per second when R^2 is below 0.5; `total_ms` swaps that into the dumped total; other stages are the dump's measurements; measured timings stay under `replay.original`.

## Git-mined query set

`cargo xtask mine-queries --repo <repo-root> --key <workspace-key> --out evaluations/mined/<key>.toml [--max 300]` reads `git log` only and turns each qualifying commit into a query: the subject plus the first body paragraph when it adds words (at most 300 characters), the touched supported-extension files as `expected_paths`, `top_k = 10`.

- It skips merges, reverts, subjects under four words, formatting commits (a subject containing the whole word lint, clippy, fmt, rustfmt, formatting, typo, typos or whitespace), commits touching no or more than ten supported source files (lockfiles, vendored and generated paths do not count), and repeated query text; `--max` keeps the most recent. `expected_paths` keeps only touched files that still exist at `HEAD`, following a git-detected rename to the current path (an undetected or heavily edited rename loses the file), and evaluation searches the checked-out tree rather than the commit's parent, so labels are an approximation.
- Tags: `keyword` (the query contains the words of a touched file's stem, in any spelling, excluding a short list of generic stems such as `main`, `mod`, `lib`, `index`, `types`; or a code-identifier-shaped token: `snake_case`, a `::` path, a `--flag`, a `/` between lowercase letters or digits or a `.` between word characters as in `src/lsp` or `index.rs`, or an inner capital as in `camelCase`, ignoring proper nouns such as `JavaScript` and `GitHub`; prose like "LSP/embedding" does not count) or `keyword-agnostic`; `gold-drift` (more than half of the commit's changed lines, from `git log --numstat`, are in files that are not gold: unsupported or excluded files, deleted files, files gone from `HEAD` even after renames; a pure move counts on both sides, an exact 50/50 is not drift), so a miss may not be a retrieval failure; and `short-query` (under 8 words) or `long-query` (25 or more), counted on the text sent to search. The report adds `by_tag` (executed count, hit@1, hit@3, MRR, mean nDCG@10 per tag); any definition's query may carry `tags = [...]`, which only group the aggregate.
- `evaluations/mined/self.toml` (workspace key `self`) is the generated set for this repository: run it like `core.toml` (`--workspace "self=$PWD"`), regenerate rather than edit it, never use it to tune ranking. `core.toml` is the hand-written required set.
