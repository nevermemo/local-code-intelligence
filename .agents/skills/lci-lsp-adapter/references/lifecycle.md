# LSP lifecycle and routing

- Define the executable, initialization options, workspace-root policy, supported language identifiers, timeout, and candidate limit as adapter data.
- Resolve the workspace root deterministically from the indexed canonical workspace. Do not use the editor's current folder as hidden state.
- Start lazily on the first applicable symbol/navigation request or retrieval channel use.
- Reuse one healthy process per workspace and configuration. Serialize JSON-RPC writes, correlate response IDs, drain notifications, and keep stderr from corrupting protocol output.
- Bound initialization and requests. On a transport failure (process exit, closed pipe, malformed protocol data including an `error` member that is not an object with an integer `code` and a string `message`, or that comes with a non-null `result`, or inactivity timeout), discard the client and allow one fresh retry where the operation is safe. A JSON-RPC error response is not a transport failure: the server is alive, so the session is kept. The manager repeats a request on the same server (up to two repeats; a repeat starts only within 5 s of the first error response, and each request keeps its normal timeout) when the error is `ContentModified`, `ServerCancelled`, `RequestFailed`, or one the adapter reports through `LspAdapter::is_loading_error` (rust-analyzer's "file not found" while not yet ready); any other error response is returned as that provider's error.
- Stop child processes when the application shuts down, when the owning state is dropped, or when a session is released or discarded (below). On Windows the transport puts each server in its own job object (kill-on-close) so the processes a wrapper started (`cmd.exe` shims, `rustup` proxies) end with it; a new adapter needs no code for this. If the job cannot be created or the server cannot be assigned to it, the server runs unconfined (only its direct process is stopped) and a one-time warning says so.
- LSP search is one candidate channel. Its failure must not suppress available semantic or lexical results.
- Direct navigation validates supported language before startup and reports tooling failures as MCP errors.
- Normalize UTF-16 character offsets according to LSP. Public input line numbers remain one-based.
- Map a location only to indexed chunks of that adapter's language and only inside the canonical workspace.

## Starting, priming, and the search budget

- **One start per (provider, workspace).** `Manager` keeps a session per key. The start (spawn, `initialize`, the adapter's `after_initialized` warm-up wait such as rust-analyzer's quiescence wait of up to ~10 s) runs on a detached task owned by the session, never inside the future of the caller that asked first. Concurrent callers share that one start. A caller that gives up (a search past its budget) only stops waiting; it must not cancel the start, because dropping a start mid-way kills the child (`kill_on_drop`) and throws the warm-up away. A failed start is reported to the callers that waited on it and is replaced by the next caller. Discard a session on a transport failure only by identity, so a second caller reporting the same failure cannot remove the replacement; the discard also stops the failed session's server (the release mechanics below, on a detached task so the retry's fresh start is not delayed).
- **Priming.** When a start succeeds, the same task sends one `workspace/symbol` request (`PRIMING_QUERY`, a single common letter in the `<term>#` form searches use). It makes the server build the symbol index its first real query would otherwise build (8-30 s on a large Rust workspace). Priming is never cancelled by a search budget and is bounded only by `lsp_timeout_seconds`. Its duration is logged at `debug`, its failure at `warn` (the session stays usable). Only `workspace/symbol` callers wait for priming; definition and references are served as soon as the start succeeds. A new adapter needs no code for this; verify that its first `workspace/symbol` is the expensive one, or that the generic priming query is harmless for it.
- **Per-search budget.** `lsp_search_budget_ms` (default 1500) is the most one search waits for each provider's symbol queries; providers run side by side. A provider that is still starting, still priming, or slow costs the search at most the budget: the search keeps the answers the provider already gave, returns, and reports an informational `notes` entry. That is not a `warning`, because nothing failed and `evaluate` counts warnings as fallbacks. The session is never discarded for running past the budget. With the LSP channel as the only enabled channel, a cold server is a clean miss plus the note, not an error.
- **Abandoning a request.** A request future that is dropped before its response (a search past its budget) removes its pending entry and sends `$/cancelRequest`; the session stays and the late response is ignored. Writes run on a detached task so a dropped caller never leaves half a frame on the pipe.
- **Stuck servers.** A server that answers an error response is alive, so its session is kept, but one that answers nothing except transient errors (`is_transient`: the protocol's `ContentModified`, `ServerCancelled`, `RequestFailed`, and the adapter's `is_loading_error`; not `RequestCancelled`) for `lsp_stuck_seconds` (default 900; `0` never) is wedged, not loading. `Session::note_answer` updates a `TransientStreak` for every answer as it arrives, each repeat's too, from inside the attempt closure of `Manager::send`, so a call that the search budget cancels still counts; a result, an error that is not transient, or a change of the transport's `$/progress` count (a server that reports progress is loading) starts the span over, and the first transient answer at least that long after the span began marks the session `stuck`. A stuck session is replaced by the next `Manager::session` call for its key (the old server is shut down on a detached task), or at once by the `Manager::send` call that is still waiting, which still returns the server's own error. It is time and not a count of failed requests because a burst of concurrent searches fails many requests within seconds of a normal load. `RequestCancelled` (-32800) answers a request that was cancelled and says nothing about the server: a late one to a request this client cancelled never reaches `note_answer` (the reader drops a response whose id is not pending), and an uncancelled one is an error that is not transient. Choose a value above the longest load of the language server you expect: a repository that needs longer is restarted every time the span runs out. The default is not measured, and neither is what a wedged server's `$/progress` looks like. A `warn` logs the replacement.
- **Diagnosing a slow search.** `RUST_LOG=local_code_intelligence=debug,lci_core=debug` shows the session start and priming durations, the quiescence wait (`warn` when it expires), a `warn` for every transport failure that discards and restarts a session (the usual cause of a sudden multi-second search), and the code and message of a server's error responses (`debug`; `warn` when a transient error outlasts the repeats).

## Releasing a session

- **Idle release.** `lsp_idle_timeout_seconds` (default 1800; 0 = never, which was the only behaviour before idle release existed) starts a sweeper in `Manager::new` that ticks every `clamp(idle / 4, 1 s, 30 s)`. It releases a session only when the session is ready, has finished priming, is not in use (no caller holds it: the strong count is checked under the registry lock, where callers get their handle), and has been idle for the timeout. Use means `Manager::session` handing the session out (touched under the lock) and the caller's wait for the start and priming ending (touched again); status polls and the session's own priming do not count. Values under 60 s are for tests.
- **Release mechanics.** A released session is removed from the registry under the lock and shut down outside it: `shutdown` request (bounded by `SHUTDOWN_GRACE`, 2 s), `exit` notification (write bounded at 200 ms), then up to 2 s for the process to exit, then kill and reap (bounded at 500 ms): about 4 s at most. A session that is still starting counts as released; its process ends when the last handle drops, and a caller already waiting on that start is still served by it. `Manager::release(workspace)` and `Manager::shutdown_all()` release explicitly; they skip the in-use check, so a request in flight fails and takes the usual retry-once path with a fresh session.
- **At service exit.** Ctrl+C on `serve` releases every server the same way, side by side, within a budget of `2 * SHUTDOWN_GRACE + 1 s` (5 s in all, `release_language_servers` in `src/main.rs`); servers still running after it are killed on exit. `POST /v1/release_workspace` releases one workspace's servers on demand.
- **After a release.** The next call starts a fresh session transparently. It primes again, so the first search may spend its budget and report a `notes` entry, exactly as after `serve` starts.
