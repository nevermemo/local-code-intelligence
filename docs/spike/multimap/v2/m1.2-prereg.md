# M1.2 pre-registration (trimmed): `reads_key` translation edges and the "+ translation" arms of `impact`

Slice M1.2 of the multimap spike v2, trimmed by the coordinator to the one kind that has a measured consumer
(M1.4 results, `config-key` stratum). T4 `raises` and T7 `uses_dep_item` stay deferred: nothing measured so far
reads them. This file is written before any extractor code, any key table, any edge and any arm. The commit
that adds it precedes the commit of the code and of any result. Results go to
`docs/spike/multimap/v2/m1.2-results.md`.

Labels: [M] measured, [I] inferred, [G] guess. Nothing in this slice is a gate: the MVP has no viability gates,
so a number here is data about the order of work, not a verdict.

## 1. Question

Fixed before any run: **does a `reads_key` edge (config key to the code that reads or sets it), extracted with a
second witness, make an `impact` closure better on the `config-key` stratum of the M1.4 gold, without
changing anything elsewhere?**

Three sub-questions, each with its own measurement:

* **Q1 (extractor).** Is the extractor right? Per-edge precision and recall of `reads_key` against the two
  golds that cover config keys (section 4), with the witness class of each edge.
* **Q2 (consumer, anchor).** Does resolving a key through the key table (TOML key to the `Config` field) give
  the closure a better anchor than M1.4's rules? M1.4 left the `config-key` kind at C - G = -0.245 [-0.413,
  -0.084] (n 30) [M]: 11 of 30 C anchors are "none" and 2 are wrong, and 3 of 30 N anchors are wrong.
* **Q3 (consumer, text).** Does the lexical class (a key written as TOML text inside a Rust string, which no SCIP
  closure can return) close the ceiling's recall gap? O's `config-key` recall is 0.933, 9 of 30 items under 1
  (`impact-0119, 0121, 0122, 0128, 0129, 0130, 0132, 0140, 0145`), while outside the kind it is 0.999 [M, M1.4
  files]. Precision of O is 1.000 on the kind.

This is a **retrieval-plus-lookup ablation** on a frozen tree, as M1.4: recorded ranked chunks and a question
in, a declaration set out, gold scorers out. It is not an agent result.

## 3. The kind: `reads_key`

An edge `reads_key(K -> D)` joins a **config key** `K` (TOML path, `section.key` or a top-level `key`) to a
**declaration** `D` (same record as M1.4: path, line, name, SCIP symbol) that reads or sets it. Each edge
carries a `role` (`read`, `write`, `init`, `toml-text`) and its **witnesses**.

### 3.1 Key table (the translation proper)

Built from the tree only, by lines (no TOML or Rust parser is added to `lci-maps`):

1. Keys: every uncommented `key = value` line of `config.example.toml`, with `section` from the nearest
   `[section]` header above (none for a top-level key). Expected: 34 keys [M, M0.x gold method text].
2. Field: the section names a field of the struct `Config` in `config.rs` (hyphens to underscores); the type of
   that field is the section struct; the key names a field of that struct. A top-level key names a field of
   `Config`. A `#[serde(rename = ..)]` or `alias` within the 3 lines above a field replaces its name; the
   entry is flagged `renamed`. The SCIP symbol is the definition occurrence of that field at its line. A key with
   no match is `unmapped` and produces no edge; the count is printed.
3. Ambiguity: the same bare key may appear in several sections. The table stores every `(section, key)`.

### 3.2 Extraction (per key `K` with field symbol `F`)

Witness W1 is **SCIP**, witness W2 is **`rg`** (text). An edge is `confirmed` when both witnesses name the same
declaration, `scip` or `text` when only one does.

* **W1, role `read`/`write`/`init`.** Non-definition SCIP occurrences of `F`, attributed to the innermost unit
  (M1.4 `closure`: same units, same enclosing-range repair). Role by the text at the occurrence: followed by
  `=` but not `==` is `write`; followed by a single `:` in a struct-literal position (the token before is `{`
  or `,`) is `init`; else `read`. Definition lines (the field itself, `config.rs` declaration) are not edges.
* **W2, text.** `rg -w -n -g '*.rs'` for the field's bare name over `<tree>`; drop hits in comments and in
  string or character literals (M0.4 / M1.4 scanner); keep a hit only if the file contains the owner name
  (the section struct or `Config`) as a whole word, or the hit is written `.key`; declaration = innermost SCIP
  definition range holding the position (position only). Role by the same text rule.
* **Rule L (TOML text in Rust strings), role `toml-text`.** Not reachable by SCIP. A hit of the key inside a
  string literal counts when it is the first word of a TOML line in that literal (after a `\n` escape, a real
  line break or the literal start) followed by `=`, and, for a key with a section, the nearest `[section]`
  header above it **in the same literal** names that section; a top-level key needs no header. If the header
  sits in a neighbouring literal, the hit is accepted only when the bare key is unique in the key table. Struct
  literal initialisers `key:` count (role `init`) in files outside SCIP (the one file the index does not hold)
  when a `Config {` or `<Section>Config {` literal opens within 14 lines above. Declaration = innermost
  enclosing function found by brace matching for files outside SCIP, the SCIP unit otherwise. These are the
  only edges with a single witness by nature; their class is `text-only (L)`.
* Edges are deduplicated by `(K, declaration)`; a pair keeps its strongest class and the union of its roles.

### 3.3 Independence of rule L from the gold (declared before any code)

The gold's own R1 for config items was built by SCIP closure plus a lexical rule of the same kind as rule L
(aggregate: 24 lexical references in 12 of the 34 config items, 6 of them in tests that set the key [M, gold
record]). The rule L implementer therefore must not copy it: the implementer writes rule L from section 3.2
only and **does not open** the gold's `lexical_refs`, `r1` entries of config items, or its builder scripts
before the edge file of section 6 is frozen (hash recorded). After the freeze, rule L's text-only edges are
compared declaration by declaration with the gold's lexical declarations (agree, only extractor, only gold),
reported as a count with item ids. A match is a reproduction, not a second opinion on correctness.

## 4. Gold for the per-edge measurement

Neither gold is independent of SCIP; this is stated here and repeated in the verdict lines.

1. **Impact gold, `config-key` stratum (n 30 primary items; 4 more config items are non-primary and not
   scored).** Per item the gold R1 is the declarations that read or set the key (SCIP closure of the field
   symbol, plus the lexical declarations above, minus the dump-copy declarations that the gold marks
   neutral). Per-edge precision and recall of `reads_key` against it = `decl_precision` and `decl_recall` of
   the arm `O+T` on the 30 items, through the unchanged scorer (neutral declarations are handled by the
   scorer). Roles are all four. Tests are included.
2. **Flow gold, `config-flow` stratum (n 15 items; 31 reader declarations in total [M, gold record]).**
   Per item: TOML key, section, field symbol, and the **reader declarations** = innermost declarations of
   reads of the field outside `config.rs`, outside test files and test modules, writes and struct-literal
   initialisers excluded. Per-edge scoring by the new checker over edges `(K, D)`:
   * key to field: the extractor's field symbol equals the gold field symbol (15 edges);
   * key to reader: extractor edges of role `read`, with declarations not in `config.rs`, not under a `tests`
     path component and not inside a `#[cfg(test)]` module, against the gold readers; precision and recall per
     item, mean over items, and over pooled edges with Wilson 95% intervals;
   * the gold marks the readers inside `config.rs` (validation, `Default`) as ignorable; the checker ignores
     them in both directions.
3. **Circularity [I].** The flow gold's reader set equals one `grep` of `.key` outside `config.rs` (the gold
   record states its builder checked that for each item), and W1 reproduces the SCIP side. A high score here is
   a reproduction of the method of the gold, not a test of correctness; its use is as a regression gate for
   the extractor (a defect shows as a miss), not as evidence for the kind. The impact gold shares the SCIP
   closure with W1 for every non-lexical edge. **Only the lexical class and the key-to-field translation are
   measured against something the closure does not already hold**, and even those follow the gold's own rule
   (section 3.3).
4. An independent check exists and is not run here: rename each field in a scratch worktree and read the
   `compile_error_at` edges of M1.3's probe. It is the next measurement if the kind survives (section 8).

## 5. Arms

Every arm returns, per item, a set of declarations, as M1.4 (`{path, line, name, symbol}`, order carries no
meaning, safety limit 2,000 declarations per item). Base arms G, O, C, N are the M1.4 arms, unchanged.

**Key anchor.** For a query, the `code_names` of M1.4 give the names. A name **resolves to a key** when its last
segment equals the bare key of exactly one table entry, or of several entries and the query also names the
section as a code span (`[section]`, `section.key`, `section::key`, or a span holding the section name alone). A
name with several candidate entries and no section hint **abstains** (the base anchor applies). A key anchor
carries `F` (the field symbol) and `K`.

| arm | what it is |
| --- | --- |
| G, O, C, N | M1.4, unchanged. G `grep_baseline` stored values; O `Cl(gold seed)`; C anchor from hits, `k = 5`; N anchor from the question. |
| **O+T** | `ClT` of the gold seed: if the gold seed symbol equals the field symbol of a table entry, `ClT(K)` = all declarations of all `reads_key(K -> D)` edges (W1 union W2 union rule L, all roles); otherwise `Cl(seed)` as O. Isolates the extractor from every anchoring effect. Uses the gold seed, like O. |
| **N+Ta** | N, but a name that resolves to a key supplies the anchor `F`; the closure is the plain `Cl(F)`. Anchor translation only. |
| **N+T** | N+Ta with the `ClT(K)` closure for key anchors. All other items identical to N. |
| **C+Ta** | C, with one addition to the candidate rule: among the chunks of rank 1 to `k = 5`, a table entry whose `config.example.toml` assignment line lies inside the chunk's file and line span, and whose bare key matches a name of the query, is a candidate (section known from the file, not from the query). Ties as M1.4 rule 3 (best chunk, then most segments, then earliest line, then string order; a SCIP definition candidate and a table candidate in one chunk tie on the same terms). Plain `Cl(F)` closure. |
| **C+T** | C+Ta with the `ClT(K)` closure for key anchors. All other items identical to C. |

C+T, N+T and O+T are the "+ translation" arms of the M1 brief. The `a` arms exist to separate the key table from the
edges: any gain of an `a` arm is credited to the translation table, and only the difference between `+T` and
`+Ta` is credited to the text and role edges. V, R, B, OD, CD are not re-run (no config-key reading depends on
them). Sensitivity, descriptive only: `O+T` restricted to `confirmed` edges; `C+T` at `k = 1` and `k = 20`.

**Gating.** A table entry is consulted only for names that resolve to a key (above). The `+T` arms change an item
only through a key anchor, so an item whose names resolve to no key is identical to its base arm. The number of
items whose answer differs from the base arm is printed per arm and kind; items outside the `config-key` kind
that change are listed by id.

**Determinism and anchors.** Deterministic, no model; `rg` output sorted; each arm run twice, byte-identical.
The anchor step reads only the stripped anchor input of M1.4 (query text, chunk file and line spans) plus the
tree; it never reads either gold. Key anchors (N+T, N+Ta, C+T, C+Ta) are written and hashed before any `+T` arm
other than O+T is scored.

## 6. Order of work

1. Build the key table and the full edge file for all 34 keys from the tree and the index only; write both,
   record their sha256 (the **freeze**). Print: keys, unmapped, entries flagged `renamed`, edges by class and
   role, edges per key (min, median, max).
2. Only then open the golds: the per-edge checks of section 4, the lexical comparison of section 3.3.
3. Key anchors for N and C (frozen, hashed), then the arms of section 5, each twice, then scoring and pairing.

A change to the extractor or the table after step 2 is a deviation, listed in the results with its reason; the
first full run stays in the record, and a repeat is allowed only for an invalid run (section 7).

## 7. Metrics, intervals, reading rules

From the M0.1 scorers, definitions in `gold-scorers.md`; nothing is added to the scorers.

* **Primary table:** `decl_f1`, `decl_precision`, `decl_recall` for G, O, O+T, N, N+Ta, N+T, C, C+Ta, C+T on
  the `config-key` stratum (n 30), outside it (n 111) and overall (n 141). Bands `unique`, `some`, `common`
  inside `config-key` (12, 10, 8) are printed and are below 10 where the cell says so ("too small to read").
* **Anchor accuracy** (share of config-key items whose anchor equals the gold seed symbol), with Wilson 95%
  intervals, the counts of wrong, none and abstained, and the items whose anchor changed against N and C, by
  id, for N, N+T, C, C+T. Read after the anchors are frozen.
* **Per-edge** numbers of section 4 with Wilson 95% intervals, per witness class (`confirmed`, `scip`,
  `text`, `text-only (L)`) and per role.
* **Per item and intervals**: as M1.4 section 4: percentile bootstrap over items, 10,000 resamples, seed
  20261014; Wilson for 0/1 values; paired differences by the same bootstrap over per-item differences, with
  counts of items better, tied and worse. Every table prints `n`; a cell under 10 items is printed and labelled
  "too small to read".
* **Reading rules.** Inherited from M1.4 section 5: rule 1 (M0b rules 1, 3, 4, 8, 9; no setting changed after the
  first full run; results [M], explanations [I] or [G]); rule 2 (**"X beats Y"**: the paired 95% interval of X
  minus Y excludes 0 on the positive side and the point difference is at least 0.05; an interval above 0 with a
  difference under 0.05 is "small gain"; an interval containing 0 is "no evidence of a difference"; "worse" is
  the mirror); rule 9 (a defect is not a result: an item for which an arm crashes or exceeds the limit is listed
  and scored as empty; more than 1 of 30 such `config-key` items, or more than 5 of 141 overall, makes the arm
  "run invalid"). New rules:
  1. **Primary comparisons** (the only ones with a stated conclusion), all `decl_f1` unless noted:
     * **PT-a (extractor, Q3):** O+T minus O on `decl_recall`, `config-key`, n 30, with the **gap closure** count:
       of the 9 items under 1 in O, the number at 1 in O+T, and `decl_precision` of O+T on the kind. The ceiling
       gap is 0.067 [M], so the 0.05 floor of rule 2 would demand closing three quarters of it; the reading is by
       count, not by rule 2: "closes the gap" = at least 6 of 9 items at recall 1 and precision at least 0.99; "partly" = 3 to
       5; "does not" = 0 to 2 [G, a count set before the data].
     * **PT-b (anchor and edges, Q2):** N+T minus N, and C+T minus C, `decl_f1`, `config-key`, by rule 2.
     * **PT-c (translation or edges):** N+T minus N+Ta and C+T minus C+Ta, same rule: what the text and role
       edges add over the key table alone.
     * **PT-d (no regression):** for each `+T` arm, overall `decl_f1` paired against its base arm, **and** the
       number of the 111 items outside `config-key` whose per-item `decl_f1` is lower than the base arm's. "Does
       not regress" = that number is 0 and the overall paired interval has a lower bound of at least -0.01.
       One lost item outside the kind is reported by id and its cause is found before any other reading.
     * Everything else (C+T and N+T against G, anchor accuracy, per-band cells, per-class precision, the
       confirmed-only and k sensitivities) is descriptive and carries no verdict.
  2. **Per-edge reading.** The flow-gold checks (key to field 15/15 expected; reader precision and recall) are
     read as a regression gate: below 0.95 on either is an extractor defect to be explained, not a finding. The
     impact-gold per-edge numbers are read with the class split of section 7.
  3. **Same-oracle caveat inside every verdict line** (as M1.4 prereg 12b): the gold shares SCIP with W1, the
     flow gold is grep-level by construction, the lexical gold follows a rule of the same kind as rule L, and G is
     handed the seed name (and for config items that includes the section) while C, N and the `+T` arms are not.
     The verdicts read "can the key be resolved and the closure completed", not "independent correctness".

## 8. Reading table (what this can change)

Nothing is a gate. Fixed here so the reading does not depend on the numbers.

| outcome | reading and effect |
| --- | --- |
| PT-a "closes the gap" **and** PT-b rule 2 for N+T or C+T | `reads_key` has a consumer in `impact` on config-key: keep the kind; T1 goes into the registry as the second translation kind (after the lookup), and the independent rename-probe audit (M1.3 `compile_probe` over the fields) is the next measurement. |
| PT-b met, PT-c not (the `a` arms carry the gain) | The gain is the **key table** (TOML key to `Config` field), not the edges. Keep a key resolver in the anchor step; do not build `reads_key` as an edge kind for `impact`. |
| PT-a "closes" or "partly", PT-b not met, PT-c small | A thin lexical-witness feature for a handful of items (the 9 under 1): record it, do not treat it as a kind. |
| **Kill:** PT-a "does not" **and** neither PT-b comparison meets rule 2 | The kind has no consumer on this gold: T1 is dropped from M1.2, the config-key loss stays an anchor problem (C 11 none) and is carried by the anchor work of M1.4 section 8. |
| PT-d fails (an item outside the kind changes for the worse) | A defect of gating, not a result; the cause is found and the arm rerun once as an invalid run. |
| Flow-gold regression gate below 0.95 | An extractor defect; the edge file is rebuilt once, disclosed, and the freeze is re-recorded. |
| Any `+T` arm run invalid | That arm is removed from PT-b and PT-c; the others are read. |

Whatever the outcome, the numbers become the "+ translation" column next to M1.4's `impact(x)` column. No outcome
supports a claim about agent performance.

## 9. Validity and stated limits

* **Leakage.** C, N and every `+T` arm see no gold. The key table is built from `config.example.toml` and
  `config.rs`; the anchor step reads only the anchor input. O+T uses the gold seed symbol, as O. Every impact question
  names the key in a code span [M, M1.4 results]; whether it also names the section varies by question template and is
  not counted before the run. The section hint is the only thing the key anchor uses beyond the bare key, and the
  number of abstentions is printed.
* **Same-oracle circularity** [I]: section 4.3. The strongest honest claim the result can carry is that the
  extractor and the key table reproduce the gold's builders from the tree alone, and that they do or do not
  convert that into a better anchor from retrieval hits (C+Ta) and from the question (N+Ta).
* **Power.** `config-key` has 30 items (12/10/8 by band); the paired intervals of M1.4 on this kind are about
  +/-0.17 wide, so a gain under about 0.10 will not be resolved. The flow gold adds 15 items and 31 readers: the
  per-edge intervals are wide too. The two golds may share keys; the overlap is printed, not corrected.
* **Rust only; one tree, one commit, 141 items, one recorded FR run.** The tree is the project's own code with
  its own `Config` struct; the extractor rules are tied to `serde` tables in `config.rs` and a single example
  TOML. It says nothing about other config systems (environment variables, CLI flags, `figment`-style layering,
  dynamic keys). `docs_recall` stays 0.0 for every arm (no arm returns documentation lines; the docs edge is
  not part of this slice).
* **k is a guess and is not tuned.** The sensitivity arms are descriptive.

## 11. Cost and files

Local CPU only. No model service, no GPU, no network, no listener. The run is a few minutes: the index load and
34 `rg` calls, the 141-item arms of M1.4 in seconds each; the bootstraps a few more.

Implementation, committed after this file and before any run: a `lci-maps` module (`reads_key`: key table,
extractor with witnesses, rule L) and an extension of `impact_eval` (arms `OT`, `NTa`, `NT`, `CTa`, `CT`, and
subcommands `reads-key` to write the edge file and `check-flow` for the per-edge check), with unit tests on
synthetic strings (rule L, role rules, ambiguity abstention). One implementer slice; no new dependency (no TOML or
Rust parser).

Scratch (not committed): `<scratch>/m1.2/` with the key table, the edge file with hashes, the key anchors, the
run, score, per-item and paired files of every arm, and the logs. Committed: this file, the code, and
`m1.2-results.md` with placeholders for paths and the hashes of section 2. Private gold content never enters a
committed file: aggregates and item ids only.

## 12. Run

```text
reads_key_eval reads-key --root <tree> --scip <frozen index> --out <scratch>/m1.2/edges.json   (freeze: sha256)
reads_key_eval check-flow --edges <scratch>/m1.2/edges.json --gold <gold>/flow.json
impact_eval anchors-key --rule N|C --anchors <scratch>/m1.4/anchor-input.json --root <tree> \
    --table <scratch>/m1.2/edges.json --out <scratch>/m1.2/anchors-<rule>T.json
impact_eval run --arm OT|NTa|NT|CTa|CT --scip <frozen index> --root <tree> --edges <scratch>/m1.2/edges.json \
    [--gold <gold>/impact.json for OT only] [--anchors <scratch>/m1.2/anchors-<rule>T.json] --out <run>.json
cargo xtask gold score --set impact --gold <gold>/impact.json --run <run>.json --out <score>.json
```

Order: freeze, flow check, key anchors (frozen), then O+T, N+Ta, N+T, C+Ta, C+T, each twice, scoring and
pairing against the M1.4 reference runs. One configuration, no tuning between steps.
