# M1.5 pre-registration: a compiler-witnessed audit of the `impact` gold

Slice M1.5 of the multimap spike v2 (boundary decision 9.4: "one independent, non-SCIP audit of the
config-key items and a sample of the other `impact` items, compiler-witnessed"; the rename-probe
check named in `m1.2-prereg.md` section 4 item 4 and owed by row M0.2). It uses the M1.3
`compile_probe`, the M1.4 unit rule and the frozen M1.4 tree, index and run files. No model is
called. Written before anything is run in this slice; the commit that adds this file precedes any
run. Results go to `docs/spike/multimap/v2/m1.5-results.md`.

Labels: [M] measured, [I] inferred, [G] guess. Nothing in this slice is a gate: the MVP has no
viability gates. The audit file lists disagreements with their cause; it does not change the gold
and proposes no fix that it applies.

## 1. Question and hypotheses

Fixed before any run: **for a sample of `impact` items, is the gold's R1 declaration set the set of
declarations the compiler itself reports when the seed's definition is renamed, and where it is not,
which pre-registered blind spot or which defect explains the difference?**

Why the compiler: every M1 verdict (M1.4, M1.3, M1.2) is scored against R1 sets built from the same
SCIP index the closure arms read (the same-oracle caveat of M1.4 section 6, M1.2 section 4 item 3).
`rustc` resolves names with its own resolver and type checker; it does not read the SCIP index. The
reference *sites* that M1.5 compares are therefore independent of SCIP. The one residual dependence
is that sites are mapped to declarations with the M1.4 unit ranges (`unit_at`, from the same index);
the file-level comparison (section 5, F-metrics) has no such dependence and is reported beside the
declaration-level one.

Hypotheses (guesses [G], stated to be tested, with the numeric readings in sections 5 and 8):

* **H1 (gold precision against the compiler).** At least 95% of the gold's compiler-comparable R1
  declarations are in the compiler set K (section 3), pooled over audited items.
* **H2 (gold recall against the compiler).** At least 90% of K (outside the structural classes of
  section 6) is in the gold's R1.
* **H3 (the ambiguous band).** Agreement in band `common` is not worse than in `unique`: the
  type-resolved SCIP closure and the compiler resolver agree even where grep is ambiguous.
* **H4 (config keys).** The 30 `config-key` items agree on their SCIP-witnessed part; their lexical
  witnesses (gold `via_lexical`, 11 declarations in 9 items [M, count over the gold]) are invisible to
  the compiler by construction and are counted, not scored as errors of the gold.
* **H5 (cargo blocking).** A single rename-and-check (K0) is a strict subset of the fixpoint set (K,
  section 3.3) for a substantial share of items, because cargo does not check dependents of a failing
  crate and because a failing `use` hides later uses in the same module [I, M0.5 finding 3]. This
  quantifies how much the plain "rename and read the errors" method of the sketch would miss.
* **H6 (verdict robustness).** The M1.4/M1.2 arms O, N, C, V keep their order and their rule-2
  categories when rescored against the compiler set instead of the gold (section 5.4).

This is an audit of the **membership of R1** for sampled items. It does not audit R2, tests, docs,
the `where-to` gold (the other half of row M0.2), the key-to-field translation of M1.2 (a `serde`
runtime property, not a compile property), or any agent result.

## 3. Method

### 3.1 The rename (stage 0)

For an audited item, the **seed definition** is the gold's `seed.path`, `seed.line` and bare name
(`seed.symbol` gives the kind: function, method, struct, enum, variant, field; for `config-key`
items the seed is the `Config` field and the identifier is the field name, not the TOML key). The
edit renames the identifier on the seed's name line: the first whole-word occurrence of the bare
name at or after the item keyword (`fn`, `struct`, `enum`) or at the line start (variant, field).
Only the definition is edited; no use is touched, no `#[serde(rename = ..)]` string is touched.

**Fresh identifier.** Same byte length as the old one (so no column on any line moves): the last
character is replaced by the first of `_`, `0` to `9`, `q`, `z` that makes a name which is not a Rust
keyword and does not occur as a whole word in any `.rs` file of `<tree>` (`rg -w`). A one-character
name, or no free candidate, takes the old name plus `_` and is listed (columns on that line may
shift by one, which section 3.4 handles).

**Seed that is not renameable as an oracle (listed, never silently dropped).** *Impl-seed*: the
seed method is declared inside an `impl Trait for Type` block (found by a text scan up from the
seed line to the enclosing `impl` header). Renaming it breaks the impl (E0407) and not its callers,
which resolve to the trait's method; the compiler cannot witness references to it. These items are
reported as `impl-seed` with the E0407 site, are excluded from every agreement denominator, and their
number is printed. They are still in the sample (they are real gold items).

### 3.2 One probe call

`compile_probe --tree <tree> --patch <p> --scip <index> --target-dir <T> --out <o>`. The patch is a
unified diff of the cumulative edits of the item, built by a scratch script from file bytes (line
endings preserved; if `git apply` is not byte-exact for a file the plumbing check of section 11
finds it before the audit). The probe applies, runs the oracle, reverts and verifies the tree
clean. Its edges (`compile_error_at`, with code, file, line, column, target unit key, and the SCIP
symbol of the innermost unit or "unattributed") are the only input to the rest. Parsing and
de-duplication are those of M1.3: primary spans of level-error messages, macro-expansion spans
replaced by the expansion site if inside the workspace else skipped and counted, key
`(code, file, line, column)`.

### 3.3 Staging to a fixpoint (the refinement of the sketch)

A single rename-and-check under-reports for two reasons that were already observed in M0.5 and are
not blind spots of the compiler but of the method: (a) cargo does not check a crate whose
dependency failed, so uses in dependents are never reported; (b) when a `use` of the old name fails,
`rustc` binds the name to an error in that module and does not report the module's other uses of
it. So the audit continues the rename the way a refactoring tool would:

* **Round 0** is the plain rename of 3.1. Its set is **K0** (the sketch's method, reported).
* **Heal.** For each error site of the round (any error code) whose position holds the old
  identifier: at the site start, the first whole-word occurrence of the old identifier on that line
  at or after the column is replaced by the new identifier. Exception: for the codes that report a
  struct-literal or struct-pattern field (E0560, E0026) when the identifier is not followed by `:`
  (field shorthand), the occurrence is replaced by `new: old`. A site with no old identifier at or
  after its column on its line is **unhealable** (typically a derived error such as E0063 "missing
  field", which disappears once its cause is healed) and is recorded, not edited. All edits of a
  round apply right to left within a line.
* **Next round**: the cumulative patch (rename plus all heals so far) is applied to the clean
  tree and the probe is called again. Newly reachable crates and newly unmasked uses appear.
* **Stop** when the check passes (zero errors: **converged**), or a round heals nothing (**stuck**),
  or 6 rounds are done, or 15 minutes of wall time are spent on the item (**not converged**). A
  converged item carries a strong certificate: the workspace builds under the new name for default
  features and all targets, so every use the compiler resolves in that configuration was edited. A
  not-converged item's set is a lower bound and is labelled so.
* **K** (the compiler set) is the union over all rounds of the error sites, mapped to units as in
  3.4. K0 is round 0 alone.

Per item and round the audit records: error count, the targets that reported errors, the targets
reached (probe `reached_units`), the targets reached by the unmutated baseline run but not by this
round (**blocked**, as M0.5), the number of healed and unhealable sites. "Crates checked" for the
item is the targets reached in its last round.

### 3.4 Mapping sites to declarations

A site's declaration is the SCIP symbol of the innermost unit holding its 0-based (line, column)
under the M1.4 unit rule (`ImpactIndex::unit_at`: function, method, struct, enum, trait, type alias,
constant and static; variants, fields and associated types are not units). The mapping is done by the
probe, in the coordinates of the round's patched tree; because heals keep byte length except for
shorthand expansion, only a site to the right of an expansion on a line with two units could be
mapped to the wrong unit, and lines carrying an expansion are listed with the item. The item's
**own unit** (the unit at the seed definition) is removed from K, as the scorer skips the seed's own
declaration; so are `accept.neutral_decls`. A site with no unit is **unattributed**; it is kept as a
site and classified by its source line as `use-line`, `impl-header` or `other` (the first two are
structural, no unit exists to hold them, as in M0.5 where all 27 were `use` lines; `other` is
listed). Unattributed sites contribute their files to the file-level set but not to K's declarations.

## 4. Sample

All 30 `config-key` items (12 `unique`, 10 `some`, 8 `common` [M, from the gold]) plus **30 of the
111 other items**, drawn once, before anything is run, by this rule, whose output is a list of item
ids recorded with its sha256 in the results:

1. Non-config-key items are grouped by band, then by seed kind in the order fn, method, struct,
   variant, enum. Cell sizes [M, from the gold aggregates]: `unique` 69 (fn 11, method 10, struct 27,
   variant 12, enum 9), `some` 15 (fn 1, method 6, struct 2, variant 6), `common` 27 (fn 2, method 23,
   variant 2).
2. Quotas: `unique` 12, `some` 8, `common` 10. The unequal quotas oversample the bands that have fewer
   items and the band (`common`) where grep and the closure differ most; sizes are chosen so that each
   audited band has n 18 to 24.
3. Within each cell the ids are sorted and shuffled with Python's `random.Random(20261014)`, one
   generator consumed in the order band (unique, some, common) then kind. A band is filled by taking
   one id per non-empty kind in kind order, cycling, until its quota is met. This gives, by
   construction, `unique`: fn 3, method 3, struct 2, variant 2, enum 2; `some`: fn 1, method 3, struct 2,
   variant 2; `common`: fn 2, method 6, variant 2.
4. The audited sample is thus 60 items: band `unique` 24, `some` 18, `common` 18. Item counts per
   cell of the audited sample are printed in the results. Population estimates from the sample use
   no weighting; every statement is about the audited items and the strata, with n beside it.

**Extension (tier 2).** The remaining 81 items are an optional second tier, decided after tier 1
and only on its measured wall time (rule: the median item took under 3 minutes). Tier 2 uses the same
rules, is reported separately, and does not alter any reading of tier 1. If it is not run, the results
say "not run".

**Order and budget.** Config-key items first (id order), then the other 30 (id order). The brief
estimated about 2 hours; a staged item may need up to 6 rounds, so [G] 2 to 5 hours under the A/B
load. If cumulative wall time passes 5 hours, items not yet started are reported "not run" and not
replaced.

## 5. Metrics

Let, per audited item, **G** be the gold R1 declarations after the scorer's skips (seed's own
declaration, `accept.neutral_decls`), split into **G-scip** and **G-lex** (the declarations the gold
marks `via_lexical`), and **K** as in 3.3. Declarations match by the scorer's rule (symbol, or path plus
a line inside the declaration span, or path plus bare or full name), implemented by the same
function as `cargo xtask gold score`.

### 5.1 Declaration level

* **Confirmed** = G-scip ∩ K. **Gold-only** = G-scip minus K. **K-only** = K minus G (R1 only).
* **conf** (gold precision against K) = |Confirmed| / |G-scip|. **cover** (gold recall against K) =
  |Confirmed| / |K|. Reported **raw** (all counted) and **adjusted** (declarations whose
  disagreement is assigned to a blind-spot class B1 to B6 by an automated rule in section 6 leave the
  denominator they are in; the count removed is printed beside each number). The adjusted figure is
  what is read; the raw figure is printed always, so the adjustment can be undone by the reader.
* Item-level: an item **agrees** when, after the removals of the adjusted figures, it has no
  unexplained gold-only declaration and no unexplained K-only unit (B7, B8 and unexplained leftovers
  are not removed). The share of agreeing items, and of items with **no unexplained gold-only
  declaration** (the gold-precision-side event), are the item-level numbers.
* Per item the audit also prints |G|, |K0|, |K|, |Confirmed|, the converged flag, the crates
  checked, the blocked crates, and the class of every disagreement.

### 5.2 File level (SCIP-free)

Gold R1 files against the files holding at least one error site of K (attributed or not), same
raw and adjusted conventions: **F-conf** = |gold files ∩ K files| / |gold files|, **F-cover** the
mirror. These do not depend on the SCIP unit ranges.

### 5.3 Wilson intervals: the "set" of row M0.2

Sets are the strata in which M1 verdicts are read: all audited items; `config-key` (30); the
audited non-config-key items; bands `unique`, `some`, `common` (all kinds, and non-config-key
alone); seed kinds with at least 10 audited items (others printed and labelled "too small to read").
For each set the audit file prints n and:

* **LB-item**: Wilson 95% lower bound (z 1.96) of the share of items with no unexplained gold-only
  declaration. Items are the independent units; **this is the lower bound that is read**.
* **LB-decl**: Wilson 95% lower bound of the pooled adjusted `conf` (declarations as trials), and the
  same for `cover`. Declarations of one item are correlated, so LB-decl is optimistic and is read
  only beside LB-item; the percentile-bootstrap interval over items (10,000 resamples, seed 20261014)
  of the pooled `conf` is printed with it.

For orientation: with no disagreement at all, the Wilson lower bound is 0.886 at n 30, 0.940 at n 60,
0.862 at n 24, 0.824 at n 18 and 0.758 at n 12. A set of n 18 cannot show a lower bound above 0.82
whatever the result: the bands are read as "no sign of a defect", not as a bound near 1.

### 5.4 Verdict rescoring

For the audited items, an **audit gold** is derived in scratch (never committed): the gold with R1
declarations replaced by K (minus own unit and neutral decls) plus G-lex, and R1 files replaced by K
files plus the lexical files. Arms O, N, C (k 5) and V are rescored by the unchanged scorer (one-item
`--partial` scoring, as M1.4) against the audit gold, with the M1.4 bootstrap (10,000, seed 20261014).
Reported: `decl_f1`, precision, recall by band for each arm against both golds, the paired differences
N minus V, C minus N and N minus O against both golds, and whether the rule-2 category ("beats", "small
gain", "no evidence", "worse") of each pair changes. Descriptive, n beside every number, no verdict
beyond "unchanged" or "changed". P1 and P2 of M1.4 compare to G and cannot be rescored (section 2); V
is the textual comparison arm.

### 5.5 K0 against K

For every converged or not item: |K0|, |K|, whether K0 is a strict subset of K, the crates blocked in
round 0, and the share of items where K0 would have missed a gold declaration that K confirms. This
is the measured size of the sketch's blind spot (H5).

## 6. Blind-spot classes and how each is classified

Every gold-only declaration and every K-only unit is assigned **exactly one** cause by the first
matching rule below, in this order. Automated rules (B1 to B6) are run by the audit script from the
gold fields and the source text of the frozen tree; a unit left after them is read once by the
auditor and assigned B7, B8 or `unexplained` with a one-line reason. Nothing is dropped.

| id | class | applies to | rule | effect on the adjusted figures |
| --- | --- | --- | --- | --- |
| B1 | lexical witness | gold-only | the gold marks the declaration `via_lexical` (string and TOML-key witnesses of config items). The compiler cannot see them | removed from the `conf` denominator; counted separately |
| B2 | unchecked or not converged | gold-only | the item is not converged and the declaration's target (crate and kind) was not reached in the last round, or the item is `impl-seed` | removed; listed |
| B3 | macro or derive generated | gold-only, K-only | gold-only: the declaration's span contains a `macro_rules!` definition holding the old identifier, or the old identifier inside a macro-invocation token tree that the macro rebuilds (`paste!`, `concat_idents!`, `stringify!` in an identifier position). K-only: the site is a macro-expansion site replaced by the call site (M1.3 rule) or has a code only generated code can raise | removed |
| B4 | trait-method dispatch | gold-only, K-only | K-only: the seed is a trait method declaration and the unit is an implementor (E0407 on an impl method). Gold-only: the seed is a trait method and the declaration calls it through a generic bound or `dyn` object that the compiler resolves to a different (impl) method after the rename, i.e. a call the rename cannot break. The seed kind is read from the source | removed |
| B5 | test and target scope | gold-only, K-only | the declaration is in a file that no workspace target compiles under `--all-targets` (not reachable from any target's module tree), or in a doc test (`rustdoc` is not run). Test modules and `tests/` are compiled and are **not** a blind spot | removed |
| B6 | cfg-gated code | gold-only, K-only | the declaration or an enclosing module, impl or file carries a `#[cfg(..)]` or `#![cfg(..)]` that is false in the checked configuration: Windows host, default features of every member (the root crate's `spike-maps` feature is off), `test` on for test targets, `debug_assertions` per the profile. The audit script evaluates `windows`, `unix`, `test`, `feature = ".."`, `debug_assertions`, `target_os = ".."`, `not`, `any`, `all`; an atom it does not know is listed for the auditor | removed |
| B7 | silent rebinding | gold-only | the compiler can still resolve the use after the rename, to another item: a glob-imported or in-scope same-name item, an applicable trait method of the same name, or a unit-variant pattern that becomes a catch-all binding. Assigned by the auditor from the source, with the other candidate named | **not removed** (a real disagreement of the oracle, reported as such) |
| B8 | unit-range or column mapping | gold-only, K-only | a K site lies inside the gold declaration's span (same path, line in span) but the symbols differ, or two units share the site's line, or the line carries non-ASCII text before the span (M1.3 note) | not removed; listed |
| B9 | collateral error | K-only | a site whose code and span do not name the old identifier (a derived error, for example E0063 on a literal) and that is not healed away by the last round | not removed; listed |
| B10 | K-only, other gold list | K-only | the unit is in the gold's R2 declarations, `tests`, `tests_deep` or `tests_lexical` of the item (R1 is the one-hop set, R2 the two-hop set and tests are separate lists, so a compiler-visible reference there is not an R1 error) | reported as a separate count; not a disagreement of R1 |
| X | unexplained | any | none of the above | **not removed**; the item's cause text is kept |

Notes. (1) B7 and X stay in the figures on purpose: an adjustment that could hide a real gold error
is not allowed to remove it. (2) B1 to B6 are removed only by rule, never by judgment, so the
adjusted number cannot be steered after the fact. (3) The rename oracle has further limits that are
not classes of a disagreement but of coverage and are stated in section 10 (one configuration, no
`rustdoc`, no runtime).

## 7. Reading rules

Fixed here so the reading does not depend on the numbers.

1. Inherited from M0b and M1.4: results [M], explanations [I] or [G]; n and an interval beside every
   number; a cell under 10 items is printed and labelled "too small to read"; no setting changed after
   the first item is scored; a defect is not a result.
2. **A set is "discharged"** when its adjusted pooled `conf` is at least 0.95 **and** its LB-item is at
   least 0.80 [G, a practical bar set before the data]. The `unique`, `some`, `common` sets of 18 to 24
   items can reach LB-item at most 0.82 to 0.86 (section 5.3), so for them 0.80 means "at most one
   unexplained gold-only item"; **the all-audited and `config-key` sets carry the bound**.
3. **"Weakened"** when pooled adjusted `conf` is below 0.90, or LB-item is below 0.60, or `cover`
   (pooled, adjusted) is below 0.85. **"Partial"** is everything between.
4. H3 is read as: `common` discharged-or-partial and its `conf` not below `unique`'s by more than 0.05
   at the point estimate. Nothing sharper is claimed at n 18.
5. H6 is read per pair of section 5.4: "unchanged" when the rule-2 category is the same against both
   golds on the audited items and the point difference moves by less than 0.05; otherwise "changed",
   named with the pair.
6. An item with `not converged` is read with its set as a lower bound: its gold-only declarations are
   B2, not evidence against the gold. More than 6 of 60 (10%) not-converged items make the audit
   "partially run" and the readings carry that statement.
7. The audit never edits the gold. Fixes it suggests (for example "item X: add declaration D to R1")
   are a list in the results.

## 8. Expectations (guesses, fixed before any run)

* Convergence: 52 to 58 of 60 items converge; stuck items are macro or shorthand cases. `impl-seed`: 0
  to 6 of 60 (method seeds named `fmt`, `from`, `default` and similar).
* Gold precision: pooled adjusted `conf` 0.96 to 1.00; raw 0.92 to 0.98 (the config-key lexical
  witnesses are about 7% of config-key R1 declarations [M, 11 of 149]).
* Cover: pooled adjusted `cover` 0.85 to 0.97. K-only units are mostly B10 (R2 and tests) and B4.
* Items agreeing (section 5.1): 70% to 92%.
* K0 is a strict subset of K for 30% to 60% of items (lci-core seeds block dependents; imports mask
  uses).
* `common` band: `conf` within 0.05 of `unique` (H3 holds).
* Rescoring: N stays above V on `common` against the audit gold, with a point difference of 0.05 or
  more, with probability about 85%; the order O ≥ N > C > V is unchanged.
* Wall time: a warm round 5 to 40 s (root-crate seeds up to 90 s), an item 1 to 6 minutes, tier 1
  2 to 5 hours under the A/B load. The brief's 2 hours is the low end.

An expectation that fails is reported as such; none triggers any action.

the probe on a different input class (renames of real seeds, cumulative patches). No outcome supports a
claim about agent performance.

## 10. Validity and stated limits

* **Independence.** The sites come from `rustc`, not from SCIP. The unit ranges that turn sites into
  declarations come from the SCIP index (section 1); the file-level metric does not.
* **One configuration.** Windows host, default features (the root crate's optional `spike-maps` feature
  is not built), `--all-targets` (library, binaries, tests, examples, benches), no `rustdoc`. Code
  gated otherwise is invisible to K and classed B6. The checked tree is the project's own code; Rust
  only; one commit; 60 of 141 items.
* **The oracle is blind to** (all classed above, none dropped): lexical witnesses (B1), uses rebuilt by
  macros (B3), dispatch that survives the rename (B4, B7), inactive cfg (B6), documentation.
* **Healing is an approximation of a refactor.** It edits only error sites that hold the old
  identifier at their start; it never edits a site that the compiler did not flag, and it stops when
  stuck. A converged item is a full certificate for the checked configuration; a stuck one is a lower
  bound. Healing changes the tree only inside the scratch worktree and is reverted by the probe.
* **Rebinding** (B7) is the one class that is not detectable from the compile result; it is found
  only if a gold-only declaration is read and the other candidate is seen.
* **Probe limits** carry over from M1.3: de-duplication across targets by position, macro spans
  replaced by their expansion site, rustc columns used as SCIP columns.
* **Load.** An A/B batch may run on the machine. Wall times are reported with the load lines of M1.3
  section 6 and are descriptive; they are not a result of this audit.

## 11. Run, determinism and plumbing

* **Plumbing check (first, results discarded).** Two items **outside the sample** (the two lowest ids
  not in the sample whose seeds are in different packages) exercise patch building (line endings),
  probe, healing and revert end to end, and the tree is checked clean. Their sets are not read. A
  defect found here is fixed and disclosed in the results; the audit itself starts only after a
  plumbing pass.
* **Determinism.** Six audited items (the three lowest-id config-key items and the three lowest-id
  others of the sample) are run a second time in full after the audit; their K sets, converged flags
  and round counts must be identical. A difference is flagged and the item is listed as such.
* **Invalid run** (stop, fix, rerun unchanged, the first attempt stays in the record): a hash of section
  2 differs; a revert leaves the tree not clean; the unmutated check of the tree has errors; a healed
  round introduces an error at a site with no relation to the old identifier more than once on an item
  (it is a harness defect, not an item result).
* **Access log.** The first read of the gold, the sample draw, the audit-gold derivation and every rescoring
  run are logged with a time stamp in the scratch directory, as in M1.2.
