# M0.4 pre-registration: the scored-walk harness on the `flow` gold set

Slice M0.4 of the multimap spike v2. Written before the first full evaluation run; the
commit that adds this file precedes the commit of any result. Code: `lci-maps/src/scip_graph.rs`,
`lci-maps/src/walk.rs`, `lci-maps/examples/walk_eval.rs`.

## 1. Question

The v2 design gives every edge a kind, a provenance, a confidence and a witness, and stores no
rank weight. A node whose out-degree is at or below a fan-out gate is followed whole (the hop
returns 1, nothing is scored); above the gate a scorer orders the out-edges. This harness asks,
on multi-hop call paths with known answers:

1. Does a cheap rules scorer rank the true next node of a path above the other out-edges, better
   than a random order and better than source order?
2. Does that survive composition? Does a beam walk with a pop budget recover whole paths, and how
   far does path recall sit from the per-hop success raised to the path length?
3. How large are the out-degrees at the gold intermediates, so the gate (default 8) can be
   recalibrated?
4. How much of the rules arm's result is the question's name overlap (the gold set's
   `name-matching-shortcut` flag) and how much is structure?

This harness measures an ordering signal on an existing graph. It does not measure retrieval,
agent behaviour or latency.

## 3. The graph

Built from the SCIP index with the `scip` crate (Apache-2.0).

* Nodes: every symbol whose descriptor ends in `().` (functions and methods).
* `calls_or_refs`: a reference occurrence of a node inside the innermost enclosing range
  (function, type or macro definition) of another node. One edge per (caller, callee) pair, with
  the first occurrence by (file, line, column) as the witness and the occurrence count as
  `sites`. Provenance `scip`; confidence 1.0, or 0.5 when every occurrence is macro-generated
  (SCIP role bit 16).
* `contains`: a function nested strictly inside another function's range, immediate parent only.
  Provenance `structure`, confidence 1.0.
* Enclosing-range repair, as in the gold's reader: a function whose range equals another
  function's range in the same file, or strictly holds one, takes the span from its name line to
  the closing brace (or `;`) of its body, found by a scanner that skips comments, strings and
  character literals. The gold's reader reports 2,043 call edges and 22 repaired definitions on
  this index; the loader is expected to reproduce both counts (a check on the build, not a
  result).
* No stored rank weight exists in `lci-maps`, so there is no "stored weight order" control.
  Every ordering below is computed at walk time.

Because the gold paths were built from the same index, every gold hop is an edge of this graph
by construction. The run reports how many are (expected: all); a hop whose edge is missing
counts as a miss for every arm.

## 4. The walk

* **Candidates of a node**: its distinct callees, in source order of their first edge (witness
  file, line, column). Out-degree means the number of candidates.
* **`hop(node)`**: if the node has at most `gate` candidates (default 8), or the arm is
  unscored, every candidate is followed with value 1. Otherwise the arm scores the candidates,
  the best `beam` are kept (ties keep source order), and the candidate at rank `r` (0-based)
  gets the value `1 / (1 + r)`.
* **`beam`** is that cut: the number of candidates kept per above-gate expansion (1 or 3). It is
  not a frontier cap.
* **`walk`**: best-first search over path states. A state's priority is the product of the hop
  values on its path; ties pop in discovery order. One pop expands one state. The walk ends at
  200 pops, an empty frontier, or depth 6 (a state at depth 6 is recorded, not expanded). Depth
  6 is the longest gold path and is the same for every item. A node already on the state's own
  path is not revisited; there is no global visited set, so the same node can be expanded by
  several paths.
* **Seed**: the gold entry. The walk needs a start, and the entry is treated as given by an
  upstream seeding map. The descriptive items do not name their endpoints, so the entry is not
  recoverable from the question.
* **Path found**: some discovered state spells the whole gold path (or a listed alternate
  shortest path) from the entry. A node counts as discovered when its parent is popped, so the
  target needs no pop of its own. "Target reached" (by any path) is reported beside it.

## 5. Arms and controls

| arm | order of candidates above the gate |
| --- | --- |
| `rules` | `prior(kind) * conf * (0.1 + 0.3 * idf + 0.6 * overlap)`. `prior`: `calls_or_refs` 1.0, `contains` 0.5. `idf`: `ln((N+1)/(indegree+1)) / ln(N+1)` over the node's distinct callers, 0 to 1. `overlap`: share, by token idf, of the question tokens that occur in some symbol name which the candidate's own name tokens contain, 0 to 1. The weights are set by hand now and are not tuned on the gold. |
| `rules-noname` | the same with `overlap` fixed at 0 (structure only). |
| `random` | seeded random order; 5 seeds, 1 to 5; reported as mean, sample standard deviation, min and max over the seeds. |
| `bfs` | unscored FIFO: every callee in source order, whatever the gate and the beam. Beam 1 and beam 3 are the same walk. |

Query tokens come from the item's `question` text only: lowercase word tokens (split on
non-alphanumerics, camel case, acronym boundaries and letter-digit boundaries), minus one-letter
tokens and the fixed stopword list `STOPWORDS` in `walk.rs` (English function words and the
boilerplate of the question templates). The gold's accept tokens, intermediates and target never
feed a query. A symbol's name tokens come from its `Owner::name` form (the impl type, trait or
module, then the function name).

## 6. Metrics

All computed on the main gold path; alternates matter only for path found.

* **M1, per-hop rank.** At each node of the gold path that has a next node (the entry and every
  intermediate), the rank of the true next node among all candidates under the arm's order,
  ignoring the gate. Hit@1 and hit@3, pooled over hops, with Wilson 95% intervals. The other
  candidates are the distractors.
* **M2, by item and by cluster.** Item level: the share of items whose every hop is hit@1 (and
  hit@3). Cluster level: M1 pooled within each `prefix_cluster`. The 96 path items carry 24
  prefix clusters (`pc-01` to `pc-24`); the 15 `cfg-*` clusters belong to the excluded
  config-flow items. The brief's "15 clusters" is therefore reported as these 24.
* **M3, path recall.** Share of items whose whole path is found, at beam 1 and beam 3, 200-pop
  budget, with Wilson intervals; mean pops used; target reached by any path.
* **M4, compounding.** By path length `k` (edges): the pooled per-hop success under the walk's
  policy (a hop succeeds when the node is under the gate, or the true next node ranks within the
  beam; the unscored arm always succeeds), `p^k`, the share of items whose every hop succeeds
  (the ceiling for any budget), and the observed path recall. The gap `ceiling - observed` is
  the budget's cost; `p^k - ceiling` is the correlation between hops.
* **M5, out-degree.** Percentiles (10, 25, 50, 75, 90, 95, 99, max) of the out-degree at the
  start node of every gold hop, and the share above gates 0, 2, 4, 6, 8, 12, 16, 24 and 32; the
  same percentiles over all nodes of the graph that have callees, for context. These recalibrate
  the gate; the gate is not changed in this run.
* **M6, groups.** Every metric above for: all 96; `headline` (55) and non-headline (41);
  `name-matching-shortcut` flagged (58) and not flagged (38); headline and not flagged (26).
* **M7, random spread.** The headline numbers (hop hit@1 and hit@3, path recall at beam 1 and
  beam 3, per group) for the 5 random seeds: mean, sd, min, max.

Intervals treat hops (M1) as independent although hops of one item are correlated, so pooled-hop
intervals are narrower than the item-level ones; the item-level rates are the more honest
uncertainty statement.

## 7. Reading rules

Fixed here so the reading does not depend on the numbers:

1. An arm is said to order better than random on a metric only if its value lies outside the
   min to max range of the 5 random seeds and its Wilson interval excludes the random mean. A
   difference inside that band is reported as no evidence of ordering.
2. A claim about the name overlap is made only from the contrast `rules` against `rules-noname`,
   and is stated separately for the shortcut-flagged and the not-flagged items. Results on the
   shortcut-flagged items are never offered as evidence about structure.
3. A path-recall difference between arms is called real only when item-level Wilson intervals
   (n = items in the group) separate.
4. Headline items are reported on their own; the all-item result is secondary to them where they
   disagree.
5. No weight, stopword, gate, beam, budget or depth is changed after the first full run. A change
   is a new pre-registration and a new run, and the earlier run stays in the record.

## 8. Known limits

* The seed is the gold entry; the harness does not test finding the entry.
* `calls_or_refs` includes references that are not calls (a function passed as a value). The
  gold requires call syntax; the walk does not, so some distractors the gold would drop remain.
* The walk has no stop rule: it cannot know it reached the target, so it spends its budget
  regardless. Path found is a property of the explored tree, not of an answer the walk gives.
* Candidate ties keep source order, so an arm with many ties degrades towards `bfs` order.
* The question text of the named strata contains the endpoint names, so `overlap` can exploit
  them; the descriptive strata name nothing. The groups of M6 expose the difference.
* Symbol documentation (SCIP `documentation`) is not used by any arm.

## 9. Deviations and disclosure

* A smoke run on three items (`flow-0001`, `flow-0044`, `flow-0062`) preceded this document, to
  prove the pipeline. Its numbers are not used. Two cosmetic changes followed it: the stopwords
  `them` and `one` were added after seeing them in a query token list, and the Wilson interval
  endpoints are set exactly to 0 and 1 for 0 and n successes. Nothing else changed.
* The 2,043-edge, 22-repair reconciliation of section 3 was observed in that smoke run (graph
  construction does not depend on the items). It is a check on the loader, not a result.

## 10. Run

```text
cargo run --release -p lci-maps --example walk_eval -- \
    --scip <index-warm4.scip> --gold <flow.json> --root <tree at bfaff44> \
    --out <result.json> --gate 8 --seed 1 --pops 200 --max-depth 6
```

The output is one JSON file: configuration, graph sizes and build report, gold coverage, the
out-degree summaries, one block per arm instance (groups, lengths, clusters), the random-seed
summary and a per-item record with the ranks and outcomes of every arm.
