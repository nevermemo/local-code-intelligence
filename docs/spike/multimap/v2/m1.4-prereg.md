# M1.4 pre-registration: `impact(x)` as a search anchor plus an exact one-hop closure

Slice M1.4 of the multimap spike v2, first step of M1 (decision 9.3 of the spike brief, from the M0
boundary review). It uses only pieces that already exist: the recorded FR evidence of M0b, the frozen
SCIP index that M0.4 loads, and the M0.1 scorers. No model is called. Written before any arm is
run; the commit that adds this file precedes the commit of the code and of any result. Results go to
`docs/spike/multimap/v2/m1.4-results.md`.

Labels: [M] measured, [I] inferred, [G] guess. Nothing in this slice is a gate: the MVP has no
viability gates, so a number here is data about the order of work, not a verdict.

## 1. Question

Fixed before any run: **does an exact reverse closure seeded from an LCI retrieval hit reach parity
with `grep_baseline` on `impact` `decl_f1` overall, and beat it on the `common` band?**

This is a **retrieval-plus-lookup ablation** on a frozen tree: recorded ranked chunks and a question
in, a declaration set out, gold scorers out. It is not an agent result. It says nothing about
whether an agent given such an enriched search result solves tasks better, about tool-call
behaviour, or about latency. The question is the cheapest test of the multimap premise that M0
left open (M0 review, section 3): whether one exact hop attached to a search hit is enough, before
any multi-hop traversal is built.

## 3. Arms

Every arm returns, per item, a **set of declarations** as `{path, line, name, symbol}` (name line of
the enclosing declaration, `Owner::name`, SCIP symbol), in `(path, line)` order. Order carries no
meaning: set metrics only are read (`decl_recall@k` and `decl_ndcg@10` are not read). There is no
size cap; the safety limit is 2,000 declarations per item and a hit is a run defect, not a result.

**Closure** `Cl(s)`, the exact one-hop reverse closure of a SCIP symbol `s`: the set of declarations
whose enclosing range holds a non-definition occurrence of `s` in the frozen index; the declaration
of an occurrence is the innermost definition occurrence whose enclosing range contains it (M0.4's
repair applied). Exact symbol only: no relationship expansion, no implementation or trait
expansion, no text matching. The seed's own declaration is not removed here (the scorer skips it).

**Anchor input** (arms C, N, V, R, B). A separate first step writes `<scratch>/m1.4/anchor-input.json`
from the FR report with exactly these fields per item: item id, the query text, and for each of the
20 evidence chunks `rank`, `relative_file_path`, `start_line`, `end_line`. Nothing else. The report
also holds gold-derived fields (`expected_paths`, `disfavored_paths`, `tags`, `metrics`, hit flags);
the anchor step reads none of them and is given only this file. Ids are matched to the report by
order; alignment is confirmed once, before anchoring, by comparing the report's query text with the
gold question (the check's result is not used afterwards).

**Anchor rule** (arms C and N), deterministic:

1. Names: the code spans (text between single backticks) of the query, each with a trailing `()`
   and any generic arguments removed, split on `::`. A query with no code span has no names.
2. A SCIP symbol (any kind with a definition occurrence in the index) **matches** a name when the
   last `n` descriptor names of the symbol equal the name's `n` segments (`n` = segments given,
   one or two or more).
3. **C (candidate), `k = 5`**: consider the evidence chunks of rank 1 to `k`; a candidate is a
   matching symbol whose definition occurrence lies in the chunk's file and line span. Pick the
   candidate in the best-ranked chunk; ties by most segments matched, then earliest definition
   line, then symbol string order. If none: **no anchor**, empty answer.
4. **N (control, no retrieval)**: candidates are all matching symbols in the index; pick the one
   with the most non-definition occurrences in the index, then the rule 3 tie-breaks. This is the
   anchor a client could take from the question alone; it is there to show what retrieval adds.

**Anchors are frozen** (written, sha256 recorded) before any arm other than O is scored. The anchor
step never reads the gold.

| arm | what it is |
| --- | --- |
| G | `grep_baseline`, stored per-item values. Given the gold's seed name, so it holds more information than C (it need not find the anchor). Its method (word-boundary hits in `.rs` code with comments and strings dropped, plus SCIP-resolved sites that show the name, then the enclosing declaration) already uses the SCIP index [M, from the gold record]. |
| O | **Ceiling, upper bound, not a result.** `Cl(gold seed symbol)`. The gold's R1 was built from the same index with the same rule, so O should reproduce R1 except for the labelled lexical witnesses (config items) [I]. It checks the closure code and bounds the other arms. |
| C | **The candidate.** `Cl(anchor)` with the `k = 5` anchor above. Sensitivity, descriptive only: `k = 1` and `k = 20` (no verdict, no re-selection of the primary). |
| N | `Cl(anchor)` with the question-only anchor. Control. |
| V | **`rg -w` plus verification**, from C's anchor (so any anchor loss is shared with C): `rg -w -n -g '*.rs'` for the anchor's bare name over `<tree>`; drop hits inside comments, string literals and character literals (M0.4's scanner); if the anchor has an owner (method, field, variant, config key), keep a hit only if its file contains the owner name as a whole word; the declaration of a kept hit is the innermost SCIP definition range containing the position (position only, the occurrence's symbol is not consulted); deduplicated. This is the substitute for a client with no resolver. A variant that checks each hit against the SCIP occurrence is not run: it equals `Cl` by construction. |
| R | Random at equal size: per item, `n = |C|` declarations drawn uniformly without replacement from all definitions with an enclosing range in the index; seeds 1 to 5; min to max (mean) printed. |
| B | BFS at equal size: per item, the first `n = |C|` nodes of a breadth-first walk over the M0.4 graph treated as undirected (callers and callees), from the declaration that holds C's anchor definition, ties by source order of the first edge witness. An item whose start is not a graph node (graph nodes are functions and methods) scores as empty; their count is printed. |
| OD, CD | **Deep-test arms, scored only on `tests_deep_recall`.** `tests_deep` is the test functions that reach R1 through 3 or more hops of the reverse call graph, so no one-hop arm can return them [M, from the gold definition]. OD: from the gold seed; CD: from C's anchor. Both return every test function (test attribute directly above the name, the gold's rule) reached by walking the M0.4 `calls_or_refs` graph backwards, from the one-hop closure as hop 1, to a depth of 12. Their `decl_*` metrics are not read. |

## 4. Metrics

From the M0.1 scorers, definitions in `gold-scorers.md`; nothing is added.

* **Primary:** `decl_f1`, with `decl_precision` and `decl_recall`, overall (n 141) and by band
  `unique` (81), `some` (25), `common` (35). `file_recall` and `file_f1` as context only (file-level
  metrics do not depend on the declaration view; a gap between them is reported, not explained away).
* **`tests_deep_recall`**, reported on its own for every arm (n defined 103), never folded into
  `decl_f1`. M0b's baseline for L, F and FR is 0.000. Interpreted for the one-hop arms as a
  statement of the gold's definition, for OD and CD as the traversal measurement.
* **Anchor accounting** (C, N, V): after the run, each item is labelled anchor correct (the anchor
  symbol equals the gold seed symbol), wrong, or none, with Wilson 95% intervals and the split of
  `decl_f1` by label. This reads the gold seed only after the anchors are frozen.
* **Per item and intervals**: as M0b section 4. Per-item values by one-item `--partial` scoring,
  checked against the full-run means; percentile bootstrap over items, 10,000 resamples, seed
  20261014; Wilson for 0/1 values. Paired differences by the same bootstrap over per-item
  differences, with counts of items gained, tied and lost. G's per-item values are the gold's stored
  `grep_baseline` fields. Every table prints `n`; a cell under 10 items is printed and labelled
  "too small to read".

## 5. Reading rules

Fixed here so the reading does not depend on the numbers.

1. Inherited from M0b: rules 1, 3, 4 (bands first, n and interval beside every number), 8 and 9 of
   `m0.3-prereg.md` section 5; no setting changed after the first full run; results [M],
   explanations [I] or [G]; wording "retrieval-plus-lookup ablation", never "the agent finds".
2. **"X beats Y"** (M0b rule 2): the paired interval of X minus Y excludes 0 on the positive side
   (lower bound above 0.000) and the point difference is at least 0.05 [G, a practical size set
   before the data]. An interval above 0 but a difference below 0.05 is "small gain"; an interval
   containing 0 is "no evidence of a difference"; "worse" is the mirror.
3. **Parity** (new), for C minus G on `decl_f1`, with margin `delta = 0.05`, the same floor as rule 2,
   so that "parity" means "neither beats the other by a size this slice would call a difference"
   [G]: the paired 95% interval lies wholly inside `[-0.05, +0.05]`. If the lower bound is above
   `-0.05` but the upper bound is above `+0.05` and rule 2 "beats" is not met, the reading is
   "non-inferior, parity not shown". If the lower bound is below `-0.05` and rule 2 "worse" is not
   met, it is "parity not shown, inconclusive". Rule 2 "worse" is "below grep". A wider margin
   would make parity too easy at n 141; a narrower one would be tighter than the bootstrap can
   resolve [I].
4. **Primary comparisons**, the only ones with a stated conclusion:
   * **P1:** C minus G, `decl_f1`, overall: parity or not by rule 3.
   * **P2:** C minus G, `decl_f1`, band `common`: "beats" by rule 2 or not.
   * Everything else is descriptive and carries no verdict. In particular the `unique` and `some`
     bands are reported with intervals (the brief's "parity elsewhere" [G] is checked by reading
     them, not by a rule); C against N, V, O, R, B is read as below.
5. **Sanity of the candidate:** C must beat R and B on overall `decl_f1` by rule 2. If it does not,
   the run is suspect and the cause is found before any other reading.
6. **What retrieval adds:** C minus N, overall `decl_f1`. "Retrieval improves the anchor" needs rule 2
   in C's favour; N within parity (rule 3 margin) of C or better means the hit adds nothing the
   question did not already give, and the result is reported that way.
7. **Exact versus textual:** C minus V and N minus V by the same rule, descriptive. This is the
   measured value of resolution over `rg -w` plus verification.
8. **Deep tests:** `tests_deep_recall` for OD and CD with Wilson/bootstrap intervals, n 103. OD is the
   ceiling; CD against OD is the anchor loss. One-hop arms are expected to read 0.000 by definition.
9. **A defect is not a result.** An item for which an arm crashes, or exceeds the safety limit, is
   listed and scored as empty for that arm; more than 7 of 141 (5%) such items for an arm makes
   that arm "run invalid" and removes it from rules 3 to 7.

## 6. Validity

**Leakage.** The candidate must not see the gold. The anchor step takes only the stripped input of
section 3 (query text and chunk locations); the query text is what every arm, including G's
question, is given. The seed name is in the query for most items (a code span holding the name in
130 of 141 [M, count over the gold]), so the question names the symbol: this is why N exists, and
why C's value is read against it. The remaining 11 items have no name in a code span; C and N
return an empty answer for them unless a code span happens to match. G, by contrast, is handed the
seed name; this favours G and is stated with the result. The ceiling O and the anchor-correctness
label use the gold seed and are never an input to C, N, V, R or B.

**Same-oracle circularity** [I]. The gold's R1 comes from the same SCIP index as the closure, so
the exact arms are scored against a reference built by their own method. They can therefore not
lose recall to the index, and G's partial use of the index makes it share the advantage. Whether the
index is right about a real client's code is not measured. A tie or win here supports "the lookup
is reachable from a hit", not "the lookup is correct".

**Determinism.** All arms are deterministic (no model, seeded random, fixed tie-breaks, `rg` output
sorted, its version recorded). Every arm is run twice in a row; the two run files must be
byte-identical or the run is invalid.

**Invalid run** (stop, fix the defect, rerun unchanged; the first attempt stays in the record):
a hash of section 2 differs; the anchor input contains a gold-derived field; the two runs of an arm
differ; the ceiling check below fails twice; the per-item mean check of the scorer fails.

**Ceiling check, pre-registered.** O is run and scored first. It must reach `decl_f1` of at least
0.95 overall and `decl_recall` of at least 0.95 outside the `config-key` kind [G]. If not, the
closure code or the declaration rule differs from the gold's builder; one fix pass to the closure
routine only is allowed, disclosed, and O is rerun. Only after O passes are anchors frozen and C, N,
V, R, B, OD, CD run. If O fails after the fix pass the slice stops: no SCIP-closure arm is read.

**Ties and caps.** Ties in the anchor rule are broken as written (section 3). There is no cap on a
closure; a closure larger than the gold's (R1 median 5, maximum 29 [M]) is not truncated.

**Stated limits.** One hop only (R1). Rust only. One tree, one commit, 141 items, one recorded FR
run (retrieval variation not measured). The tree is the project's own code. The index is the
frozen warm index (85 documents), so the closure never sees a file it did not index. Config-key
items (30) are partly textual in the gold; no SCIP closure can return their lexical witnesses.
`k` is a guess and is not tuned; the sensitivity arms are descriptive. The comparison with G is
not between equal-information arms (section 6, leakage).

## 7. Expectations (guesses, fixed before the run)

* O: `decl_f1` at or above 0.95 overall; below that on config-key items.
* N: `decl_f1` overall 0.80 to 0.90, limited by the 11 items without a code-span name and by
  ambiguous names. C: 0.70 to 0.85, a little below N because a hit outside the top 5 loses the
  anchor. Parity overall (P1) is **uncertain, about even** [G]; "beats on `common`" (P2) is more
  likely than not, because G's precision on `common` is 0.39 and the closure's is near 1.
* V: between G and C overall (0.55 to 0.80), below C on `common` precision.
* R, B: `decl_f1` below 0.10.
* `tests_deep_recall`: 0.000 for O, C, N, V (by definition); OD near 1.0; CD within 0.15 of OD.
* Anchor correct for C on 75 to 90% of items.

An expectation that fails is reported as such; none triggers any action.

## 8. What this can change (the reading for M1's order)

Nothing is a gate. The result decides what M1 builds next (M0 review, section 3):

| outcome | reading and effect on M1 |
| --- | --- |
| P1 parity **and** P2 beats | Search plus an exact one-hop closure is enough for `impact`: the enrichment candidate stands. M1.3 (compiler probe against the mutation gold) goes next as planned; M1.2 is trimmed to the kinds with a measured consumer; no multi-hop work for `impact` itself. |
| P1 parity, P2 not beaten | The closure matches grep but does not improve on it where grep is weakest; its value would be cost, not accuracy. M1.2/M1.3 stay as ordered; the closure is judged by A/B call savings, not by `decl_f1`. |
| P1 not shown (below), O passes, **N at parity or above** | The loss is the anchor from the hit, not the closure and not the question: anchoring from the question's code spans (N) replaces anchoring from the hit. One small anchor follow-up (pre-registered) before M1.3; M1.3 order unchanged. |
| P1 not shown, **N also below** | The question, not the retrieval, does not give the symbol often enough. Insert an anchor-resolution slice (a client-side resolver, or the product asking for the symbol) before M1.3 and M1.2; everything downstream of `impact(x)` depends on it. |
| `common` beaten only by C and V together | Resolution is not what wins; the verification of textual hits is. Closure through SCIP is then optional for `impact`, and M1.2's extractors lose their `impact` consumer. |
| Ceiling O fails | The comparison is void (section 6); no reading, repair the closure routine. |
| CD `tests_deep_recall` high (CD at 0.5 or more with interval above the one-hop 0.000) | Multi-hop reach adds something one hop cannot, for the indirect-test stratum: the traversal premise is supported there and only there. Low: indirect tests stay a grep-level problem and traversal for them is not a reason to build M1.1 early. |

Whatever the outcome, the numbers become the `impact(x)` column that M1.3 and M1.2 results are read
against. No outcome supports a claim about agent performance.

## 9. Cost and files

Local CPU only. No model service, no GPU, no network, no listener; the M0b services need not be
running. Rough time [G]: loading the index a few seconds; closures milliseconds; `rg` per item about
a second; the whole run (every arm twice, plus the sensitivity anchors) under 30 minutes, scoring and
bootstraps a few more. Implementation: one `lci-maps` example (`impact_eval`, next to `walk_eval`),
about one implementer slice, with unit tests on a synthetic index; it is committed after this
file and before the first run.

Scratch (not committed): `<scratch>/m1.4/` holding `anchor-input.json`, the frozen anchor files for
C (k 1, 5, 20) and N, the run file, score, per-item and stats of every arm, the paired-difference
files, the two repeat run files, and the logs. Committed: this file, the example, and
`m1.4-results.md` with placeholders for paths and the hashes of section 2.

## 10. Run

```text
<anchor step>   --report <scratch>/m0b/out5/impact-FR-report.json --out <scratch>/m1.4/anchor-input.json
cargo run --release -p lci-maps --example impact_eval -- --scip <frozen index> --root <tree> \
    --gold <gold>/impact.json --anchors <scratch>/m1.4/anchor-input.json \
    --arm <O|C|N|V|R|B|OD|CD> [--k 5] [--seed 1] --out <scratch>/m1.4/<arm>-run.json
cargo xtask gold score --set impact --gold <gold>/impact.json --run <run>.json --out <score>.json
```

Order: ceiling check (O, twice), anchor freeze, C, N, V, R, B, OD, CD, each twice, then the
sensitivity anchors, then scoring and pairing. One configuration, no tuning between steps.

## 12. Coordinator review before implementation (2026-10-14, written before any code or run)

Choices 1 to 8 of the report on the commit that added sections 1 to 11 are accepted as written. The
following is appended; nothing above is edited.

* **(a) Anchor accuracy is a primary descriptive.** For C and N (and for C at `k = 1` and `k = 20`,
  descriptive), the results report the share of items whose chosen anchor equals the gold seed
  symbol, overall and per band (`unique`, `some`, `common`), with Wilson 95% intervals, and the
  counts of "wrong anchor" and "no anchor". This extends section 4's anchor accounting and is
  printed in the first results table, before `decl_f1`.
* **(b) Reading rule for the circularity caveat.** Because the gold R1 is built from the same SCIP
  index as the closure, C's `decl_f1` is approximately anchor accuracy times the closure ceiling
  (O) [I]. The verdict lines for P1 and P2 therefore carry the caveat inside the line itself, and
  are read as "can retrieval pick the right anchor", not as independent reference correctness,
  until the independent audit of the `impact` gold (M0.2) exists. The verdict line also states that
  G is given the seed name and C is not.
* **(c) Product mapping.** The closure step stands in for LCI's existing `find_references` (LSP)
  path. This slice does not measure an LSP closure. If C reaches parity (P1), the results document
  names the LSP closure measurement as the next one.
