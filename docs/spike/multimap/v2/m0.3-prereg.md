# M0.3 pre-registration: today's LCI with only the lexical channel, on the `impact`, `where-to` and `flow` gold sets

Slice M0.3 of the multimap spike v2. Written before the first run on the gold items; the commit
that adds this file precedes the commit of any result. Scorers: `cargo xtask gold` (slice M0.1,
`docs/spike/multimap/v2/gold-scorers.md`). Results go to `docs/spike/multimap/v2/m0.3-results.md`.

Labels: [M] measured, [I] inferred, [G] guess. Nothing in this slice is a gate: the MVP has no
viability gates, so a bad number here is data about the order of work, not a verdict.

## 1. Question

Before any new retrieval machinery is built, how much of the three structural questions does the
current LCI answer with its lexical channel alone, and how far is that from the trivial
baselines the gold sets ship with?

1. `impact`: given a seed symbol, does the lexical channel return the declarations that must
   change (R1 gold), compared with the `grep_baseline` stored in the gold?
2. `where-to`: given a "where do I register / what are the exemplars" question, does it return
   the expected file and span, compared with a file-level BM25?
3. `flow`: given two endpoints (or a description), does it return the functions on the call
   path?

This measures a retrieval ablation of today's code on a frozen tree. It does not measure the
fused or reranked product (that half is M0b, run when the model services return), agent
behaviour or latency. "LCI-lexical" below always means this ablation, never "LCI".

## 3. Arms

**LCI-lexical.** `lci evaluate` over the frozen tree with this configuration (the only keys set;
`<scratch>` is a directory outside the repository and outside the user's data directory):

```toml
data_dir = "<scratch>/data"
embedding_url = "http://127.0.0.1:<stub port>/v1"   # a local stub, see below

[channels]
semantic = false
lexical  = true      # ripgrep search with IDF-weighted, BM25-style chunk scoring
lsp      = false
reranker = false

[index]
freshness = "manual" # the tree is frozen; no staleness check per search
```

* One query per gold item: the item's `question` text, verbatim. (For `impact` the
  `question_behaviour` variant is not run.)
* Result window (`top_k`): 20 for `impact` (its metrics reach recall@20), 10 for `where-to` and
  `flow`. The window is the evaluate definition's `top_k`; the fusion cap `max_chunks_per_file`
  keeps its default of 2, and every other setting is the built-in default.
* Indexing needs an embedding service even when the semantic channel is off (the index commit
  embeds the chunks). The model services are not used: a **stub** HTTP server on a loopback port
  outside 8765 to 8771 answers `POST /v1/embeddings` with deterministic short pseudo-vectors.
  The vectors are never read, because the semantic channel is off and the LSP and reranker
  channels are off. The stub is a mock and is reported as one; it affects nothing that the
  lexical channel computes (chunk boundaries and the ripgrep pass do not depend on vectors).
* The ranked chunk list of each query comes from the evaluate report (`rank`,
  `relative_file_path`, `start_line`, `end_line`). It is turned into a run file by converter
  **C1**, fixed here:
  * `impact`, `where-to`: one answer per result, in rank order, `{path, line = start_line}`.
  * `flow`: the answer names functions. For each result in rank order, the lines
    `start_line` to `end_line` of the file in `<tree>` are read; every `fn <ident>` item
    declared inside that span (a line whose first tokens are optional `pub(...)`, then
    `const`/`async`/`unsafe`/`extern "..."` qualifiers, then `fn`, then an identifier) yields
    the bare identifier as an answer, in source order. A result with no `fn` yields nothing.
    Answers are bare names, so a gold node whose bare name is ambiguous inside its item can
    only be matched by `file:line`, which C1 does not produce; that loss is accepted.
  * An item whose query returns nothing is scored as an empty answer (0), as the scorer does for
    a missing item. No item is dropped.

**grep_baseline.** The `grep_baseline` field stored in each `impact` item, averaged by the
scorer (`cargo xtask gold baseline --set impact`): the word-boundary hit of the bare name in
`.rs` code plus SCIP-resolved sites that show the name, and the enclosing declaration of each.
It is a metrics report, not a run (the gold stores no returned declarations), so it can be set
beside LCI-lexical per item and per stratum but cannot be re-scored. `flow` and `where-to` ship
no grep baseline; there is none for them in this slice.

**BM25.** `cargo xtask gold baseline` provides no BM25 for these sets (its BM25-like baselines
are for `instructions`). The reference used is the gold's own file-level BM25 difficulty check
for `where-to` (`<gold>/scripts/where-to/baseline_bm25.py`: tracked `.rs`, `.md`, `.toml`,
`.yml` files of `<tree>`, camel/snake-split identifier tokens, path tokens counted three times,
k1 1.2, b 0.75, top 10 files). It is run unchanged in algorithm on the `where-to` questions and,
with the same code over the `impact` questions, on `impact`. Its answers are file paths, so
only file-level metrics are read from it: `reg_hit@3` and `reg_mrr` (and the set metrics, where
a path-only answer matches only a file with a single implementation) on `where-to`, and
`file_precision/recall/f1` on `impact`. It cannot name functions, so it has no `flow` score and
no `impact` declaration metric.

## 4. Metrics

All from the M0.1 scorers, with the definitions in `gold-scorers.md`; no metric is added.

* **impact** (141 primary items; strata `kind`, `band` = name ambiguity, `coverage`): primary
  `decl_f1`; also `decl_precision`, `decl_recall`, `decl_recall@5/10/20`, `decl_ndcg@10`,
  `file_f1`, `file_precision`, `file_recall`. Secondary recalls (`r2_decl_recall`,
  `tests_recall`, ...) are reported only if the scorer defines them for the cell.
* **where-to** (60 items; strata `form`, `leak`): registration `reg_hit@3` (primary), `reg_mrr`,
  `reg_decl_hit@3`; exemplar and convention `set_recall`, `set_precision`, `set_f1`.
* **flow** (111 items; strata `stratum`, `headline`): primary `path_recall` on the headline
  items. `spurious` and the number of answers per item are reported as context. `tau` and
  `exact_order` are not read: retrieval returns relevance order, not call order.
* **Per item.** The scorer reports means only. Per-item values are obtained by scoring each
  item alone with `--partial` (a one-item run) and are checked: the mean of the per-item values
  must equal the full run's mean for every metric the scorer defines on all items of the cell
  (metrics averaged over a subset, `n_defined`, are checked on that subset).
* **Intervals** (95%). Proportions of items that are 0 or 1 per item (`reg_hit@3`; the share of
  flow items with `path_recall` = 1) use the Wilson interval. Every other mean uses a percentile
  bootstrap over items: 10,000 resamples, seed 20261014. For flow headline items the resampling
  unit is the `prefix_cluster` (the gold README: effective n is the cluster count), and the
  number of clusters is printed beside each such interval.
* **Paired difference.** LCI-lexical against `grep_baseline` on `impact` (`decl_f1`,
  `decl_recall`, `file_f1`; the gold stores per-item baseline values) and against BM25 on
  `where-to` and `impact` (file-level metrics): percentile bootstrap of the per-item differences,
  10,000 resamples, seed 20261014.
* Every table prints `n` (items in the cell).

## 5. Reading rules

Fixed here so the reading does not depend on the numbers:

1. One number is never read alone: each is read with its interval and its `n`. A cell with
   fewer than 10 items is printed but labelled "too small to read".
2. LCI-lexical is called better or worse than a baseline on a metric only if the paired
   interval of section 4 excludes 0. Otherwise the result is "no evidence of a difference". An
   overlap of the two arms' separate intervals is not used.
3. `impact` is read by name-ambiguity band (`unique`, `some`, `common`); the all-item mean is
   secondary because the bands are unbalanced. Every `impact` score is set beside the
   `grep_baseline` of the same cell (gold README: `rg -w` plus the enclosing declaration gives
   F1 0.995, 0.79 and 0.42 on the three bands).
4. `flow` is read on the headline items first; the all-item mean is secondary where they
   disagree. A score on a `name-matching-shortcut` item is evidence about name overlap, not
   about finding a path; the split shortcut-flagged / not flagged is reported for the headline
   items. Structure is claimed only from the not-flagged items.
5. `where-to` is read as provisional (section 2) and by `form`; `leak` strata are reported
   separately and stem-leak items are never offered as evidence of retrieval ability.
6. The converter C1 is a lossy view of a chunk ranking (section 7). A low `impact` or `flow`
   score may reflect C1 rather than the ranking; file-level metrics (`file_*`, `reg_hit@3`) do
   not depend on C1's line or name choice and are the more direct reading. A difference between
   file-level and declaration-level scores is reported, not explained away.
7. The word "baseline" in the results means the reference arms of section 3, not a threshold.
8. No setting (query text, `top_k`, config key, C1 rule, metric, interval method) is changed
   after the first full run. A change is a new pre-registration and a new run; the first run
   stays in the record. A run may be repeated unchanged only if it was invalid (crash, wrong
   tree, wrong gold hash), never on the basis of a score.
9. Results are labelled [M]; anything said about why, or about what would help, is [I] or [G].

## 6. Expectations (guesses, fixed before the run)

[G] LCI-lexical returns whole chunks for a handful of query terms, so:

* `impact`: below `grep_baseline` on `decl_f1` in every band, most clearly on the `unique` band
  (baseline near 0.995); file-level recall decent (it finds the defining and referencing files
  of a distinctive name) and file precision low at 20 results.
* `where-to`: `reg_hit@3` within a few items of the file-level BM25 (0.68 on the provisional
  gold, from the gold's own log); set metrics for exemplar and convention near zero.
* `flow`: `path_recall` higher on `named` than on `descriptive` items, and on shortcut-flagged
  than on not-flagged items; headline `path_recall` below 0.5.

An expectation that fails is reported as such; none triggers any action.

## 7. Known limits

* Results are chunks; the gold wants declarations and function names. C1 maps a chunk to its
  start line (impact, where-to) or to the `fn` items inside its span (flow). A chunk that holds
  several gold declarations earns credit for at most the one that holds its start line; a
  chunk that begins with attributes or documentation above a function may start before the
  declaration's span. This under-credits `impact` declaration metrics. In `flow` a chunk that
  spans several functions can name more functions than the ranking "chose"; `spurious` shows
  that inflation.
* The query is the question text, not a hand-written query; the lexical channel selects its own
  terms. No query rewriting is done (not part of today's LCI).
* One tree, one commit; the gold's name leakage and lexical shortcuts apply to every arm.
* The stub embedder means index build time is not representative; no latency is reported.
* The `where-to` and `impact` golds still owe audits (section 2).

## 8. Deviations and disclosure

* The brief names `cargo xtask gold baseline` for the `grep_baseline` and BM25 arms. That command
  ships `grep_baseline` for `impact` only (as stored metrics), and no BM25 for these sets; the
  BM25 arm is the gold's own `where-to` BM25 algorithm, applied to `impact` as well (section 3).
  No grep or BM25 arm exists for `flow`; none exists for `where-to` other than BM25.
* Before this document: a release build of this branch was started (it produces no numbers) and the gold files were opened to read their field layout and hashes. No query has
  been run against the frozen tree or the gold items, and no result exists. A mechanics smoke
  test on a toy directory (not the frozen tree, not gold queries) may precede the run to prove
  the stub embedder and the evaluate-to-run pipeline; its output is not used and the results
  document says whether it happened.
* Any later deviation is listed in the results document with the reason.

## 9. Run

```text
cargo xtask gold to-evaluate --set <set> --gold <gold>/<set>.json --out <def>.toml --top-k <k>
lci --config <scratch>/lci-m03.toml --no-local-config evaluate <def>.toml \
    --workspace self=<tree> --output <report>.json
<convert report -> run file, C1>
cargo xtask gold score --set <set> --gold <gold>/<set>.json --run <run>.json --out <score>.json
cargo xtask gold baseline --set impact --gold <gold>/impact.json --out <grep>.json
```

If `to-evaluate` drops an in-scope item, the query is added to the definition by hand with a
placeholder expected path (the scorer, not the evaluator, judges the answers). Scripts, the
stub, configuration and raw outputs stay in the scratch directory; only the two documents of
this slice are committed.
