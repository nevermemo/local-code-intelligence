# M1.4 results: `impact(x)` as a search anchor plus an exact one-hop closure

Pre-registration: `m1.4-prereg.md` (sections 1 to 11, plus the coordinator note in section 12), committed
before the code (`impact_eval` in `lci-maps`, commit `a579d8d`) and before any arm. One full run,
2026-10-14, with the pre-registered settings (k = 5, parity margin 0.05, floor 0.05, bootstrap 10,000
resamples, seed 20261014). Nothing was changed after the first arm was scored (rule 8 of M0.3).
Every arm was run twice: all 13 repeat pairs are byte-identical [M]. No defects, no item above the
safety limit. Labels [M] measured, [I] inferred, [G] guess. This is a retrieval-plus-lookup
ablation on a frozen tree, not an agent result.

## 6. Reading for M1's order (prereg section 8)

* **P1 and P2 are not met by the hit-seeded candidate.** Search plus an exact closure from the top-5 hits is below
  grep overall and ties it on `common`. The cause is the anchor (30% of items without a correct anchor, 27.7% with
  none), not the closure and not the question.
* **Anchoring from the question's code spans (N) reaches and exceeds grep**, overall and on `common`, with identical
  results on `unique`. This is the row of section 8 that reads "one small anchor follow-up before M1.3, M1.3 order
  unchanged", and the follow-up is to ask what retrieval is for in `impact`: in this set it adds nothing the
  question does not already give, because the question names the symbol [I]. Whether that holds for questions
  that do not name the symbol is not tested (the gold's questions hold the full seed name in 130 of 141 items; N still
  anchors correctly on 137 of 141). N is about O times anchor accuracy (0.991 x 0.972 = 0.963 against 0.967
  measured); its margin over G is the gold-builder reproduction (O minus G) scaled, not evidence that SCIP references
  are more correct than grep's.
* **Resolution beats text:** the closure beats `rg -w` plus verification on the same anchors by +0.112 overall and
  +0.141 on `common`, and N beats V by +0.379. So the SCIP resolver, not retrieval, is the source of the `common` gain [M, on this gold; I for
  the cause], partly by construction: the gold's R1 is defined by SCIP exactness, which is exactly where G's `common`
  precision (0.320) loses.
* **Indirect tests:** reaching `tests_deep` needs the traversal; CD 0.650 and OD 0.947 against 0.000. Traversal
  for indirect tests is supported here, and only here.
* **Product mapping (prereg 12c):** the closure stands in for LCI's existing `find_references` (LSP) path. This
  slice does not measure LSP closure. Because C did not reach parity the pre-registered trigger for naming the next
  measurement does not fire; the one suggested for the order of work is the LSP `find_references` closure seeded from
  the question's symbol (the N path) on this gold, since N is the arm that beats grep [G].
* Not changed by this result: M1.3 next, M1.2 trimmed to kinds with a measured consumer, M1.1 deferred.

## 7. Deviations and disclosure

* **Build check before the first arm, against the gold's recorded build counts.** The SCIP unit rule (functions,
  methods, structs, enums, traits, type aliases, constants and statics; not variants, fields or associated types) gave
  8,835 decl-to-decl edges and 13,405 attributed sites in the gold's record and 8,838 and 13,408 in `impact_eval kinds`
  (no item was scored). The first version of the unit rule left out trait methods (3,704 edges counted over unit targets
  only, 8,838 after both changes); `TraitMethod` was added to the units before any arm was run. The ceiling check passed
  without a fix pass. The remaining difference (3 edges, 3 sites: 0.03%) is unexplained; it is too small to
  have been chased and the ceiling check covers the effect on the items.
* **Deviations from the prereg text that do not change a verdict** (found in the review of this slice):
  (1) `code_names` also drops leading `crate`, `self` and `super` segments (`impact.rs`, `code_names`); this only adds
  matches. (2) `is_test` accepts `#[test]` or `#[tokio::test` anywhere from the name line up to 12 lines above it
  (or from the start of the enclosing range, whichever is higher up), which is broader than the gold's "directly
  above"; OD and CD precision may be inflated, recall is unaffected. (3) R draws from the kind-filtered units
  (functions, types, consts and so on), not from all definitions with an enclosing range. (4) B orders each node's neighbours as
  out-edges in stored order and then in-edges by witness position, not by one global source order of first edge
  witnesses; B is a sanity arm only.
* **Name extraction.** The rule keeps the code spans that read as paths (trailing `()` and generics removed); a span
  with arguments or spaces is rejected, not partly parsed. 11 spans over the set were rejected; no item lost all names.
* **Order.** The sensitivity anchors (k 1, 20) and the anchor-accuracy labels were produced right after the freeze and before
  C, N, V, R, B, OD, CD were run (prereg section 10 put the sensitivity anchors after). They are deterministic functions
  of the frozen input and the index; the labels read the gold seed, which means I saw the anchor accuracy (0.695 for C,
  0.972 for N) before the arms were run. No setting changed afterwards.
* **Alignment check.** `make-input` compared the report's query text with the gold question for all 141 items (all
  equal) and used the gold only for ids.
* **Equal-size arms.** R and B take their size from C's answer, which is empty for 39 items, so they are empty
  there as well. B is also empty where the anchor's unit is not a function or method of the M0.4 graph (71 items
  in all).
* **Process lapses.** An empty `python -` heredoc was started once by mistake at the beginning of the reading (it
  only opened an interpreter that exited on end of input), and one `sleep 1` was used once in a shell command; both
  against the run rules. Busy-wait loops without `sleep` were used in two monitors. Nothing depended on them.
* The FR report, the gold and the index hashes were those of the prereg (checked at run start); the model services
  and the A/B were not touched; no network or listener was used; `rg` 15.2.0.
* Raw outputs stay in the scratch directory: `<scratch>/m1.4/` (anchor input, four anchor files, run, repeat, score,
  per-item and paired files). Run-file sha256 prefixes: C `e35ceeed`, N `d6ca2851`, V `796463ed`, B `af66e4ec`,
  R seed 1 `d7e5f247`, OD `7e77657f`, CD `cbebc09f`, O `84492e0e`; anchor input `b8731cef`; anchors C5 `8af15a2e`,
  N `80d7e753`, C1 `b48c6adc`, C20 `c4e63961`.
