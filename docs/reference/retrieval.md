# Retrieval behavior and evaluation

This file is the home of the shipped retrieval pipeline's behavior and of how retrieval is evaluated.

## Retrieval behavior

The shipped search pipeline, in order; the code-level picture (types, constants, functions) is [docs/architecture.md](../architecture.md) "Chunks and the manifest", "Indexes and channels" and "Indexing flow and freshness"; the LSP channel: [lsp-channel.md](../lsp-channel.md). Traverse mode: [engine.md](../spike/multimap/engine.md).

1. Scan the eighteen extensions of [Supported languages](../../README.md#supported-languages) (any ASCII case: a `.RS` file is Rust, N94) recursively with `.gitignore`, nested ignores and standard `ignore` crate rules. The checked-in `.lciignore` is an additional ignore file that keeps agent control-plane material (`.agents`, `.github/agents`, `.github/instructions`, `.github/skills`, `.codex`, `.claude`, `.kilo`) and generated `test-results` out of this repository's searchable corpus while leaving them on disk for agents. Symlinks are not followed, `.git` is skipped, hidden source files are eligible when not ignored. A file that is not valid UTF-8 (for example Windows-1252 C source) is indexed from a lossy decoding (invalid bytes become U+FFFD, line structure kept) and reported in `lossy_decoded_files`; it never fails indexing or search. A Qt Linguist `.ts` catalog is left out and counted in `skipped_non_source_files`; it does not affect the staleness fingerprint, and a file that changes into one drops its chunks at the next refresh like a deleted file. A source file removed between the walk and its read, or whose path is not valid UTF-8, is skipped with a logged warning. Other read/traversal errors abort the update and preserve the previous index; under `on-search` freshness the search then reuses the previous snapshot with a warning.
2. Select a static language adapter and Tree-sitter grammar by extension. Chunks preserve: Rust, its original declaration boundaries; TypeScript/JavaScript, imports, executable top-level statements, exports, comments/decorators, functions, classes and methods, interfaces and signatures, type aliases, enums, variable-assigned arrow functions; Python, imports, assignments, executable top-level statements, sync and async functions, classes, methods, decorators and leading comments; C#, using directives, namespaces, top-level statements, types, members, attributes, XML documentation comments, local functions; Go, top-level functions, methods, type/const/var declarations and leading comments; Java, packages, imports, classes, interfaces, enums, records, methods, constructors, fields, annotations, Javadoc; C, functions, structs, unions, enums, typedefs, preprocessor macros, global declarations, leading comments; C++, namespaces, classes, structs, unions, templates, methods, fields, leading comments. Oversized syntax splits only at named syntax boundaries toward 6,000-byte groups, with declarations preserved up to 24,000 bytes; large indivisible leaves stay whole rather than truncated; parser error recovery remains searchable. Markdown (`.md`) is cut into heading sections: a heading line plus its own body up to the next heading of any level (ATX and setext headings), with fenced code blocks kept whole and never searched for headings, YAML front matter kept with the first section, and text before the first heading as its own chunk; a section over 6,000 bytes is packed by paragraph toward that size, and a fence stays whole.
3. Parsed chunks, language identifier and adapter version are persisted per file in the external manifest (fingerprints include path, content, language and adapter version), so a later manual or watched pass reparses only changed, new or adapter-version-changed files, also after restart. A missing, incompatible or malformed manifest safely causes a full parse.
4. Each exact source chunk is hashed; vectors from the current workspace snapshot are reused when content hashes and the stored embedding URL/model/document-format identity match, and duplicate new chunks are embedded once. Cached vectors whose width differs from what the embedding service now returns are embedded again: the width comes from the process's latest embedding response, or, in a process that has embedded nothing yet, from one single-attempt probe of a short prefix of the first chunk, sent only when cached vectors exist (a failed probe warns and keeps them). A width change no request has revealed since the process's last one is found by the next search, which serves no semantic hits and warns; the index run after it repairs the index. Parser adapter versions are decoupled from embedding compatibility, so unchanged chunk text keeps its vector. Documents are embedded as source, without a query instruction.
5. A complete workspace snapshot is built in memory and committed as a LanceDB table overwrite after embedding succeeds; the matching manifest is saved only after that commit. Removed chunks disappear from the snapshot; line-only changes update locations without re-embedding. This is a small/medium-repository design, not a streaming indexer for huge monorepos.
6. Queries are embedded with `embedding_query_template` (default `Instruct: Given a code search query, retrieve relevant code passages that answer the query` newline `Query: <query>`).
7. Candidates come from three channels. Semantic: LanceDB cosine distance, the `semantic_candidate_count` nearest chunks that pass the request's filters (the fetch is widened when filters reject rows, up to 10,240 rows; a search stopping at that cap warns that farther matching chunks were not considered). Lexical: ripgrep over all supported extensions in one pass, scored in process:
   - Terms are the query's tokens as written plus the sub-tokens of their camelCase, snake_case and letter/digit parts (`parseConfig` also searches `parse` and `config`), without generic English and commit-message words such as `add`, `fix`, `when`, at most 24 per query. A query with no usable term returns no lexical candidates, without a warning.
   - Matching lines are credited with the terms each really holds: a term of five or more characters counts as a case-insensitive substring, a shorter one only as a whole word (`add_item` and `addItem` hold `add`; `padding` does not). Lexical lines map to chunks of any indexed language.
   - Chunks score by IDF-weighted term evidence: a term's document frequency is the number of indexed files with a credited line; terms credited in more than a quarter of the indexed files are dropped (kept when every term is that common); the twelve rarest remain; a chunk scores the BM25 sum over them of `idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * length / average_length))` with `idf = ln((N - df + 0.5) / (df + 0.5) + 1)`, `tf` the chunk's credited lines of the term, `length` its line count, `average_length` the mean over the filtered index's chunks, `k1 = 1.2`, `b = 0.75`. Chunks matching only dropped terms are not candidates. The constants live in `lci-core/src/lexical.rs` and are not configurable.
   - LSP: for each language present in the filtered index, its enabled language server also searches workspace symbols; locations map only to same-language chunks.
8. Candidates are deduplicated and fused with Reciprocal Rank Fusion: each channel adds `weight / (rrf_k + rank)` for a chunk it returned, a chunk found by several channels sums the terms, and the source-role prior is added afterwards, unscaled. The `[fusion]` weights default to `1.0` (plain RRF); each must be finite and greater than zero (disabling a channel is `[channels]`' job). Weights change only `fusion_score` and through it the fusion order and shortlist, never ranks, scores or the reranker's per-document input. After the order is settled and before the shortlist is cut to `rerank_candidate_count`, `[fusion].max_chunks_per_file` (default `2`; `0` is unlimited and changes nothing) walks the fused order, keeps a chunk in the head while its file (by relative path) has fewer than that many kept, and moves the rest to a tail; the result is head then tail, each in original relative order. Nothing is removed, so `top_k` is still filled from demoted chunks when there are too few distinct files; `fusion_score` is not rescaled, so a demoted chunk can follow one with a lower score. The reranker sees the capped shortlist, reranker-off and reranker-failure results use the same capped order, and the reranker's output is not capped again. The cap and the weights were measured on the mined set and `core.toml` (numbers: [decisions](../decisions.md)). Results expose channel ranks, lexical match count and score, fusion score and channels; the lexical score never feeds the semantic or reranker scores. The full contract: `.agents/skills/lci-retrieval-evaluation/references/retrieval-contract.md`.
9. The fused shortlist is reranked, each candidate sent as its path plus at most `rerank_document_max_bytes` of its code (cut at a UTF-8 boundary, keeping the head); results always carry the full chunk. The three channels fail independently and available channels continue; an LSP provider that fails is skipped for the rest of that search. Each provider gets at most `lsp_search_budget_ms` of wall clock per search, alongside the other channels: a server still starting (rust-analyzer waits up to about ten seconds for its first indexing pass) or slow is skipped for that search, which reports an informational `notes` entry rather than a warning because nothing failed. The skipped server is not discarded: its start (spawned at most once per provider and workspace) keeps running in the background, followed by one priming `workspace/symbol` request that builds its symbol index (8-30 s on a large Rust workspace; searches during it also report the note, and no search budget cancels the priming), and a later search uses the server. A partial answer gathered before the budget ran out is kept; `lsp_search_ms` in the timings is the capped wait. Channels and the reranker can be switched off on purpose with `[channels]` (silent, unlike a failure). If reranking fails, the fusion order is returned with a warning appended to any earlier warnings.
10. Documentation lane. Markdown chunks (the prose extractor's, not every chunk with the `documentation` source role) are split off after the request's filters and never enter the code pipeline above, unless the request names `source_roles` (then the filters apply as stated and one list comes back). The code `results` list is therefore exactly what an index without the Markdown files returns: semantic search, lexical statistics (BM25 average length and document frequencies) and LSP mapping all see code chunks only. The documentation lane runs beside it with the same query vector: semantic over prose chunks only (`docs_lane.semantic_candidate_count`), lexical over prose chunks only, no LSP, the same fusion and per-file cap, a cut to `docs_lane.rerank_candidate_count`, a second rerank only when `docs_lane.reranker` (or the profile's `docs_reranker`) is on (default off, whatever `[channels].reranker` says), and the best `docs_lane.top_k` (default 2) come back in `docs.results` with `candidate_count`, `reranked`, its own timings and `warning`. `docs` is present exactly when the lane ran and the index holds prose chunks. The lane is fail-open: a semantic, lexical or reranker failure sets `docs.warning` and never changes the code list or its warning. The compact MCP view lists the docs after the results and shares its response ceiling.

- ripgrep resolution: with the default `rg` or `rg.exe`, `PATH` is checked first; on Windows without `rg` on `PATH` it also checks common per-user and system-wide VS Code, VS Code Insiders and VSCodium installations (including versioned application directories). Any other configured value is an explicit command or path, used unchanged. If ripgrep cannot start, lexical retrieval fails open and the warning explains how to set `ripgrep_path`.
- Model clients: embedding response indices are validated and reordered; vectors must have consistent dimensions, finite values and nonzero norm. Model HTTP errors include the status and a bounded response body. Index-time document embedding retries connection errors, timeouts and a connection the server closed or reset mid-request (typically a pooled keep-alive connection closed while idle), up to three attempts with backoff (a cold model may still be loading). The query embedding, the indexing width probe (step 4) and the reranker make a single attempt, so a hung service costs a search one timeout and a refused connection costs no backoff; after a refused connection the reranker is also skipped for 30 s, and the warning says so. When the embedding service rejects a batch's input itself (HTTP 400/413/422, typically one chunk longer than the model's context), indexing retries that batch one chunk at a time and embeds a rejected chunk from a progressively halved prefix (down to 512 bytes); the full chunk is still stored, returned and lexically searchable and is listed in `truncated_for_embedding`. Its vector is cached by content hash, so raising the server's context limit later needs a reindex into a new data directory to re-embed it in full. Changing an embedding URL/model requires reindexing; replacing a model behind an unchanged name/URL is not detectable unless its vector width differs (step 4), so use a distinct model name or a new data directory.
- Timing fields (milliseconds) cover query embedding, LanceDB search, lexical search, LSP search, fusion, reranking and total retrieval; total also includes validation and index access/wait time. The same timings appear in tracing logs on stderr; CLI JSON stays on stdout. The default log filter is `local_code_intelligence=info,lci_core=info`; `RUST_LOG` replaces it (for example `RUST_LOG=local_code_intelligence=debug,lci_core=debug`). A `RUST_LOG` made only of crate-scoped directives that do not name `lci_core` silences that crate; a bare level such as `RUST_LOG=debug` applies to every crate.

## Retrieval evaluation

- `evaluate` runs a portable definition through the same application search path: `"$lci" evaluate ./evaluations/core.toml --workspace "self=$PWD" --workspace "gust=/path/to/gpu-dialect-v0" --output ./test-results/evaluation.json`. Workspace mappings are supplied at runtime, so checked-in definitions hold no machine paths. The GUST workspace is optional; its queries are skipped without a mapping. Without `--output`, JSON goes to stdout. A required missing workspace, search error, expected-path miss, wrong expected role or missing required snippet fails the query and gives a nonzero exit after the report is emitted; valid optional skips do not fail the run. `evaluate --baseline <report.json>` also embeds a `comparison` and prints its summary to stderr (`--seed`, `--resamples`, `--keep-failed`). With `[channels] lsp` on, `evaluate` first starts and primes every enabled language server for each workspace it queries (rust-analyzer is always enabled, so a missing binary is recorded as a failed warm-up), so no query pays a cold start; the outcome is the report's `priming` block (per workspace key and provider: `primed`, `ms`, `error`). `--no-prime` keeps the cold first query for a cold-start measurement. Priming changes which query pays the start, never a ranking.
- Arms: run `evaluate` once per configuration with `--config` and name the outputs by arm: the default, `[channels] reranker = false` (fusion order alone), or the grep-only baseline (see [Channels](../../README.md#channels) in the README). Reports do not record the switches, and the switches never invalidate an index, so arms can run one after another on one `data_dir`; never two at once on the same one.
- `compare` measures the difference between two saved reports without services, configuration or index: `"$lci" compare test-results/fusion.json test-results/semantic-only.json --output test-results/fusion-vs-semantic-only.json`. It pairs queries by workspace and query text (both reports must come from the same definition) and prints, for MRR, nDCG@10 and hit@1, the baseline and candidate means, the mean per-query delta (`candidate - baseline`) with a seeded 95% paired-bootstrap interval (`--resamples`, default 10,000; `--seed`), whether the interval excludes zero, and reciprocal-rank wins, losses and ties. Queries in only one report, or skipped in either, are excluded and counted; so is a query in which either side's language server missed `lsp_search_budget_ms` (`metrics.lsp_budget_hit`: it measured a cold start, not retrieval), counted as `budget_hit_*` on the pairs line and, for tagged definitions, per tag (`budget_hit_by_tag`), unless `--keep-failed` keeps it; a definition with `tags` also gets one block per tag. A regression is not an error: the exit code is nonzero only when a report cannot be read or parsed, or `--output` cannot be written (the summary is printed first). A delta whose interval contains zero is noise at that query count.
- Reports hold bounded path, line-range, role, rank, score and preview evidence; per-query hit@1, hit@3, hit@8, reciprocal rank, nDCG@10, recall@3/@8, file-level accuracy@5/@10, preference/disfavor counts, role distribution, reranker state, `lsp_budget_hit` (with `lsp_providers_over_budget` when set; a search response names them as `lsp_over_budget` only when a provider missed the budget), timings, lifecycle and effective filters; and aggregates: hit rates, MRR, means of the rank-aware metrics, `lsp_budget_hit_queries` (and per tag under `by_tag`), median/p95/max latency with sample count `n` (total and per stage; nearest-rank p95 hides the worst query at small `n`, for example it is the second-highest of 35, so read `max`), fallback count, and created/reused/waited/refreshed index counts. nDCG@10 uses graded gain (`expected_paths` match 2, `preferred_paths` only 1) and credits each gold pattern once; recall@k is the fraction of distinct expected patterns in the first k; file accuracy@k counts distinct files. The `@10` metrics are bounded by the query's `top_k`: hand-written `core.toml` uses 8 (effectively @8), the git-mined set 10; use `top_k >= 10` to compare with literature @10 numbers. Reports belong under `test-results` and are not committed. Evaluation reuses compatible persisted indexes and calls only the configured embedding and reranking services.
- Offline scoring: `evaluate --dump-candidates` records every query's whole fused candidate pool, the dumped configuration and the reranker's scores; `LCI_CANDIDATE_DUMP=<file>` appends the same pool per search of a running process to a JSON Lines file (read once at startup; MCP, REST and CLI responses are unchanged). `"$lci" replay test-results/dump.json --output test-results/replay-w12.json --window 12 --cap 2 --cap-stage results` then scores other windows, caps, fusion weights, `rrf_k`, priors and rerank modes from the dump without services, configuration (the `--config` file is not read) or index, and `compare` pairs the output with real reports. A query replay cannot score exactly is refused and counted, never approximated. Row format, replay semantics, the latency model and when to run live instead: `.agents/skills/lci-retrieval-evaluation/references/evaluation-workflow.md`.
- Git-mined query set: `cargo xtask mine-queries --repo <repo-root> --key <workspace-key> --out evaluations/mined/<key>.toml [--max 300]` turns qualifying commits from `git log` into queries (subject plus first body paragraph as the query, touched supported files as `expected_paths`, `top_k = 10`). `evaluations/mined/self.toml` (workspace key `self`) is the generated set for this repository: run it like `core.toml` (`--workspace "self=$PWD"`), regenerate rather than edit it, never use it to tune ranking. `core.toml` is the hand-written required set. Skip rules, labels and tags: same reference.
- Gold strata and transcript shapes: `cargo xtask gold strata --set <set> --gold <path> [--out <path>]` classifies each gold item as `core`, `grep_easy` or `agent_trap` from the item alone and reports the counts, the hop quantiles, the items no rule reaches and the items whose question holds a gold file's stem; the same `guard` is a stratum of every scorer. `cargo xtask mine-transcripts --input <sim.json or .jsonl>.. [--gold <path>] [--out test-results/transcripts/shapes.json]` counts question shapes and trace classes over synthetic transcripts in the sim trace shape and writes only shapes, counts and anonymised templates. Rules and schema: [gold-scorers.md](../spike/multimap/v2/gold-scorers.md).
- Live acceptance: `cargo xtask acceptance core` and `acceptance lsp` default to this repository (`--profile gust --workspace /path/to/gpu-dialect-v0`, or `$LCI_ACCEPTANCE_GUST_WORKSPACE`, runs them against the optional external GUST example); `lsp` checks workspace-symbol, definition and reference navigation against the same symbol and saves each normalized response in `test-results`. With the real embedder and reranker running, `cargo xtask acceptance multilingual` creates a disposable fixture and data directory under `test-results`, uses the real debug binary; it verifies all supported language IDs, semantic and lexical retrieval with live reranking, production TypeScript, Python and C# ranking over test decoys, zero-work unchanged indexing, one-file invalidation, deletion, restart reuse, and prior-snapshot retrieval after an unreachable embedding endpoint makes an update fail (`test-results/multilingual-*.json`). Per language, `<lang>-lsp`, `<lang>-missing` and `<lang>-recovery` (markdown has no `-recovery`) run a real server (options and prerequisites: `.agents/skills/lci-lsp-adapter/references/acceptance.md`, `docs/development/live-acceptance-ci.md`); each skips with `PREREQUISITE_UNAVAILABLE` when its server is not found.
- Metric tiers (method and status in [evaluation.md](../spike/multimap/evaluation.md)): agent runs are the ground truth but too costly to run regularly, so cheap proxies run constantly and are checked against agent runs now and then, and quality is reported together with cost.

| Tier | When | What |
| --- | --- | --- |
| 1 | every change, deterministic | hit@k, recall@k, span hit, MRR on the frozen sets; speed proxies (pops, hops, expansions); cost-aware recall (recall per 1k tokens returned); the simulated agent (design, not built) |
| 2 | milestones, cheap model in the loop | confidence calibration; a small fixed subset judged by a cheap model |
| 3 | rare, before releases | real agent A/B runs, mainly to validate the proxies |
