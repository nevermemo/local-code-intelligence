# local-code-intelligence

Cross-platform (Windows, macOS, Linux) Rust, TypeScript, JavaScript, Python, C#, Go, Java, C, and C++ code retrieval for any Streamable HTTP MCP client, or directly over a plain REST/OpenAPI surface for clients that don't speak MCP. It combines Tree-sitter syntax chunks, an owned embedded LanceDB index, local Qwen embeddings, ripgrep lexical search, optional persistent language-server retrieval for every supported language, Reciprocal Rank Fusion, and fail-open neural reranking.

Supported source extensions and result language identifiers are exact and case-sensitive:

| Extension | Language identifier | Parser |
| --- | --- | --- |
| `.rs` | `rust` | Tree-sitter Rust |
| `.ts` | `typescript` | Tree-sitter TypeScript |
| `.tsx` | `tsx` | Tree-sitter TSX |
| `.js` | `javascript` | Tree-sitter JavaScript |
| `.jsx` | `jsx` | Tree-sitter JavaScript/JSX |
| `.py` | `python` | Tree-sitter Python |
| `.cs` | `csharp` | Tree-sitter C# |
| `.go` | `go` | Tree-sitter Go |
| `.java` | `java` | Tree-sitter Java |
| `.c` | `c` | Tree-sitter C |
| `.cpp` | `cpp` | Tree-sitter C++ |
| `.hpp` | `cpp` | Tree-sitter C++ |

The extension decides the language, with one content exception: a `.ts` file whose first non-blank content (after an optional UTF-8 byte-order mark) is an XML declaration (`<?xml`) or a `<TS` root element with attributes is a Qt Linguist translation catalog, not TypeScript. It is skipped as non-source data (not parsed, chunked, embedded, or listed by `list_indexed_files`) and counted in `skipped_non_source_files`. No TypeScript file starts that way: a comment, a bare `<TS>` type assertion, or `<TS extends T>(...) => ...` stays TypeScript. Other extensions have no content check.

All twelve extensions (eleven distinct languages -- `.cpp` and `.hpp` both identify as `cpp`) always have Tree-sitter syntax indexing and retrieval regardless of LSP configuration. Navigation (`search_symbols`/`find_definition`/`find_references`) is additionally available behind an optional, independently-configured language server per language family: Rust uses `rust-analyzer`; C# uses standalone `csharp-ls`; TypeScript/TSX/JavaScript/JSX share one `typescript-language-server` instance; Python uses `pyright` (`pyright-langserver`); Go uses `gopls`; Java uses `jdtls` (Eclipse JDT Language Server); C and C++ share one `clangd` instance. None of these are bundled or installed by LCI, and a disabled or unavailable one never affects syntax retrieval for its language — only navigation on that language's files is affected: `find_definition` and `find_references` fail with a clear tooling error, and `search_symbols` answers without that language and names it in a `warnings` entry. `workspace/symbol` search (`search_symbols`) is honestly limited for TypeScript/Python: since LCI never writes a `tsconfig.json`/`pyrightconfig.json` into a user's repository, a freshly spawned server has no project context until `find_definition`/`find_references` open a file, so `search_symbols` results depend on what's already been opened in that server session. Go's `gopls` needs a `go.mod` at or above the workspace root to build its package graph; without one it degrades to a much weaker fallback (fail-open, same as every other adapter here -- LCI never writes one on the caller's behalf). Unlike every other server, `[java].path` configures the jdtls *installation directory*, not an executable: `jdtls` has no single native binary, so LCI spawns `java` directly itself, finding the Equinox launcher jar and platform config directory under that path (an earlier design that reused jdtls's own Python launcher script produced a `local-code-intelligence -> python -> java` process chain that hung indefinitely on Windows, since killing the direct `python` child does not cascade to the `java` grandchild without a Job Object; spawning `java` directly, like every other adapter, avoids that entirely). `clangd` needs no `compile_commands.json` for LCI's per-file navigation use case -- confirmed live against a standalone fixture with no build system present -- but a workspace with a real build system can still point it at its own compilation database via `[clangd].args` (e.g. `--compile-commands-dir=...`); LCI never generates one on the caller's behalf.

## Build and run

Build prerequisites are Rust stable 1.95 or newer, a C/C++ toolchain (MSVC + Windows SDK on Windows; a system compiler on macOS/Linux), CMake, and `protoc`. `cargo xtask setup` auto-downloads and verifies the official `protoc` release on Windows; on macOS/Linux it checks `PATH` for `protoc`/`cmake` and prints an install hint (`brew install protobuf cmake`, `apt install protobuf-compiler cmake`, etc.) if either is missing. Ripgrep is optional and fails open when unavailable. Rust navigation additionally needs the optional `rust-analyzer` and `rust-src` Rustup components. C# navigation optionally needs a standalone `csharp-ls` executable. TypeScript/JavaScript navigation optionally needs `typescript-language-server` (`npm install -g typescript-language-server typescript`; the workspace itself also needs its own `typescript` dependency, same as any real TS/JS project). Python navigation optionally needs `pyright` (`npm install -g pyright`, providing `pyright-langserver`). Go navigation optionally needs `gopls` (`go install golang.org/x/tools/gopls@latest`). Java navigation optionally needs a JDK 21+ and a jdtls install (an extracted `jdt-language-server-*.tar.gz` release directory from https://download.eclipse.org/jdtls/snapshots/; `[java].path` points at that directory, not at an executable -- see Configuration below). C/C++ navigation optionally needs a standalone `clangd` executable. None of these are bundled or installed by LCI. No Python environment or database server is required to build or run LCI itself.

All dev/build/test/acceptance tasks run through the `xtask` crate (`cargo xtask <command>`) instead of shell scripts, so the workflow is identical on Windows, macOS, and Linux:

```bash
cd local-code-intelligence
cargo xtask setup
rustup component add rust-analyzer rust-src
cargo xtask build --test
./target/debug/local-code-intelligence init    # optional: write this machine's local overlay (tool paths, data_dir); see Configuration
./target/debug/local-code-intelligence serve   # local-code-intelligence.exe on Windows
```

The first build compiles LanceDB and its dependencies and can take several minutes. Subsequent builds reuse Cargo's cache. When iterating on chunking, language adapters, filters, or LSP adapters, `cargo check -p lci-core` / `cargo test -p lci-core --lib` skip that dependency tree entirely and finish in seconds -- see `docs/development/testing.md` for the full picture, including an optional personal (not project) sccache/linker setup that speeds up full-workspace builds too.

Build note: LanceDB 0.38.0 requires its `remote` Cargo feature to compile because its job module references an HTTP error variant without a feature guard. This project enables that compile-time feature but uses only local embedded database paths.

The executable serves:

- MCP: `http://127.0.0.1:8768/mcp`
- MCP, one more endpoint per configured `[search_profiles.<name>]`: `http://127.0.0.1:8768/mcp/<name>` (the same tools, with `search_code` running that search profile; none unless profiles are configured, and the startup log lists them)
- REST: `http://127.0.0.1:8768/v1/*` (plain JSON-over-HTTP mirror of the MCP tools, for non-MCP clients)
- OpenAPI document: `http://127.0.0.1:8768/openapi.json`
- Health: `http://127.0.0.1:8768/health`
- Readiness: `http://127.0.0.1:8768/ready`

Those URLs use the default port. With another `port` (configuration file, local overlay or `LCI_PORT`), `lci config` prints the URLs for the port in effect (see Configuration); a one-off `serve --port` override is not visible to it.

Smoke test from another terminal:

```bash
curl http://127.0.0.1:8768/health
./target/debug/local-code-intelligence config   # every resolved value, its source and the URLs for the port in effect
```

The server binds only to loopback. Its MCP transport uses the official `rmcp` SDK with host/origin validation (on `/mcp/<name>` too) and supports session-based older clients as well as the SDK's current protocol. Every other route (the REST mirror, `/openapi.json`, `/health`, `/ready`) applies the same DNS-rebinding protection: the `Host` header must name a loopback address (`127.0.0.1`, `localhost`, `::1`), and a browser `Origin`, when present, must be this server's own `http://127.0.0.1:<port>` or `http://localhost:<port>`; anything else gets HTTP 403. Non-browser clients that send no `Origin` (curl, scripts, the CLI) are unaffected. `/health` is a cheap process-liveness check and never contacts model services. `/ready` and the MCP `service_status` tool return the same bounded dependency report. They return HTTP 200 when a new semantic index can be created, even if optional channels are degraded, and `/ready` returns HTTP 503 when a required dependency is unavailable. Ctrl+C stops the server.

## Configuration

Defaults work with the services specified for this project. Copy `config.example.toml` to `config.toml` to override them, then pass `--config config.toml` before or after a subcommand (or set `LCI_CONFIG` to its path). A configuration file is read only when named this way; the one other file consulted is the local overlay described below. Unknown fields are errors.

Values resolve in layers, lowest to highest: the built-in default, the configuration file, one local overlay file, `LCI_<KEY>` environment variables, and command-line flags (`serve --port`). Resolution is per key: an overlay that sets `data_dir` leaves the file's `embedding_url` alone, and a setting no layer sets keeps its default. Without an overlay file and without `LCI_*` variables the result is exactly the file's values over the defaults.

The configuration file describes behaviour and is the one to share. Only machine-specific settings may come from the overlay or the environment: `data_dir`, `port`, `embedding_url`, `embedding_model`, `reranker_url`, `reranker_model`, `ripgrep_path`, `rust_analyzer_path`, and, for each language-server section (`csharp`, `typescript`, `python`, `go`, `java`, `clangd`), `path`, `args` and `disabled`. Any other key in the overlay (a candidate count, a template, a timeout, `[channels]`, `[fusion]`, `[index]`, `[search_profiles]`) is an error that names the key and says it belongs in the configuration file, so a local file can never change ranking. Changing `embedding_url` or `embedding_model` this way changes the embedding identity, so indexes built with the old values are re-embedded; `lci config` prints the identity.

- Overlay file: `<stem>.local.toml` beside the configuration file in use (`config.local.toml` for `config.toml`, `lab.local.toml` for `lab.toml`). With no configuration file it is the per-user file `local-code-intelligence/config.local.toml` under the platform's configuration directory (`%APPDATA%` on Windows, `~/Library/Application Support` on macOS, `$XDG_CONFIG_HOME` or `~/.config` on Linux). `LCI_LOCAL_CONFIG=<path>` names a different file, and `--no-local-config` ignores it. A missing overlay is not an error, and nothing creates it except `lci init` (below). It holds this machine's paths: keep it out of version control.
- Environment: `LCI_DATA_DIR`, `LCI_PORT`, `LCI_EMBEDDING_URL`, `LCI_EMBEDDING_MODEL`, `LCI_RERANKER_URL`, `LCI_RERANKER_MODEL`, `LCI_RIPGREP_PATH`, `LCI_RUST_ANALYZER_PATH`, and `LCI_<LANG>_PATH` / `LCI_<LANG>_DISABLED` (`true`, `false`, `1` or `0`) for `LANG` in `CSHARP`, `TYPESCRIPT`, `PYTHON`, `GO`, `JAVA`, `CLANGD`; `args` can be set only in a file. An empty variable counts as unset, and a malformed one is an error naming it. `LCI_CONFIG` and `LCI_LOCAL_CONFIG` name the two files; `--config` wins over `LCI_CONFIG`. `LCI_CANDIDATE_DUMP` is process-level behaviour, not configuration (see Direct CLI).
- Values are taken exactly as written: there is no `~` or `${VAR}` expansion, and `data_dir` must be absolute.
- Port 8765 belongs to the separate generation model, which LCI never contacts: `embedding_url` and `reranker_url` are rejected when their effective port is 8765 (an explicit `:8765` on any host; a URL without a port uses its scheme's default), whichever layer supplies them.
- `lci config [--json]` resolves all of this and prints every value with the layer it came from, the files it consulted, and the URLs derived from the port, without creating the data directory, opening the index, sending a request or starting a language server. Values are printed as configured, including any credentials in a URL, so treat the output as local. See Direct CLI.
- `lci [--config <file>] init [--force] [--dry-run] [--no-probe] [--json]` writes the overlay for this machine from what it finds, so an agent or a second machine does not have to guess a path:
  - It writes only facts. `data_dir` is written as the platform default made explicit, and each of `rg`, `rust-analyzer`, `csharp-ls`, `typescript-language-server`, `pyright-langserver`, `gopls` and `clangd` found on `PATH` is written as an absolute path (the `.exe` or `.cmd` shim on Windows), because an editor-launched server often sees a shorter `PATH` than your shell. A key that a higher layer (the configuration file, an `LCI_*` variable) already sets is left alone and noted. Nothing is started to check a tool.
  - Everything else it learns is a comment in the file: a missing tool and how to install it, whether each model service answers and which models it lists, whether the configured model is among them, whether the port is free on `127.0.0.1` (and, when it is not, whether an LCI answers `/health` there), and that `jdtls` (an installation directory) must be set by hand. It never writes a model name, a model URL or a port, never picks another port, and never writes the main configuration.
  - The overlay is the one `lci config` reports as `local`: beside `--config`, else the per-user file, or the file `LCI_LOCAL_CONFIG` names (it need not exist; its directory is created). An existing file is never replaced without `--force`: without it `init` exits 3 and changes nothing. `--dry-run` prints what would be written and writes nothing; the file is otherwise written through a temporary file and a rename. The result is read back and validated before it is written.
  - It contacts only the model services and the port, only on loopback hosts (`127.0.0.1`, `localhost`, `::1`), with no proxy and without following redirects, and never port 8765 (the generation model): a model URL on 8765 or on any other host is reported as not probed, on stderr and in the file, whatever flags are given. `--no-probe` sends no request at all. A port from 8765 to 8767 is not even bound.
  - `--json` prints one object whose keys include `path`, `status` (`written`, `dry_run` or `exists`), `overlay` (the text), `set` (the keys written), `detected` (the data directory and each tool), `probes` (the two URLs and the port), `comments`, `valid` and `warnings`.

`[channels]` switches the retrieval channels and the reranker off for searches, mainly to run controlled evaluation arms. A file without the section behaves as before. A disabled channel contributes no candidates and does no work (`semantic = false` never embeds the query, `lsp = false` never starts a language server), reports a zero timing, and adds no warning, because turning it off is a choice rather than a failure; enabled channels still fail independently and open (an optional channel's failure never fails a search). A disabled reranker returns the fusion order with `reranked = false`, sends no rerank request, and adds no warning; the shortlist is still capped at `rerank_candidate_count`, exactly as in the reranker-failure fallback. At least one of `semantic`, `lexical`, and `lsp` must stay enabled: a configuration that disables all three is rejected when the file is loaded, since no search could return anything. With `semantic = false`, a query that matches nothing returns an empty result instead of an error when an enabled lexical or LSP channel ran without failing; if every enabled channel fails (or none can run), the search fails and the error carries the channel warnings. The grep-only baseline arm is `semantic = false`, `lsp = false`, `reranker = false`: ripgrep matches mapped onto chunks and ranked by match count, nothing else. The switches affect searches only. Indexing still embeds and stores every chunk, so flipping a switch never requires a reindex, and `/ready` and `service_status` keep probing the embedding service (a required dependency of indexing) even when `semantic = false`.

`[search_profiles.<name>]` names a set of overrides for those same query-time switches, so one configuration can hold several quality/speed settings next to the default. A profile may set only `semantic`, `lexical`, `lsp`, `reranker`, and `rerank_candidate_count`; every key it leaves out keeps the top-level value, and an unknown key (an embedding setting, a candidate depth, a fusion setting, `rerank_document_max_bytes`) is an error. Nothing a profile can set changes the index or the embedding identity, so every profile searches the same index, and fusion, the per-file cap, and the reranker's input are the same too. The `lsp` switch behaves exactly as in `[channels]`: a profile with `lsp = true` over a top-level `lsp = false` starts language servers for its searches, and one with `lsp = false` never does. A profile name is 1 to 32 letters, digits, `_` or `-`, starting with a letter or digit; `default` is reserved for the unprofiled search. Each profile is checked when the file is loaded, with its overrides applied: it must keep at least one of `semantic`, `lexical`, and `lsp` enabled and a `rerank_candidate_count` of 1–200. A search that names no profile is unchanged by any of this: same results, same JSON, and a response that has no `search_profile` key. A search that names one reports it as `search_profile` in the response, and an unknown name is an error that lists the configured names, never a silent fall back to the defaults. A search chooses its profile by where it is asked: the command line with `search --search-profile <name>` (below), MCP by connecting to the endpoint `/mcp/<name>`, and REST with `POST /v1/search_code?search_profile=<name>` (both described under the MCP tools table and the REST/OpenAPI surface below). `evaluate` always runs the top-level settings. An example with a `fast` and a `deep` profile is in `config.example.toml`.

Persistent data lives in `data_dir\lancedb` and `data_dir\manifests`, outside indexed repositories. Canonicalization resolves path aliases and symlinks. A SHA-256 of the canonical workspace path identifies a workspace; each workspace has a separate LanceDB table (`ws_` plus the first 16 hex digits of that id) and parse manifest. Indexes written under the earlier full-id table name (`ws_<64 hex>`) stay searchable and are read until the workspace's next index commit, which writes the short-named table without re-embedding unchanged chunks and then drops the old one. The move is one-way: an older binary then sees the workspace as not indexed and embeds it again. A table that records a different workspace path than the one asking for it is refused with a table-name collision error instead of being overwritten; give one of the workspaces its own `data_dir`. On Windows keep `data_dir` under 150 characters: LanceDB's internal paths below it must fit Windows' 260-character limit, and `/ready` flags a longer one. Manifest schema v2 records language and adapter compatibility per file, so changing one language parser does not invalidate unaffected languages. Compatible schema-v1 Rust manifests are migrated without reparsing unchanged files. Data directories and indexed workspaces cannot contain one another. Moving a repository creates a new workspace identity. This milestone has no automatic index cleanup command.

The generation service at port 8765 is independent and is never called, inspected, proxied, or managed by this application.

### Security: language servers and untrusted repositories

Search uses enabled language servers for the indexed languages; symbol search,
definitions and references also start the applicable server. Rust's adapter is
always enabled when its executable is available; the other adapters are disabled
until configured. These are local processes with the user's permissions, not
sandboxed parsers.

By default LCI starts rust-analyzer with `cargo.buildScripts.enable = false`,
`procMacro.enable = false` and `checkOnSave = false`, and clears
`cargo.buildScripts.overrideCommand` and `check.overrideCommand`. Its child
environment sets `CARGO_NET_OFFLINE=true` and empties `RUSTC_WRAPPER`,
`RUSTC_WORKSPACE_WRAPPER`, `CARGO_BUILD_RUSTC_WRAPPER` and
`CARGO_BUILD_RUSTC_WORKSPACE_WRAPPER`; the same overrides are supplied through
`cargo.extraEnv` and `check.extraEnv`. This avoids ordinary build-script,
procedural-macro and check-on-save execution and Cargo downloads, at the cost of
incomplete analysis of generated code and missing uncached dependencies.
See the rust-analyzer manual's [Configuration](https://rust-analyzer.github.io/book/configuration.html)
sections for those option names.

The top-level config key `rust_analyzer_trusted = true` removes these LCI
restrictions (but keeps workspace-symbol search settings), restoring
rust-analyzer's own defaults and inherited environment. It permits build scripts,
procedural macros, checks and dependency downloads, including dependency code.
Enable it only when **all** repositories and dependencies accessed by that LCI
process are trusted; it is not a per-request or per-workspace trust grant. Keep
this behavioral setting in the main LCI configuration, not a machine overlay.

**Residual risks:** these defaults are defense in depth, not an untrusted-code
sandbox. LCI does not suppress or rewrite repository files such as
`rust-analyzer.toml` or `.cargo/config.toml`; depending on the rust-analyzer
version, settings in them can take precedence over the client settings LCI
sends, so do not rely on client settings as a version-independent policy against
repository commands or environment overrides. Cargo's `[env]` table with
`force = true` can replace inherited values for processes Cargo runs. Compiler
and toolchain selection, repository-provided executables, other Cargo
configuration and language-server vulnerabilities remain execution risks, and
rust-analyzer still invokes Cargo metadata and toolchain discovery. Other enabled
servers can also execute project tooling or load plugins (notably Java build
imports and C# MSBuild) or access the network (for example gopls modules); this
Rust option does not harden them. For untrusted input, use OS-level isolation with
restricted permissions/network and trusted tool binaries. `[channels].lsp = false`
disables language servers for code search only; it does **not** disable explicit
symbol/navigation tools.

## MCP tools

All tools return structured JSON, also available as MCP text content. Tool failures set MCP `isError`.

| Tool | Arguments | Result |
| --- | --- | --- |
| `index_workspace` | `workspace_path` | Canonical workspace/ID, file/chunk counts, parsed/unchanged/removed files, `skipped_non_source_files` (source-extension files whose content is another format, currently Qt Linguist `.ts` catalogs), newly embedded/reused chunks, total time; plus, only when non-empty, `lossy_decoded_files` (non-UTF-8 files indexed from a lossy decoding) and `truncated_for_embedding` (chunks embedded from a shortened prefix because the embedding service rejected their full length) |
| `index_status` | `workspace_path` | Whether indexed/indexing/stale/watched, chunk count, embedding dimension, configuration compatibility, last successful indexing time; `stale_check_error` when staleness could not be determined (an unreadable file), in which case an indexed workspace reports `stale: true`; `analyzers_running`, an object with one entry per language server (`rust-analyzer`, `csharp-ls`, `typescript-language-server`, `pyright`, `gopls`, `jdtls`, `clangd`) that is `true` while a started, ready server of that name runs for this workspace and `false` otherwise (not started, released, disabled, or not installed). The older booleans `analyzer_running` (rust-analyzer), `csharp_analyzer_running`, `typescript_analyzer_running`, `python_analyzer_running`, `go_analyzer_running`, `java_analyzer_running`, and `clangd_analyzer_running` are deprecated: they still report the same values for one more release, then go; read `analyzers_running` instead. | `list_indexed_files` | `workspace_path` | Every file the persistent index has cached chunks for, with language and chunk count, from the last successful `index_workspace` |
| `watch_workspace` | `workspace_path` | Start debounced polling and automatic reindexing for an indexed workspace |
| `unwatch_workspace` | `workspace_path` | Stop automatic reindexing for a workspace |
| `search_symbols` | `workspace_path`, `query` | Workspace symbols from every applicable enabled language server (rust-analyzer, csharp-ls, typescript-language-server, pyright, gopls, jdtls, clangd), with provider/language metadata. When some servers fail and another answers, the call still succeeds with the answering servers' symbols plus, only when non-empty, `warnings` (one `Optional LSP provider unavailable: <provider>: <cause>` entry for each failed server, in provider order), so an empty `results` is not a confirmed "no match"; the call is an error only when every applicable server failed |
| `find_definition` | workspace path, relative file path, one-based line, zero-based UTF-16 character | Definition locations routed by extension to the matching language server |
| `find_references` | the definition arguments plus optional `include_declaration` | Reference locations routed by extension to the matching language server |
| `search_code` | `workspace_path`, `query`, optional `top_k` | Ranked source chunks, scores, timings, fallback warning, informational notes (for example a language server still starting, or a `top_k` above `rerank_candidate_count`), and index lifecycle metadata; on `/mcp/<name>`, also `search_profile` (the search profile this endpoint runs, see below) |
| `service_status` | none | The same required/optional readiness report as `/ready` |

Example arguments (these index this repository itself -- the one workspace every reader already has on disk):

```json
{"workspace_path":"C:\\code\\local-code-intelligence"}
```

```json
{
  "workspace_path": "C:\\code\\local-code-intelligence",
  "query": "plain REST JSON-over-HTTP mirror of the MCP tools",
  "top_k": 8
}
```

On macOS/Linux the same argument is a plain `/path/to/local-code-intelligence`; the doubled backslashes above are JSON string escaping, not part of the path.

Search profiles are chosen by endpoint, not by argument. `/mcp` runs `search_code` exactly as configured at the top level. For each `[search_profiles.<name>]` (see Configuration) the server also mounts `/mcp/<name>`, whose `search_code` runs that profile and whose result then carries `"search_profile": "<name>"`; the result of `/mcp` has no such key. Every endpoint serves the same tools with the same input schemas and the same server instructions, so `initialize` and `tools/list` answer identically on each, and `search_code` takes no profile argument. Point a client at the endpoint it should search with; to offer several profiles to one client, register one MCP server entry per URL. Each endpoint keeps its own sessions: a session id issued by one is unknown (HTTP 404) at every other. A path under `/mcp/` that names no configured profile is HTTP 404 rather than the default search, and only `/mcp` and `/mcp/` (a trailing slash) are the default endpoint. A configuration with no profiles has `/mcp` alone and answers exactly as it did before profiles existed.

`search_code` automatically creates a missing workspace index, waits for its commit, and continues the requested search in the same call. Concurrent first searches for one workspace share that indexing job; different callers receive results from the committed snapshot without duplicate document embeddings. A compatible persisted index is reused immediately after restart.

Once an index exists, the `[index]` `freshness` policy (default `on-search`) decides whether a search checks for staleness. Under `on-search`, the first search that needs it compares the workspace's file manifest and content hashes against disk, throttled by `stale_check_interval_seconds` so repeated searches in an unchanged workspace reuse the current snapshot without rescanning. When changed, new, or removed files are detected (or the embedding configuration changed), the search incrementally refreshes the index — reusing cached vectors for unchanged content hashes — before continuing. If another refresh is already running, the search waits up to `wait_for_existing_job_seconds` and then reuses that job's result; if the embedding service is unavailable, the previous snapshot is kept and the search still returns results with a warning explaining the refresh could not complete. `freshness = "manual"` never refreshes automatically; use `index_workspace` for an explicit refresh. `freshness = "watch"` leaves refresh to `watch_workspace`'s background poller instead of checking on every search, which suits long-running editor sessions.

The search result's separate `index` object explains first-search latency. `action: created` means that request performed initial indexing, `waited_for_existing_job` means another concurrent request performed it, `refreshed_incrementally` means the search found and applied a staleness refresh before continuing, and `reused` means a compatible, current-enough snapshot was already available. `wait_ms` covers index creation, refresh, or waiting and is zero or near zero for plain reuse; it does not overload retrieval-stage timing fields. Indexing is synchronous and finishes when the new index is persisted, so allow a long client tool timeout for a first search, an automatic refresh, or an explicit indexing pass. Index writes are serialized in the running service, with per-workspace read/write coordination. This version is intended for one running service per data directory; multiple clients should connect to that service. Index commits are additionally serialized across processes by an OS file lock (`<data_dir>/index.lock`), so a CLI `index`, `search`, or `evaluate` run next to a server on the same data directory waits for the other process's commit instead of interleaving LanceDB table overwrites and manifest writes with it; reads never take the lock.

Readiness requires a writable application data directory, accessible embedded LanceDB storage, a reachable embedding endpoint, and the configured embedding model in its OpenAI-compatible model listing. Reranking, ripgrep, rust-analyzer, csharp-ls, typescript-language-server, pyright, gopls, jdtls, and clangd are optional fail-open components. Readiness reports each language server independently; an absent one never disables syntax retrieval for its language. On Windows, the optional `data_dir_path_length` component degrades the report (it never changes `ready`) when `data_dir` is longer than 150 characters, because LanceDB can then fail with `os error 3` (the ceiling is about 163 characters). Dependency probes use `readiness_timeout_seconds`; readiness never downloads, starts, stops, or manages dependencies, and it never inspects or contacts the independent generation service on port 8765.

Watching is opt-in for each server run. It polls only after `watch_workspace`, debounces a detected source change, and calls the same safe indexing path. Watch registrations are not restored after a process restart; persistent indexes and manifests are. A failed automatic update is logged and retried after another poll while the prior LanceDB snapshot remains searchable.

The first applicable LSP request for a workspace starts one long-lived provider process per language server; later calls reuse it. A request that fails because the server went away (it exited, closed a pipe, stayed silent for `lsp_timeout_seconds`, or sent an error response that is not a well-formed error object, or one that comes with a non-null result) discards the process, stops it the way a release does (in the background, so the retry does not wait for it), and retries once with a fresh provider. A server that answers with an error response is alive and is not restarted: an answer that means "ask again" (`ContentModified`, `ServerCancelled`, `RequestFailed`, and rust-analyzer's "file not found" until it reports it is ready) is repeated on the same server up to twice, a repeat starting only within about 5 seconds of the first error response (each request keeps its normal timeout), and any other error (for example tsserver's "No Project") is returned as that provider's error, which `search_symbols` skips like any failed provider. A server that has answered nothing but those "ask again" errors for `lsp_stuck_seconds` (default 15 minutes, counted from its first such answer; each repeat's answer counts, also when a search's latency budget cancelled the call; any result, any other error and any `$/progress` notification from the server start the count over; `0` never replaces it) is wedged rather than loading: the session is replaced, by the call that noticed if it is still waiting (it still returns the server's error) and otherwise by the next call for that language server, and the old server is stopped in the background (a loading server answers them for minutes, and a restarted one starts the load over, so keep the value above the longest load you expect). `RequestCancelled` is not one of these errors. On Windows each server runs in its own job object, so the processes it started (the `node.exe` behind a `.cmd` shim, the binary behind a `rustup` proxy) end with it when it is released, discarded, or the service exits. If the job object cannot be created or the server cannot be assigned to it (an environment that forbids nested jobs, for instance), the server runs unconfined: only its own process is stopped, and a one-time warning in the log says so. A server that nobody has asked for in `lsp_idle_timeout_seconds` (default 30 minutes; `0` disables the release; any search or navigation call for the workspace counts as use, a status check does not) is released to free its memory: LCI sends the protocol's `shutdown` request and waits up to 2 seconds for the answer, sends the `exit` notification and waits up to 2 seconds more for the process to end, and kills a server that ignores them, so a release takes about 4 seconds at most. A server that is still building its symbol index or is serving a call is not released as idle. You can release a workspace's servers yourself with `POST /v1/release_workspace` (below), and a Ctrl+C on `serve` shuts every server down the same way before the process exits, giving the shutdown 5 seconds in all (the servers shut down side by side). After any release, the next search or navigation call for that workspace starts a fresh server transparently. That start pays the cold start and priming again, so the first `search_code` after a release can hit `lsp_search_budget_ms` and report the informational `notes` entry, exactly like the first search after the service starts; a request that was in flight on a server at the moment it was released fails and takes the retry-once path above. `search_code` queries each applicable, enabled provider independently only when filtered indexed chunks contain a language it navigates, and maps locations only to same-language chunks. A missing or disabled optional server leaves semantic and lexical retrieval available. Direct navigation rejects unsupported extensions before startup and returns an MCP error when the selected provider is disabled or unavailable. Definition/reference input lines are one-based; character offsets follow LSP and are zero-based UTF-16 units.

### REST/OpenAPI surface

Every MCP tool above is also reachable as plain JSON-over-HTTP, for clients that don't speak MCP. It's the same process, the same port, and the same `App` methods behind both -- not a second service -- so behavior, filters, and index lifecycle semantics are identical either way.

| MCP tool | REST endpoint |
| --- | --- |
| `index_workspace` | `POST /v1/index_workspace` |
| `index_status` | `POST /v1/index_status` |
| `list_indexed_files` | `POST /v1/list_indexed_files` |
| `watch_workspace` | `POST /v1/watch_workspace` |
| `unwatch_workspace` | `POST /v1/unwatch_workspace` |
| `search_symbols` | `POST /v1/search_symbols` |
| `find_definition` | `POST /v1/find_definition` |
| `find_references` | `POST /v1/find_references` |
| `search_code` | `POST /v1/search_code` |
| `service_status` | `GET /v1/service_status` |

Every `POST` endpoint in this table takes the identical JSON arguments as its MCP tool (see the table above) as the request body. A successful call returns HTTP 200 with the same structured JSON an MCP `tools/call` would return; a failed call returns HTTP 500 with `{"error": "<message>"}` rather than MCP's `isError` content block.

```bash
curl -X POST http://127.0.0.1:8768/v1/search_code \
  -H 'Content-Type: application/json' \
  -d '{"workspace_path":"/path/to/local-code-intelligence","query":"plain REST JSON-over-HTTP mirror of the MCP tools"}'
```

`POST /v1/search_code` also takes an optional `search_profile` query parameter naming a configured `[search_profiles.<name>]`, for example `/v1/search_code?search_profile=fast`; the request body is unchanged. The result then carries `"search_profile": "fast"`. Without the parameter the search is the default one and the result has no such key. An unknown name is the usual HTTP 500 with an error that lists the configured names (or says that none are configured).

One endpoint has no MCP tool: `POST /v1/release_workspace` takes the same `{"workspace_path": ...}` body and shuts down the language servers this service runs for that workspace (the `shutdown` request, then `exit`, bounded to about 4 seconds per server, then a kill for a server that ignores both; several servers shut down side by side). It needs no index. The response is `{"workspace": {"id": ..., "path": ...}, "released": ["csharp-ls"]}`, where `released` lists, sorted, the servers that were stopped (the names `index_status` uses in `analyzers_running`); a workspace with nothing running, or one that was never indexed, answers HTTP 200 with `"released": []`, and a directory that does not exist is the usual HTTP 500. The next search or navigation call for the workspace starts a server again. The command line has no equivalent: a CLI run owns no long-lived servers. MCP `tools/list` is unchanged.

`GET /openapi.json` serves an OpenAPI 3.0.3 document describing every endpoint above, including the `release_workspace` endpoint and the `search_profile` query parameter of `/v1/search_code`. Its request-body schemas are generated directly from the same `schemars`-derived argument structs the MCP tools themselves use, so they cannot drift from what a request actually accepts; response bodies are documented as an open JSON object, matching the exact shapes in the MCP tools table above rather than duplicating them a second time.

## Direct CLI and acceptance test

The CLI calls the same application logic and is useful for testing without configuring an editor. Index commits from the CLI and a running server on the same data directory are serialized by the data directory's index lock, but a separate data directory (`--config` with its own `data_dir`) keeps CLI experiments from waiting on, or refreshing, the server's indexes.

```bash
lci=./target/debug/local-code-intelligence   # local-code-intelligence.exe on Windows
repo=$PWD                                    # this repository: the walkthrough indexes LCI's own source
"$lci" index "$repo"
"$lci" status "$repo"
"$lci" list-files "$repo"
"$lci" search "$repo" 'plain REST JSON-over-HTTP mirror of the MCP tools'
"$lci" symbols "$repo" 'openapi_document#'
"$lci" definition "$repo" 'src/rest.rs' 264 64
"$lci" references "$repo" 'src/rest.rs' 160 3 --include-declaration
"$lci" references "$repo" 'lci-core/src/workspace.rs' 17 11 --include-declaration
"$lci" index "$repo"
```

Everything above runs against this repository, so the walkthrough needs nothing but a clone, a build, and the embedding/reranking services. `search` returns `openapi_document` in `src/rest.rs` as its top hit -- the function that builds the document served at `/openapi.json`. `definition` starts from the call in the `/openapi.json` route at the end of `src/rest.rs` and resolves to that function's declaration; the first `references` call starts from the declaration and returns both it and the wiring. The second `references` call starts from `Workspace::resolve` in `lci-core/src/workspace.rs` and crosses crates: its callers live in `src/app/` and `tests/cases/`. Lines are one-based and characters are zero-based UTF-16, as in every navigation call; the numbers above are this repository's own, so if a file has shifted since, `grep -n openapi_document src/rest.rs` gives the current ones. The second indexing pass should report zero new embeddings if source and model configuration are unchanged. `cargo xtask acceptance core` runs this same index/search/repeat-index flow against this repository and checks that production implementation chunks dominate the top eight results, including `openapi_document`. Pointing any of these at another repository is just a different first argument -- the optional GUST example under retrieval evaluation below shows one.

`config` shows how the configuration resolves (see Configuration) without opening the application:

```bash
"$lci" --config config.toml config          # layers, machine settings with their sources, derived URLs, other settings
"$lci" --config config.toml config --json   # the same as one JSON object
```

`init` writes this machine's local overlay from what it detects (see Configuration for what it writes and what it will not contact):

```bash
"$lci" --config config.toml init --dry-run   # print the overlay it would write; write nothing
"$lci" --config config.toml init             # write config.local.toml beside config.toml (exit 3 if it exists)
"$lci" --config config.toml init --force --no-probe   # replace it, sending no request to any service
```

`--json` prints one object on stdout: `valid` and `error`; `layers` (`file` with `path` and `named_by`, `--config` or `LCI_CONFIG`; `local` with `path`, `state` of `present`, `absent` or `disabled`, and `named_by`; `env`, the machine-set variables that were set; `flags`); `values`, every setting keyed by its dotted name (`port`, `typescript.path`, `index.freshness`; the `[search_profiles.<name>]` tables are one entry, `search_profiles`, present when profiles are configured) with `value`, `source` (`default`, `file`, `local`, `env` or `flag`) and `from` (the file, variable or flag); `config`, the whole resolved configuration; `derived` (`mcp_url`, `mcp_profile_urls`, `rest_base`, `health_url`, `ready_url`, `openapi_url`, `embedding_identity`); and `environment.other` (whether `LCI_CANDIDATE_DUMP` is set). The exit status is 0 for a valid configuration, 2 for one that resolves but fails validation (for example a reserved `port`; the report is still printed, with `valid` false), and 1 when a layer cannot be read or parsed (a missing file, a key outside the machine set in the overlay, a malformed `LCI_*` value; only `valid` and `error` are printed with `--json`).

Search accepts repeatable `--language`, `--include-path`, `--exclude-path`, and `--source-role` filters. Path filters are case-sensitive repository-relative globs: `*` and `?` stay within one path component, while `**` crosses directories. Absolute paths, backslashes, traversal components, empty patterns, and malformed globs are rejected. An explicitly empty include list is a valid filter that returns no results. Requested filters are applied to every retrieval channel and reported back as effective filters; no result may bypass them.

Search also accepts `--search-profile <name>`, which runs it with that `[search_profiles.<name>]` of the configuration applied over `[channels]` and `rerank_candidate_count` (see Configuration). The response then carries `"search_profile": "<name>"`; without the flag it has no such key. An unknown name exits with an error that lists the configured names, before any index work.

Each result includes a deterministic source role. Classification precedence is generated, test, benchmark, example, documentation, configuration, then source. Tests are recognized by `test`/`tests`/`__tests__` directories, the Gradle/Android test source sets `androidTest`/`integrationTest`/`testFixtures`, and per-language file names: Python `test_*.py`/`*_test.py`, JS/TS `*.test.*`/`*.spec.*`, C# `*Test(s).cs`, Go `*_test.go`, Rust `tests.rs`/`test_*.rs`/`*_test.rs`/`*_tests.rs` (a bare `test.rs` stays source, since it is a legitimate production module name; test code in inline `#[cfg(test)] mod tests` blocks cannot be told from the path), Java `*Test`/`*Tests`/`*TestCase`/`*IT.java`, and C/C++ `*_test`/`*_tests`/`*_unittest(s)`/`test_*` (`.c`/`.cpp`/`.hpp`). Layout directories (`examples`, `docs`, `config`, `scripts`, `tools`, `build`, ...) count only above a Maven/Gradle source root -- under `src/<set>/java/` (or `kotlin`/`scala`/`groovy`) the remaining directories are package names, so `com/example/...` is not an example -- and a `config`/`configs`/`configuration` directory marks only non-source files, so production code such as `internal/config/loader.go` stays source. Production source receives a small transparent `0.004` fusion prior; all other roles receive zero. The role and prior are included in result metadata, and explicit role filters remain authoritative.

Run the portable retrieval evaluation with the same application search path:

```bash
"$lci" evaluate ./evaluations/core.toml \
  --workspace "self=$PWD" \
  --workspace "gust=/path/to/gpu-dialect-v0" \
  --output ./test-results/evaluation.json
```

To compare arms on the same queries, run `evaluate` once per configuration with `--config` and name the output files by arm: the default, `[channels] reranker = false` for fusion order alone, or the grep-only baseline `[channels] semantic = false`, `lsp = false`, `reranker = false` (see Configuration). Reports do not record the channel switches, and the switches never invalidate an index, so the arms can run one after another on one `data_dir`; do not run two at once on the same one.

Once two arms have run, `compare` measures the difference between their saved reports without services, configuration, or an index:

```bash
"$lci" compare test-results/fusion.json test-results/semantic-only.json \
  --output test-results/fusion-vs-semantic-only.json
```

It pairs queries by workspace and query text, so both reports must come from the same definition, and prints, for MRR, nDCG@10 and hit@1, the baseline and candidate means, the mean per-query delta (`candidate - baseline`) with a seeded 95% paired-bootstrap interval (`--resamples`, default 10,000; `--seed`), whether that interval excludes zero, and reciprocal-rank wins, losses and ties. Queries present in only one report, or skipped in either, are excluded from the pairs and counted in the summary; a definition with `tags` also gets one block per tag. `--output` writes the full JSON comparison, per-query pairs included. A regression is not an error: the exit code is nonzero only when a report cannot be read or parsed. A delta whose interval contains zero is noise at that query count, so read the interval before calling an arm better. `evaluate --baseline <report.json>` runs an evaluation as usual, embeds the same comparison under a `comparison` key in its report, and prints the summary to stderr.

`evaluate --dump-candidates` additionally records, for every query whose search ran (a skipped query, or one whose search failed, carries no dump), the whole post-filter fused candidate pool (at most the three channel depths together, before the per-file cap and the shortlist cut) so other settings can be scored from the report without services. Each such query then carries `candidates`, one row per chunk in fused order; `arm`, the configuration the dump was taken under (`rrf_k`, the `fusion` weights and per-file cap, `rerank_candidate_count`, `rerank_document_max_bytes`, the three channel depths, `channels`, the query's result window `k`, the embedding identity, the reranker model, and `rerank_mode`); `rerank_outcome`: `scored`, `failed` (fusion order with a warning), `off` (`[channels] reranker = false`), or `not_run` (nothing to rerank); and `notes`, the search's informational notes when it has any (for example "LSP still starting or slow" when the language-server channel hit its budget), so queries whose language-server channel was cut short can be excluded or stratified. A row holds the path, language, line range, content hash (empty in a dump written before the field existed), and source role; the semantic, lexical, and language-server ranks (one-based, exactly as fusion consumed them) with the semantic and lexical scores and the lexical match count; the source-role `prior`; `fusion_score`; `fused_rank` (before the cap) and `capped_rank` (after the cap, before the cut), both one-based; `shortlisted` (`capped_rank <= rerank_candidate_count`); for shortlisted rows `document_bytes` and `est_tokens` (`document_bytes / 4`) of the document the reranker was given; `rerank_rank` and `reranker_score` for the shortlisted rows when the outcome is `scored`; and the bounded `snippet`. With `f32` arithmetic, `fusion_score` is `0.0 + semantic_weight / (rrf_k + semantic_rank) + lexical_weight / (rrf_k + lexical_rank) + lsp_weight / (rrf_k + lsp_rank) + prior`, adding only the channels that returned the chunk, in that order, so the rows reproduce it bit for bit. The flag changes nothing else: the results, metrics, and every other field of the report are the same with it on or off, and without it none of these keys is written; the MCP, REST, and CLI `search` never emit them. Reports are pretty-printed, and a dump takes roughly 100 KB or more per query. Because the shortlist cut bounds what a dump can say about the reranker, take a dump with `rerank_candidate_count` as large as the largest shortlist you want to score (up to 200).

Starting a process with `LCI_CANDIDATE_DUMP=<file>` makes each of its searches that returns a report (a failed search appends nothing) also append one JSON line (`ts`, `workspace_path`, `query`, `search_profile` when the search named a search profile and absent otherwise, `filters`, `channels`, `rerank_candidate_count`, `rerank_outcome`, `timings`, and `candidates` as above; with a profile, `channels` and `rerank_candidate_count` are its resolved values) to that file, leaving every MCP, REST, and CLI response unchanged; the variable is read once at startup, a failed write only logs a warning, and each append logs its own cost (`dump_ms`), which `timings` does not include.

`replay` scores other retrieval settings from such a dump, again without services, configuration, or an index (the configuration named with `--config` is not read):

```bash
"$lci" replay test-results/dump.json --output test-results/replay-w12.json \
  --window 12 --cap 2 --cap-stage results
"$lci" compare test-results/dump.json test-results/replay-w12.json
```

For each dumped query it recomputes fusion from the dumped ranks (first checking, at the dumped arm, that every `fusion_score`, the fused order, and the per-file cap's `capped_rank` and `shortlisted` reproduce bit for bit), re-sorts under the replayed weights, applies the per-file cap (`--cap`; `--cap-stage shortlist`, the default, caps before the window is cut as production does, `results` caps the whole list after reranking), cuts the first `--window` rows, orders them with the dumped reranker scores, appends the rest of the fused order, takes the query's own result window `k`, and runs the unchanged metrics. `--rerank-mode` is `replace` (production: reranker score descending, then position in the window, the order the reranker service returns), `vote` (re-sort by `fusion_score + --vote-weight / (rrf_k + reranker rank)`, the rank counted within the replayed window), or `off` (fused order). Every setting left out keeps the dumped arm's value: `--window`, `--cap`, `--cap-stage`, `--semantic-weight`, `--lexical-weight`, `--lsp-weight`, `--rrf-k`, `--prior` (the prior of `source` chunks; 0.004 in production), `--rerank-mode`, `--vote-weight`. `--output` writes an ordinary evaluation report that `compare` pairs with real ones, plus a report-level `replay` block: the source file, the dumped and replayed arm, query counts, refusals, the latency model, and the original timings. At the dumped arm (no options) the evidence and metrics equal the dumped ones whenever the window is at least `k`; production returns only the window, so for a smaller window replay returns more rows and `replay.past_window_queries` counts those queries. Replay is exact for any window up to the dumped shortlist, either cap stage, and any weights, `rrf_k`, or prior under `--rerank-mode off`. A query it cannot score exactly is refused, counted, and listed, never approximated: `unscored_window` (a reranked window holding a candidate the dump never sent to the reranker, for example a larger window or a different cap than the dump took), `rerank_not_scored` (a reranked arm over a dump whose reranker failed or was off), `fusion_mismatch` or `shortlist_mismatch` (the dump does not reproduce at its own arm), and `not_dumped` (the query carries no dump). A refused query is written as skipped (`skipped`, `replay_refusal`, the cause in `reason`), so `compare` leaves it out of every pair; queries skipped or failed in the source carry over unchanged. It cannot replay a larger window or channel depth than the dump took, another `rerank_document_max_bytes`, reranker, query instruction, chunking, or embedding: run those live. Latency in a replayed report is an estimate, labelled so in `replay.latency`: `reranking_ms` is `a + b * tokens` over the `est_tokens` of the replayed window, fitted by least squares over the dump's reranked queries (`a`, `b`, and R^2 are reported), falling back to 400 ms plus 290 tokens per second when R^2 is below 0.5; `total_ms` swaps that into the dumped total; the other stages are the dump's measurements; the measured timings stay under `replay.original`.

Workspace mappings are supplied at runtime, so checked-in definitions contain no machine-specific absolute paths. The GUST workspace is optional; its queries are explicitly skipped when no mapping is supplied. Without `--output`, JSON is written to stdout. A required missing workspace, search error, expected-path miss, wrong expected role, or missing required snippet produces a failed query and a nonzero process exit after the JSON report is emitted. Valid optional skips do not fail the run.

Reports contain bounded path, line-range, role, rank, score, and preview evidence; per-query hit@1, hit@3, hit@8, reciprocal rank, nDCG@10, recall@3/@8, file-level accuracy@5/@10, preference/disfavor counts, role distribution, reranker state, timings, lifecycle, and effective filters; and aggregate hit rates, MRR, means of the rank-aware metrics, median/p95/max latency with the sample count `n` (total and per stage; nearest-rank p95 hides the worst query at small `n`, for example it is the second-highest of 35, so read `max`), fallback count, and created/reused/waited/refreshed index counts. nDCG@10 uses graded gain (a result matching `expected_paths` scores 2, one matching only `preferred_paths` scores 1) and credits each gold pattern once, so a repeated chunk of the same file adds nothing; recall@k is the fraction of distinct expected patterns found in the first k results; and file accuracy@k counts distinct files so repeated chunks of one file take a single position. The `@10` metrics are bounded by the query's `top_k`: the hand-written `core.toml` uses 8, making them effectively @8 (like `hit_at_8_or_window`), while the git-mined set below uses 10; set `top_k >= 10` to compare with literature @10 numbers. Generated reports belong under `test-results` and are not committed. Evaluation reuses compatible persisted indexes and preserves the existing first-search lifecycle behavior. It calls only the configured embedding and reranking services, whose defaults are ports 8766 and 8767; application paths never contact port 8765.

Git history yields a larger query set at no annotation cost. `cargo xtask mine-queries --repo <repo-root> --key <workspace-key> --out evaluations/mined/<key>.toml [--max 300]` reads `git log` (nothing else) and turns each qualifying commit into one query: the subject, plus the first body paragraph when it adds words (at most 300 characters), with the touched supported-extension files as `expected_paths` and `top_k = 10` so the `@10` metrics are not window-bound. It skips merges, reverts, subjects under four words, formatting commits (a subject containing the whole word lint, clippy, fmt, rustfmt, formatting, typo, typos, or whitespace), commits touching no or more than ten supported source files (lockfiles, vendored and generated paths do not count), and repeated query text; `--max` keeps the most recent queries. `expected_paths` keeps only touched files that still exist at `HEAD`, following a file through any later git-detected rename to its current path (a rename git does not detect, or one with heavy edits, loses the file), and evaluation searches the checked-out tree rather than the commit's parent, so the labels are an approximation: a file may have been rewritten since. Commit authors often name the files they changed, so each query is tagged `keyword` (the query text contains the words of a touched file's stem, in any spelling, where only a short list of generic stems (`main`, `mod`, `lib`, `index`, `types`, ...) is excluded; or it contains a code-identifier-shaped token: `snake_case`, a `::` path, a `--flag`, a `/` between lowercase letters or digits or a `.` between word characters as in `src/lsp` or `index.rs`, or an inner capital as in `camelCase` or `ResultEvidence`, ignoring common proper nouns such as `JavaScript` and `GitHub`; prose alternatives like "LSP/embedding" do not count) or `keyword-agnostic` (it has neither). A query may also carry `gold-drift`: more than half of the commit's changed lines (added plus deleted, from `git log --numstat`) are in files that are not gold -- unsupported or excluded files, deleted files, and files gone from `HEAD` even after later renames; a pure move counts on both sides and an exact 50/50 is not drift -- so a miss on such a query may not be a retrieval failure. It may also carry one of `short-query` (query text under 8 words) or `long-query` (25 words or more), counted on the query text sent to search, so an appended body paragraph counts. The report adds `by_tag` with executed count, hit@1, hit@3, MRR, and mean nDCG@10 per tag. Any query in any definition may carry `tags = [...]`; tags only group the aggregate. `evaluations/mined/self.toml` (workspace key `self`) is the generated set for this repository: run it like `core.toml` (`--workspace "self=$PWD"`), regenerate it rather than editing it, and never use it to tune ranking. `core.toml` stays the hand-written required set.

`cargo xtask acceptance lsp` independently checks workspace-symbol, definition, and reference navigation against the same symbol and saves each normalized response in `test-results`. Both `cargo xtask acceptance core` and `cargo xtask acceptance lsp` default to this repository and need no arguments; `--profile gust --workspace /path/to/gpu-dialect-v0` (or `$LCI_ACCEPTANCE_GUST_WORKSPACE`) runs the same flows against the optional external GUST example instead, exactly like `evaluations/core.toml`'s optional `gust` workspace.

With the real embedding and reranking services running on ports 8766 and 8767, the mixed-language acceptance creates a disposable fixture and data directory under `test-results`, uses the actual debug binary, and never contacts port 8765:

```bash
cargo xtask acceptance multilingual
```

It verifies all supported language IDs, semantic and lexical retrieval with live reranking, production TypeScript, Python, and C# ranking over test decoys, zero-work unchanged indexing, one-file invalidation, deletion, restart reuse, and prior-snapshot retrieval after a deliberately unreachable embedding endpoint causes an update to fail. Reports are written as `test-results/multilingual-*.json`.

C# language-server acceptance is split across three more subcommands: `cargo xtask acceptance csharp-lsp` (real `dotnet` fixture + `csharp-ls`, plus `--probe-only` for a standalone JSON-RPC protocol probe with no LCI binary involved), `cargo xtask acceptance csharp-missing` (provider-isolation/degradation when `csharp-ls` is unavailable), and `cargo xtask acceptance csharp-recovery` (persistent process reuse and forced-kill recovery). Each requires `dotnet` and `csharp-ls` on `PATH` (or `$LCI_ACCEPTANCE_CSHARP_LS` naming the executable, for a `dotnet tool` install that isn't on `PATH`) and skips gracefully (printing `PREREQUISITE_UNAVAILABLE`) when they're missing.

TypeScript/JavaScript, Python, Go, Java, C, and C++ follow the same three-subcommand pattern: `cargo xtask acceptance typescript-lsp` / `typescript-missing` / `typescript-recovery` against a real npm-scaffolded fixture and `typescript-language-server` (`--typescript-language-server <path>` overrides discovery); `cargo xtask acceptance python-lsp` / `python-missing` / `python-recovery` against a real Python package fixture and `pyright` (`--pyright <path>` overrides discovery); `cargo xtask acceptance go-lsp` / `go-missing` / `go-recovery` against a real `go.mod`-rooted module and `gopls` (`--gopls <path>` overrides discovery); `cargo xtask acceptance java-lsp` / `java-missing` / `java-recovery` against a real Eclipse `.project`/`.classpath` fixture and jdtls (`--java <jdtls install directory>` overrides discovery -- a directory, not an executable, matching `[java].path`; `$LCI_ACCEPTANCE_JDTLS` sets the same directory for repeated local runs); and `cargo xtask acceptance c-lsp` / `c-missing` / `c-recovery` and `cpp-lsp` / `cpp-missing` / `cpp-recovery` against real standalone C/C++ fixtures and one shared `clangd` (`--clangd <path>` overrides discovery for each). All six skip gracefully when their server isn't found.

## Retrieval and persistence behavior

1. Scan exact lowercase `.rs`, `.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.cs`, `.go`, `.java`, `.c`, `.cpp`, and `.hpp` extensions recursively with `.gitignore`, nested ignores, and standard `ignore` crate rules. The checked-in `.lciignore` is honored as an additional ignore file and keeps agent control-plane material (`.agents`, `.github/agents`, `.github/instructions`, `.github/skills`, `.codex`, `.claude`, `.kilo`) and generated `test-results` out of this repository's searchable corpus while leaving those files available to agents on disk. Symlinks are not followed and `.git` is skipped. Hidden source files are eligible when not ignored. A file that is not valid UTF-8 (e.g. a Windows-1252 C source) is indexed from a lossy decoding -- invalid bytes become U+FFFD, line structure is preserved -- and reported in `lossy_decoded_files`; it never fails indexing or search. A `.ts` file that is really a Qt Linguist catalog (see the language table) is left out and counted in `skipped_non_source_files`; it does not affect the staleness fingerprint, and a file that changes into one drops its chunks at the next refresh like a deleted file. A source file that is removed between the directory walk and its read, or whose path is not valid UTF-8, is skipped with a logged warning. Other read/traversal errors abort the update and preserve the previous index; under `on-search` freshness such an error makes the search reuse the previous snapshot with a warning instead of failing.
2. Select a static language adapter and Tree-sitter grammar by extension. Rust retains its original declaration boundaries. TypeScript/JavaScript chunks preserve imports, executable top-level statements, exports, comments/decorators, functions, classes and methods, interfaces and signatures, type aliases, enums, and variable-assigned arrow functions. Python chunks preserve imports, assignments, executable top-level statements, synchronous functions, asynchronous functions, classes, methods, decorators, and associated leading comments. C# chunks preserve using directives, namespaces, top-level statements, types, members, attributes, XML documentation comments, and local functions. Go chunks preserve top-level functions, methods, type/const/var declarations, and associated leading comments. Java chunks preserve packages, imports, classes, interfaces, enums, records, methods, constructors, fields, annotations, and Javadoc comments. C chunks preserve functions, structs, unions, enums, typedefs, preprocessor macros, global declarations, and associated leading comments. C++ chunks preserve namespaces, classes, structs, unions, templates, methods, fields, and associated leading comments. Oversized syntax splits only at named syntax boundaries toward 6,000-byte groups, with declarations preserved up to 24,000 bytes. Large indivisible leaves stay whole rather than being truncated; parser error recovery remains searchable.
3. Hash each complete source file and persist its parsed chunks, language identifier, and adapter version in the external manifest. A later manual or watched pass reparses only changed/new files or files whose selected adapter version changed, including after restart. Fingerprints include path, content, language, and adapter version. A missing, incompatible, or malformed manifest safely causes a full parse.
4. Hash each exact source chunk. Reuse vectors from the current workspace snapshot when content hashes and the stored embedding URL/model/document-format identity match. Cached vectors whose width differs from what the embedding service returns now are embedded again: the width comes from the process's latest embedding response, or, in a process that has embedded nothing yet, from one single-attempt probe of a short prefix of the first chunk, sent only when there are cached vectors (a failed probe warns and keeps them). A width change that no request has revealed since the process's last one (no search, no changed chunk) is found by the next search, which serves no semantic hits and warns; the index run after it repairs the index. Parser adapter versions are intentionally decoupled from embedding compatibility, so unchanged chunk text keeps its vector. Duplicate new chunks are embedded once. Documents are embedded as source, without a query instruction.
5. Build a complete workspace snapshot in memory and commit a LanceDB table overwrite after embedding succeeds. Save the matching parse manifest only after that commit. Removed chunks disappear from the current snapshot; line-only changes update locations without re-embedding unchanged chunks. Previous Lance versions may remain on disk. This is a straightforward small/medium-repository design, not a streaming indexer for huge monorepos.
6. Embed queries with exactly:

```text
Instruct: Given a code search query, retrieve relevant code passages that answer the query
Query: <query>
```

7. Retrieve semantic candidates with LanceDB cosine distance (the `semantic_candidate_count` nearest chunks that pass the request's filters: LanceDB returns the `min(4 * count, 160)` nearest rows and the filters apply to them; only when the filters rejected a row and fewer chunks passed than were asked for and than the index holds under those filters is the fetch repeated with four times as many rows, up to 10,240, and a search that stops at that cap warns that farther matching chunks were not considered; an unfiltered search runs the first fetch alone) while ripgrep independently searches the query's lexical terms across all supported extensions in a single pass. The terms are the query's tokens as written plus the sub-tokens of their camelCase, snake_case, and letter/digit parts (`parseConfig` also searches `parse` and `config`), without generic English and commit-message words such as `add`, `fix`, and `when`, at most 24 per query. ripgrep's line matches are then credited in-process with the terms each line really holds: a term of five or more characters counts as a case-insensitive substring, a shorter one only as a whole word (`add_item` and `addItem` hold `add`; `padding` does not). Lexical lines map to chunks of any indexed language, and chunks are scored by IDF-weighted term evidence rather than matching-line count: a term's document frequency is the number of indexed files with a credited line, terms credited in more than a quarter of the indexed files are dropped (kept when every term is that common), the twelve rarest remain, and a chunk scores the BM25 sum over those terms of `idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * length / average_length))` with `idf = ln((N - df + 0.5) / (df + 0.5) + 1)`, `tf` the chunk's credited lines of the term, `length` the chunk's line count, `average_length` the mean over the filtered index's chunks, `k1 = 1.2`, and `b = 0.75`, so a long chunk does not win merely by holding many terms; chunks that match only dropped terms are not lexical candidates. A query with no usable term (only stop words) returns no lexical candidates, without a warning. These constants live in `lci-core/src/lexical.rs` and are not configurable. For each language present in the filtered index, its enabled language server (rust-analyzer, csharp-ls, typescript-language-server, pyright, gopls, jdtls, clangd) also searches workspace symbols, and LSP locations map only to same-language chunks.
8. Deduplicate and fuse semantic, lexical, and LSP ranks with Reciprocal Rank Fusion: each channel adds `weight / (rrf_k + rank)` for a chunk it returned, a chunk found by several channels sums those terms, and the source-role prior is added afterwards, unscaled. The three `[fusion]` weights (`semantic_weight`, `lexical_weight`, `lsp_weight`) all default to `1.0`, which is plain unweighted RRF (a `semantic_weight` of `2.0`, which counts the semantic channel's term double, was the default for a while, roadmap F2a, and was reverted when an exact offline replay with the LSP channel present found no significant effect); each weight must be finite and greater than zero, and a zero or non-finite weight is rejected when the file is loaded (disabling a channel is `[channels]`' job). The weights change only `fusion_score`, and through it the fusion order and the reranker shortlist; ranks, scores, and the reranker's per-document input are unchanged. After the fused order is settled and before the shortlist is cut to `rerank_candidate_count`, `[fusion].max_chunks_per_file` (default `2`; `0` is unlimited and changes nothing) demotes a file's chunks beyond that many behind every other chunk, which measured better on the mined evaluation set and on `core.toml` (roadmap F2b; fusion-only nDCG@10 +0.049 on the mined set, significant in both halves, +0.168 on core, significant; reranked on the mined set nDCG@10 +0.046, significant, MRR -0.023, not significant): it walks the fused order, keeps a chunk in the head while its file (by relative path) has fewer than that many kept, and moves the rest to a tail, so the result is the head then the tail, each in the original relative order. Nothing is removed, so `top_k` is still filled from the demoted chunks when there are too few distinct files; `fusion_score` is not rescaled, so a demoted chunk can appear after a chunk with a lower `fusion_score`. The reranker sees the capped shortlist, the reranker-off and reranker-failure results use the same capped order, and the reranker's own output order is not capped again. Results expose channel ranks, the lexical match count (credited lines of the scoring terms) and lexical score, fusion score, and retrieval channels; the lexical score never feeds the semantic or reranker scores.
9. Rerank the configured fused shortlist, sending each candidate as its path plus at most `rerank_document_max_bytes` of its code (cut at a UTF-8 boundary, keeping the head), so no single chunk can exceed the reranker's context or dominate its cost; results always carry the full chunk. Semantic, lexical, and LSP channels fail independently; available channels continue, and an LSP provider that fails is skipped for the rest of that search. Each provider also gets at most `lsp_search_budget_ms` of wall clock per search, running alongside the other channels and providers: a server that is still starting (rust-analyzer waits up to about ten seconds for its first indexing pass) or slow to answer is skipped for that search, which then reports an informational `notes` entry rather than a warning, because nothing failed. The skipped server is not discarded; its start (spawned at most once per provider and workspace, however many searches ask) keeps running in the background, followed by one priming `workspace/symbol` request that builds the server's symbol index (8-30 s on a large Rust workspace; searches during it also report the note, and no search budget cancels the priming request), and a later search uses the server. A partial answer gathered before the budget ran out is kept. `lsp_search_ms` in the timings is the capped wait. Each channel, and the reranker, can also be switched off on purpose with `[channels]`; that is silent, unlike a failure. If reranking fails, return fusion order with a warning appended to any earlier warnings.

When `ripgrep_path` is the default `rg` or `rg.exe`, resolution checks `PATH` first. On Windows, if `rg` isn't on `PATH`, it also checks common per-user and system-wide VS Code, VS Code Insiders, and VSCodium installations, including versioned application directories, since Windows users are less likely to have a system-wide ripgrep install than macOS/Linux users with a package manager. Any other configured value is treated as an explicit command or path and is used unchanged. If ripgrep cannot be started, lexical retrieval fails open and the warning explains how to set `ripgrep_path`.

Embedding response indices are validated and reordered; vectors must have consistent dimensions, finite values, and nonzero norm. Model HTTP errors include the service's status and (bounded) response body. Index-time document embedding retries connection errors, timeouts, and a connection the server closed or reset mid-request, typically a pooled keep-alive connection the server closed while idle (up to three attempts with backoff; a cold model may still be loading). The query embedding, the indexing width probe (step 4 above), and the reranker make a single attempt, so a hung service costs a search one timeout and a refused connection costs no backoff; after a refused connection the reranker is also skipped for 30 s, and the search warning says so. When the embedding service rejects a batch's input itself (HTTP 400/413/422, typically one chunk longer than the model's context), indexing retries that batch one chunk at a time and embeds a rejected chunk from a progressively halved prefix (down to 512 bytes); the full chunk is still stored, returned, and lexically searchable, and is listed in `truncated_for_embedding`. Its vector is cached by content hash like any other, so raising the server's context limit later needs a reindex into a new data directory to re-embed it in full. Changing an embedding URL/model requires reindexing. Replacing a model behind an unchanged name/URL is not detectable automatically unless its vector width differs (step 4 above); use a distinct configured model name or a new data directory for that change.

JSON timing fields measure query embedding, LanceDB search, lexical search, LSP search, fusion, reranking, and total retrieval in milliseconds. Total also includes validation and index access/wait time. The same timings appear in tracing logs on stderr; CLI JSON remains on stdout. The default log filter is `local_code_intelligence=info,lci_core=info`, so language-server restarts, readiness timeouts, and JSON-RPC reader failures from the core crate are logged. Set `RUST_LOG` to replace it (for example `RUST_LOG=local_code_intelligence=debug,lci_core=debug`). A `RUST_LOG` made only of crate-scoped directives that do not name `lci_core` silences that crate; a bare level such as `RUST_LOG=debug` applies to every crate.

## Module boundaries and checks

- `config` / `workspace`: configuration, canonical identity, external storage boundary.
- `language` / `chunk` / `manifest`: static language adapters, ignore-aware incremental scan, Tree-sitter chunks, and persistent per-file parse reuse.
- `models`: embedding and reranking HTTP clients.
- `lexical`: ripgrep-based lexical candidate channel.
- `lsp`: the shared `LspAdapter` trait and JSON-RPC transport, plus one adapter module per optional language server (rust-analyzer, csharp-ls, typescript-language-server, pyright, gopls, jdtls, clangd) and normalized navigation locations.
- `store`: embedded LanceDB schema, snapshot writes, cosine candidates.
- `filter`: retrieval filter validation and deterministic source-role classification.
- `evaluate`: portable evaluation definitions, execution, and metrics; it observes retrieval without changing ranking.
- `app`: indexing/cache coordination and retrieval pipeline.
- `server`: MCP tools and HTTP transport. `rest`: the plain JSON-over-HTTP/OpenAPI mirror of the same tools. `main`: CLI/server startup.

There is no BM25 index (the lexical channel scores ripgrep matches with BM25 at query time), no editor-specific integration, Docker setup, generation proxy, or web frontend yet. Later candidate sources can join the same fusion boundary before reranking.
