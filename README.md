# local-code-intelligence

LCI (local-code-intelligence) is a local code-retrieval service for any Streamable HTTP MCP client, with a plain REST/OpenAPI mirror for clients that do not speak MCP and a CLI over the same application logic. It is developed and tested on Windows (macOS and Linux builds are not verified during development; CI runs them for early warning only) and covers Rust, TypeScript, JavaScript, Python, C#, Go, Java, C and C++ code, plus Markdown documentation.

- Search combines Tree-sitter syntax chunks, an owned embedded LanceDB index, embeddings from any OpenAI-compatible embedder (the default configuration names `qwen3-embedding-4b`), ripgrep lexical search, optional persistent language-server retrieval for every supported code language, Reciprocal Rank Fusion, and fail-open neural reranking.
- It is meant to work like grep, with ranked chunks, and to extend grep by walking a code graph ("traverse" mode, off by default): a Wikirace on a code graph, where each step picks the next link (call, implementation, test, documentation mention, commit) from compiler-grade edges.
- The traversal engine, its status and its measurements are in [docs/spike/multimap/README.md](docs/spike/multimap/README.md). Everything else in this file is the shipped retrieval service.
- Boundaries (the rules are in [AGENTS.md](AGENTS.md) "Hard rules"): one process, no BM25 index (the lexical channel scores ripgrep matches with BM25 at query time), no editor-specific integration, Docker setup, generation proxy or web frontend.

## Supported languages

Source extensions and result language identifiers are exact and case-sensitive:

| Extension | Language identifier | Parser |
| --- | --- | --- |
| `.rs` | `rust` | Tree-sitter Rust |
| `.ts` | `typescript` | Tree-sitter TypeScript |
| `.tsx` | `tsx` | Tree-sitter TSX |
| `.js` | `javascript` | Tree-sitter JavaScript |
| `.jsx` | `jsx` | Tree-sitter JavaScript/JSX |
| `.py` | `python` | Tree-sitter Python |
| `.cs` | `csharp` | Tree-sitter C# |
| `.go` | `go` | Tree-sitter Go |
| `.java` | `java` | Tree-sitter Java |
| `.c`, `.h` | `c` | Tree-sitter C |
| `.cpp`, `.cc`, `.cxx`, `.hpp`, `.hh`, `.hxx` | `cpp` | Tree-sitter C++ |
| `.md` | `markdown` | Heading splitter (no Tree-sitter) |

These eighteen extensions (twelve language identifiers) are the whole indexable set; `.md` is indexed only with `[index].prose = true` (default `false`, so the default indexed set is the seventeen code extensions). Seventeen are source code; `.md` is the one prose format, and no other documentation or data format (`.rst`, `.adoc`, `.txt`, `.json`, `.toml`, `.yaml`) is indexed. All the code extensions always have Tree-sitter syntax indexing and retrieval, whatever the LSP configuration. Markdown has its own heading splitter and no language server: its files take part in search, filters (`language: markdown`, role `documentation`) and the lexical channel, and the navigation tools do not cover them.

- The extension decides the language. The one content check excludes, never selects: a `.ts` file whose first non-blank content (after an optional UTF-8 byte-order mark) is an XML declaration (`<?xml`) or a `<TS` root element with attributes is a Qt Linguist translation catalog, not TypeScript. It is skipped as non-source data (not parsed, chunked, embedded or listed by `list_indexed_files`) and counted in `skipped_non_source_files`. A comment, a bare `<TS>` type assertion or `<TS extends T>(...) => ...` first stays TypeScript. Other extensions have no content check.
- `.h` is always `c`: the extension cannot tell a C header from a C++ one and LCI never guesses from content. A C++ project's `.h` headers are chunked with the C grammar (the parser recovers around C++ constructs, the file stays searchable, results carry the language `c`), so a `language: c` filter also returns `.h` files from C++ projects. `.hpp`, `.hh` and `.hxx` are `cpp`. clangd serves both families and opens `.h` as C++, so navigation works on either kind of header.
- Navigation (`search_symbols`, `find_definition`, `find_references`) is additionally available behind an optional, independently configured language server per family: Rust `rust-analyzer`; C# standalone `csharp-ls`; TypeScript/TSX/JavaScript/JSX one shared `typescript-language-server`; Python `pyright` (`pyright-langserver`); Go `gopls`; Java `jdtls` (Eclipse JDT Language Server); C and C++ one shared `clangd`. LCI bundles and installs none of them. A disabled or unavailable server never affects syntax retrieval; only navigation on that language fails: `find_definition` and `find_references` return a clear tooling error, and `search_symbols` answers without that language and names it in a `warnings` entry.
- Per-server limits:
  - TypeScript and Python: LCI never writes a `tsconfig.json` or `pyrightconfig.json` into a user's repository, so a fresh server has no project context until `find_definition` or `find_references` opens a file; `search_symbols` results depend on what that server session has already opened.
  - Go: `gopls` needs a `go.mod` at or above the workspace root to build its package graph; without one it degrades to a much weaker fallback (fail-open, LCI never writes one).
  - Java: `[java].path` is the jdtls installation directory, not an executable. jdtls has no single native binary, so LCI spawns `java` itself and finds the Equinox launcher jar and platform config directory under that path (a process chain through jdtls's Python launcher hung on Windows, because killing the direct child does not end the `java` grandchild without a Job Object).
  - C/C++: clangd needs no `compile_commands.json` for LCI's per-file navigation; a workspace with a real build system can point it at its compilation database through `[clangd].args` (for example `--compile-commands-dir=...`). LCI never generates one.

## Build and run

Prerequisites: Rust stable 1.95 or newer; a C/C++ toolchain (MSVC + Windows SDK on Windows, a system compiler on macOS/Linux); CMake; `protoc`. `cargo xtask setup` downloads and verifies the official `protoc` release on Windows; on macOS/Linux it checks `PATH` for `protoc` and `cmake` and prints an install hint (`brew install protobuf cmake`, `apt install protobuf-compiler cmake`) when one is missing. No Python environment or database server is needed. Optional tools, none bundled or installed by LCI:

- ripgrep (`rg`): optional for serving (lexical search fails open without it), but required for the test gate `cargo xtask test --suite Full`, whose integration cases exercise the lexical channel (CI installs it; [testing guide](docs/development/testing.md));
- Rust: `rust-analyzer` and `rust-src` Rustup components; C#: a standalone `csharp-ls`;
- TypeScript/JavaScript: `npm install -g typescript-language-server typescript` (the workspace also needs its own `typescript` dependency); Python: `npm install -g pyright` (provides `pyright-langserver`);
- Go: `go install golang.org/x/tools/gopls@latest`; Java: JDK 21+ and an extracted `jdt-language-server-*.tar.gz` release from <https://download.eclipse.org/jdtls/snapshots/> (`[java].path` points at that directory); C/C++: a standalone `clangd`.

All dev, build, test and acceptance tasks run through `cargo xtask <command>` (subcommands: `setup`, `build`, `test`, `acceptance`, `live-acceptance`, `env`, `lint-machine-paths`, `docs`, `gold`, `maps`, `mine-queries`), identical on every OS:

```bash
cargo xtask setup
rustup component add rust-analyzer rust-src
cargo xtask build --test
./target/debug/local-code-intelligence init    # optional: write this machine's local overlay (see Configuration)
scratch=$(mktemp -d)                                  # any directory outside target/
cp target/debug/local-code-intelligence "$scratch/"   # local-code-intelligence.exe on Windows
"$scratch/local-code-intelligence" serve              # a long-lived server runs from the copy
```

- Serve from a copy, not from `target/`: a running executable is locked on Windows, so the next build would fail, and on any OS a rebuild would silently change what a long-running server is. Short commands (`init`, `config`, the CLI walkthrough) can run from `target/debug` directly.
- `serve` needs the model services below. `/health` answering only proves the process is up; wait for `curl http://127.0.0.1:8768/ready` to answer HTTP 200 before the indexing walkthrough (see CLI).

### Model services (prerequisite)

LCI does not bundle, download or start a model. It needs two HTTP services, each local, on another machine or hosted (the launch commands are specific to a machine and are not in this repository; see [machine values](docs/development/machine-values.md)):

- Embedder (required). An OpenAI-compatible server on `http://localhost:8766/v1` by default (`embedding_url`). LCI sends `POST <embedding_url>/embeddings` with `{"model", "input": [...], "encoding_format": "float"}` and reads `data[].index` and `data[].embedding`. Readiness also reads `GET /v1/models` at the same origin and needs the configured model in that listing. Default model name: `qwen3-embedding-4b` (`embedding_model`).
- Reranker (optional, fail-open). A server answering `POST <reranker_url>` (default `http://localhost:8767/rerank`) with `{"model", "query", "documents": [...], "top_n"}` and returning `results[].index` and `results[].relevance_score`. Default model name: `qwen3-reranker-4b` (`reranker_model`). Without it, searches return the fusion order with a warning.
- Other URLs, model names and API-key environment variables go in `config.toml` or the local overlay (`config.example.toml`, "Configuration" below). Changing the embedder's URL or model re-embeds existing indexes.
- Check with `curl http://127.0.0.1:8768/ready` once `serve` runs: HTTP 200 means a new index can be created; HTTP 503 names the missing dependency. `lci init` also reports which services answer, without writing a model setting.

- The first build compiles LanceDB and can take several minutes; later builds reuse Cargo's cache. For work on chunking, language adapters, filters or LSP adapters, `cargo check -p lci-core` and `cargo test -p lci-core --lib` skip that dependency tree and finish in seconds ([testing guide](docs/development/testing.md), which also covers a personal sccache/linker setup).
- Build note: LanceDB 0.38.0 needs its `remote` Cargo feature to compile (its job module references an HTTP error variant without a feature guard). The project enables the feature and uses only local embedded database paths.

### Ports and URLs

- Ports (stated here once; the agent-side rule is [AGENTS.md](AGENTS.md) "Hard rules"): LCI serves on 8768 (`port`); the embedder is expected on 8766 and the reranker on 8767; 8765 belongs to a separate generation model that LCI never calls, inspects, proxies or manages, and the live acceptance harness starts fixture servers on 8769. `port` rejects 8765, 8766 and 8767; `embedding_url` and `reranker_url` are rejected when their effective port is 8765 (an explicit `:8765` on any host, or a URL whose scheme default is 8765), whichever layer supplies them.
- The executable serves, on the default port:
  - MCP `http://127.0.0.1:8768/mcp`;
  - one more MCP endpoint per configured `[search_profiles.<name>]`, `http://127.0.0.1:8768/mcp/<name>` (none unless profiles are configured; the startup log lists them);
  - REST `http://127.0.0.1:8768/v1/*` (JSON-over-HTTP mirror of the MCP tools), OpenAPI `/openapi.json`, `/health`, `/ready`.
- With another `port` (configuration file, local overlay or `LCI_PORT`), `lci config` prints the URLs for the port in effect; a one-off `serve --port` is not visible to it.
- Smoke test from another terminal: `curl http://127.0.0.1:8768/health`, then `./target/debug/local-code-intelligence config` (every resolved value, its source and the URLs).

### Server behaviour

- The server binds only to loopback. MCP uses the official `rmcp` SDK with host/origin validation (on `/mcp/<name>` too) and supports session-based older clients as well as the SDK's current protocol. Every other route applies the same DNS-rebinding protection: the `Host` header must name a loopback address (`127.0.0.1`, `localhost`, `::1`) and a browser `Origin`, when present, must be this server's own `http://127.0.0.1:<port>` or `http://localhost:<port>`; anything else gets HTTP 403. Clients that send no `Origin` (curl, scripts, the CLI) are unaffected. Ctrl+C stops the server.
- `/health` is a cheap process-liveness check and never contacts model services. `/ready` and the MCP `service_status` tool return the same bounded dependency report: HTTP 200 when a new semantic index can be created, even if optional channels are degraded; `/ready` returns HTTP 503 when a required dependency is unavailable.
- Readiness requires a writable data directory, accessible embedded LanceDB storage, a reachable embedding endpoint, and the configured embedding model in its OpenAI-compatible model listing. Reranking, ripgrep and every language server are optional fail-open components, reported independently; an absent server never disables syntax retrieval for its language. On Windows the optional `data_dir_path_length` component degrades the report (it never changes `ready`) when `data_dir` is longer than 150 characters, because LanceDB can then fail with `os error 3` (the ceiling is about 163 characters). Probes use `readiness_timeout_seconds` (which also bounds the `lsp.live` map's version probe); readiness never downloads, starts, stops or manages a dependency.

## Configuration

Defaults work with the services described under Ports and URLs. Copy `config.example.toml` to `config.toml` to override them and pass `--config config.toml` before or after a subcommand (or set `LCI_CONFIG`). A configuration file is read only when named this way; the one other file consulted is the local overlay. Unknown fields are errors. Values are taken exactly as written: no `~` or `${VAR}` expansion, and `data_dir` must be absolute.

- Layers, lowest to highest: built-in default, configuration file, one local overlay file, `LCI_<KEY>` environment variables, command-line flags (`serve --port`). Resolution is per key: an overlay that sets `data_dir` leaves the file's `embedding_url` alone, and a setting no layer sets keeps its default. Without an overlay file and without `LCI_*` variables the result is exactly the file's values over the defaults.
- The configuration file describes behaviour and is the one to share. Only machine-specific settings may come from the overlay or environment: `data_dir`, `port`, `embedding_url`, `embedding_model`, `reranker_url`, `reranker_model`, `ripgrep_path`, `rust_analyzer_path`, and for each language-server section (`csharp`, `typescript`, `python`, `go`, `java`, `clangd`) `path`, `args` and `disabled`. Any other key in the overlay (a candidate count, a template, a timeout, `[channels]`, `[fusion]`, `[index]`, `[search_profiles]`) is an error naming the key, so a local file can never change ranking. Changing `embedding_url` or `embedding_model` this way changes the embedding identity: indexes built with the old values are re-embedded (`lci config` prints the identity).
- Overlay file: `<stem>.local.toml` beside the configuration file in use (`config.local.toml` for `config.toml`); with no configuration file, the per-user `local-code-intelligence/config.local.toml` under the platform configuration directory (`%APPDATA%` on Windows, `~/Library/Application Support` on macOS, `$XDG_CONFIG_HOME` or `~/.config` on Linux). `LCI_LOCAL_CONFIG=<path>` names another file; `--no-local-config` ignores it. A missing overlay is not an error and only `lci init` creates it. It holds this machine's paths: keep it out of version control.
- Environment: `LCI_DATA_DIR`, `LCI_PORT`, `LCI_EMBEDDING_URL`, `LCI_EMBEDDING_MODEL`, `LCI_RERANKER_URL`, `LCI_RERANKER_MODEL`, `LCI_RIPGREP_PATH`, `LCI_RUST_ANALYZER_PATH`, and `LCI_<LANG>_PATH` / `LCI_<LANG>_DISABLED` (`true`, `false`, `1`, `0`) for `LANG` in `CSHARP`, `TYPESCRIPT`, `PYTHON`, `GO`, `JAVA`, `CLANGD`; `args` can be set only in a file. An empty variable counts as unset; a malformed one is an error naming it. `LCI_CONFIG` and `LCI_LOCAL_CONFIG` name the two files (`--config` wins over `LCI_CONFIG`). `LCI_CANDIDATE_DUMP` is process-level behaviour, not configuration (see CLI).
- Model services: the embedder, the reranker and the optional System One slot (`[system_one]`, a small model planned to steer a traversal; off when absent) are each a URL, a model name and, optionally, the NAME of an environment variable holding an API key (`embedding_api_key_env`, `reranker_api_key_env`, `system_one.api_key_env`) sent as a bearer token. The key itself is never read from a configuration file and no error or log shows it. Each can be a local server, a server on another machine, or a hosted provider. A key sent over plain `http` to a non-loopback host is sent unencrypted, and LCI logs a warning about it. `[system_one]` refuses a non-loopback host unless `allow_remote = true`; the embedder and reranker accept any host. For System One only the configuration and the provider client exist: no traversal rung calls it yet, and `steer.ladder` rejects a `system_one` rung ([engine.md](docs/spike/multimap/engine.md), "Known gaps"). With `provider = "system_one_wire"` the same table configures the typed rescorer (`rescorer = "system_one"`, see the settings table). Its `timeout_ms` applies per batch request: when `batch_size` is smaller than the shortlist, the worst case before fail-open is (number of batches) x `timeout_ms`. See `config.example.toml`.
- `lci config [--json]` resolves all of this and prints every value with its layer, the files consulted and the URLs derived from the port, without creating the data directory, opening the index, sending a request or starting a language server. Values are printed as configured, including credentials in a URL, so treat the output as local.
- Before the first build the defaults below are what `lci config --json` would report with no file, overlay or `LCI_*` variable (the agent rule is in [machine values](docs/development/machine-values.md), "The agent rule").

### `lci init`

`lci [--config <file>] init [--force] [--dry-run] [--no-probe] [--json]` writes the overlay for this machine from what it finds.

- It writes only facts: `data_dir` as the platform default made explicit, and each of `rg`, `rust-analyzer`, `csharp-ls`, `typescript-language-server`, `pyright-langserver`, `gopls`, `clangd` found on `PATH` as an absolute path (the `.exe` or `.cmd` shim on Windows; an editor-launched server often sees a shorter `PATH`). A key that a higher layer already sets is left alone and noted. Nothing is started to check a tool.
- Everything else it learns is a comment: a missing tool and how to install it, whether each model service answers and which models it lists, whether the configured model is among them, whether the port is free on `127.0.0.1` (and if not, whether an LCI answers `/health` there), and that `jdtls` (an installation directory) must be set by hand. It never writes a model name, model URL or port, never picks another port, never writes the main configuration.
- The overlay is the one `lci config` reports as `local`: beside `--config`, else the per-user file, or the file `LCI_LOCAL_CONFIG` names (it need not exist; its directory is created). An existing file is replaced only with `--force`; without it `init` exits 3 and changes nothing. `--dry-run` prints and writes nothing; otherwise the file is written through a temporary file and a rename, after the result is read back and validated.
- It contacts only the model services and the port, only on loopback hosts, with no proxy and without following redirects, and never port 8765: a model URL on 8765 or any other host is reported as not probed (stderr and file), whatever flags are given. `--no-probe` sends no request. A port from 8765 to 8767 is not even bound.
- `--json` prints one object with `path`, `status` (`written`, `dry_run`, `exists`), `overlay` (the text), `set` (keys written), `detected` (data directory and each tool), `probes` (the two URLs and the port), `comments`, `valid`, `warnings`.

### Channels

`[channels]` switches the three retrieval channels and the reranker off for searches, mainly to run controlled evaluation arms. A file without the section behaves as before.

- A disabled channel contributes no candidates and does no work (`semantic = false` never embeds the query, `lsp = false` never starts a language server), reports a zero timing and adds no warning: turning it off is a choice, not a failure. Enabled channels still fail independently and open.
- A disabled reranker returns the fusion order with `reranked = false`, sends no rerank request, adds no warning; the shortlist is still capped at `rerank_candidate_count`, as in the reranker-failure fallback.
- At least one of `semantic`, `lexical`, `lsp` must stay enabled; a file that disables all three is rejected on load. With `semantic = false`, a query that matches nothing returns an empty result instead of an error when an enabled lexical or LSP channel ran without failing; if every enabled channel fails (or none can run), the search fails and the error carries the channel warnings.
- The grep-only baseline arm is `semantic = false`, `lsp = false`, `reranker = false`: ripgrep matches mapped onto chunks and ranked by match count, nothing else.
- The switches affect searches only: indexing still embeds and stores every chunk, so flipping one never requires a reindex, and `/ready` and `service_status` keep probing the embedding service (a required dependency of indexing) even with `semantic = false`.
- When the embedding service is unavailable (a refused or dropped connection, a timeout, an HTTP 5xx) and there are no stored vectors to lose (a first index, or an index that is already vectorless), indexing commits the chunks without vectors instead of failing: the snapshot reports `vectors_missing`, searches skip the semantic channel with the warning `Semantic retrieval unavailable: the index has no vectors (the embedding service was unreachable when it was built)` and answer from the lexical and LSP channels, and traverse seeds from lexical (its opt-in `search.vector` map sends no embedding request and records that reason as a fail-open note). A previous snapshot with vectors, an embedding identity change and an HTTP 4xx or malformed answer stay hard errors. Any refused connection to the embedder trips a breaker for 30 s: index runs then make one attempt without retries or backoff, and a search skips the semantic channel at once with the fail-open warning instead of connecting. `/ready` stays HTTP 503 until the embedder answers: it reports whether a vectored index can be created.

### Search profiles

`[search_profiles.<name>]` names a set of overrides for the query-time switches, so one configuration holds several quality/speed settings. An example with a `fast` and a `deep` profile is in `config.example.toml`.

- A profile may set only `semantic`, `lexical`, `lsp`, `reranker`, `rerank_candidate_count`, and the four presentation keys below; omitted keys keep the top-level value; any other key (an embedding setting, a candidate depth, a fusion setting, `rerank_document_max_bytes`) is an error. Nothing a profile sets changes the index or the embedding identity, so every profile searches the same index, with the same fusion, per-file cap and reranker input. `lsp` behaves as in `[channels]`: a profile with `lsp = true` over a top-level `lsp = false` starts language servers for its searches.
- A profile name is 1 to 32 letters, digits, `_` or `-`, starting with a letter or digit; `default` is reserved for the unprofiled search. Each profile is validated on load with its overrides applied: at least one of `semantic`, `lexical`, `lsp` enabled and `rerank_candidate_count` of 1-200.
- A search that names no profile is unchanged by any of this (same results, same JSON, no `search_profile` key). A search that names one reports it as `search_profile`; an unknown name is an error listing the configured names, never a silent fallback. A search picks its profile by where it is asked: CLI `search --search-profile <name>`, MCP by connecting to `/mcp/<name>`, REST `POST /v1/search_code?search_profile=<name>`. `evaluate` always runs the top-level settings.
- The four presentation keys change only how `/mcp/<name>` presents itself, never what a search retrieves:
  - `tools`: `"full"` or `"search"`. `"search"` lists and serves only `search_code`, `search_symbols`, `find_definition`, `find_references`; the maintenance tools (`index_workspace`, `index_status`, `list_indexed_files`, `watch_workspace`, `unwatch_workspace`, `service_status`) and the recipe tools are not listed and fail as unknown tools, which removes about a third of the default tool list an agent carries on every turn. The server instructions are unchanged; a "workspace is not indexed" error there says to run `search_code` (which builds the index) instead of naming `index_workspace`.
  - `response`: `"full"` or `"compact"`. A compact `search_code` result has per hit `relative_file_path`, `start_line`, `end_line`, `language`, `source_role`, `code`; scores, ranks, channels, content hash, absolute path, `query`, `candidate_count`, `reranked` and `timings` are left out; the envelope keeps `workspace.path`, `search_profile`, `warning` (when set), `notes` (when any), `filters`, `index`. Hits, order and locators are the full result's.
  - `compact_max_hit_lines` (default 40) cuts each hit's `code` after that many lines; a shortened hit has `code_truncated: true`, `excerpt_end_line`, and a last line naming the unshown lines, for example `[lci: code truncated; lines 50-109 of this file are not shown, read them from the file]`. A line over 500 characters is cut and marked too.
  - `compact_max_response_chars` (default 16000, a starting value, not a measured client limit) bounds the serialized result: when exceeded, the code of all hits is shortened alike, no hit is dropped or reordered, and the result has `response_truncated: true`; if the envelope, the locators and one closing line per hit do not fit, the call fails asking for a lower `top_k` or narrower filters. The two compact keys are errors without `response = "compact"`.
  - REST and the CLI always return the full report whatever these keys say.

### Storage

- Persistent data lives in `data_dir/lancedb` and `data_dir/manifests`, outside indexed repositories. A data directory and an indexed workspace cannot contain one another. Canonicalization resolves path aliases and symlinks; moving a repository creates a new workspace identity.
- A SHA-256 of the canonical workspace path identifies a workspace. Each workspace has its own LanceDB table (`ws_` plus the first 16 hex digits of the id) and parse manifest. Indexes under the earlier full-id name (`ws_<64 hex>`) stay searchable until the workspace's next index commit, which writes the short-named table without re-embedding unchanged chunks and then drops the old one; this is one-way (an older binary then sees the workspace as not indexed and embeds it again). A table recording a different workspace path than the one asking is refused with a table-name collision error instead of being overwritten; give one of the workspaces its own `data_dir`.
- On Windows keep `data_dir` under 150 characters: LanceDB's internal paths below it must fit the 260-character limit, and `/ready` flags a longer one.
- Manifest schema v2 records language and adapter compatibility per file, so changing one language parser does not invalidate other languages. Compatible schema-v1 Rust manifests are migrated without reparsing unchanged files. Previous Lance versions stay on disk; there is no automatic index cleanup command.

### Security: language servers and untrusted repositories

Search uses the enabled language servers for the indexed languages; symbol search, definitions and references also start the applicable server. Rust's adapter is always enabled when its executable is available; the other adapters are disabled until configured. These are local processes with the user's permissions, not sandboxed parsers.

- By default LCI starts rust-analyzer with `cargo.buildScripts.enable = false`, `procMacro.enable = false`, `checkOnSave = false`, and clears `cargo.buildScripts.overrideCommand` and `check.overrideCommand`. Its child environment sets `CARGO_NET_OFFLINE=true` and empties `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `CARGO_BUILD_RUSTC_WRAPPER`, `CARGO_BUILD_RUSTC_WORKSPACE_WRAPPER`; the same overrides go through `cargo.extraEnv` and `check.extraEnv`. This avoids ordinary build-script, procedural-macro and check-on-save execution and Cargo downloads, at the cost of incomplete analysis of generated code and missing uncached dependencies. Option names: the rust-analyzer manual's [Configuration](https://rust-analyzer.github.io/book/configuration.html) sections.
- `rust_analyzer_trusted = true` removes these LCI restrictions (but keeps workspace-symbol search settings) and restores rust-analyzer's own defaults and inherited environment, permitting build scripts, procedural macros, checks and dependency downloads, including dependency code. Enable it only when all repositories and dependencies accessed by that LCI process are trusted; it is not a per-request or per-workspace grant. Keep it in the main configuration, not a machine overlay.
- `probe.compile` (the opt-in traverse map, `lci traverse --maps probe.compile --root <tree>`) runs `cargo check` on a scratch copy of the tree, which executes the build scripts and procedural macros of the tree and its dependencies. It is behind the same grant: without `rust_analyzer_trusted = true` a call that names it gets a note and the walk runs with its other maps; with it, the answer carries a note saying what runs and the service logs a warning once per process. The scratch copy, its own target directory, `--offline`, the offline environment above, a timeout and a process-tree kill bound it. The environment settings do not confine what build scripts read or write or whether they open network connections, and the tree's `.cargo/config.toml` (`build.rustc`, `[env]` with `force = true`) can still change what runs; the grant is the control.
- Residual risks: these defaults are defense in depth, not a sandbox. LCI does not suppress or rewrite repository files such as `rust-analyzer.toml` or `.cargo/config.toml`; depending on the rust-analyzer version their settings can take precedence over the client settings LCI sends, so do not rely on client settings as a version-independent policy against repository commands or environment overrides. Cargo's `[env]` table with `force = true` can replace inherited values for processes Cargo runs. Compiler and toolchain selection, repository-provided executables, other Cargo configuration and language-server vulnerabilities remain execution risks, and rust-analyzer still invokes Cargo metadata and toolchain discovery. Other servers can also execute project tooling or load plugins (notably Java build imports and C# MSBuild) or reach the network (for example gopls modules); the Rust option does not harden them. For untrusted input use OS-level isolation with restricted permissions and network and trusted tool binaries. `[channels].lsp = false` disables language servers for code search only; it does not disable the explicit symbol/navigation tools.

## MCP tools

All tools return structured JSON, also available as MCP text content. Every successful result has a top-level `profile_hash`, the run-profile hash of the server's configuration (64 lowercase hex characters, the `derived.run_profile_hash` of `config --json`; 82 bytes per result, carried in both the text and the structured content; the last key of a compact `search_code` result). Tool failures set MCP `isError` and carry none. A call to a tool with an argument the tool does not have (a misspelt `top_kk` or `include_path`, say) is refused with a tool error ("unknown field") that names it; `service_status` takes no arguments and refuses any (send none or `{}`). The REST request bodies, which use the same argument structs, refuse it the same way, and the REST search query string refuses an unknown parameter (HTTP 400). **Breaking change (d388):** `service_status` arguments and unknown REST search query parameters were previously ignored; clients sending them must drop them. Every tool input schema has `additionalProperties: false`. `search_code` and `search_symbols` accept nonblank queries up to 16,000 UTF-8 bytes inclusive; longer queries fail with `query exceeds 16000 bytes`. `workspace_path` is an absolute workspace directory (on Windows a drive path with doubled backslashes in JSON). Example arguments for `search_code` on this repository: `{"workspace_path": "/path/to/local-code-intelligence", "query": "plain REST JSON-over-HTTP mirror of the MCP tools", "top_k": 8}`.

All endpoints share input schemas and server instructions. To offer several profiles to one client, register one MCP server entry per URL. Each endpoint keeps its own sessions (a session id from one is HTTP 404 at every other). A path under `/mcp/` naming no configured profile is HTTP 404; only `/mcp` and `/mcp/` are the default endpoint. A configuration with no profiles has `/mcp` alone.
- `search_code` creates a missing workspace index, waits for its commit and continues the search in the same call. Concurrent first searches for one workspace share that indexing job; other callers get results from the committed snapshot without duplicate embeddings. A compatible persisted index is reused immediately after restart.
- With an index present, `[index].freshness` (default `on-search`) decides whether a search checks for staleness. `on-search`: the first search that needs it compares the file manifest and content hashes against disk, throttled by `stale_check_interval_seconds`; on changed, new or removed files (or a changed embedding configuration) it refreshes incrementally, reusing cached vectors for unchanged hashes, before continuing. If another refresh is running it waits up to `wait_for_existing_job_seconds` and reuses that result; if the embedding service is unavailable the previous snapshot is kept and the search returns results with a warning. A vectorless snapshot (`vectors_missing`) counts as stale too: under `on-search` the next search past the same throttle runs the index again to embed the chunks, and keeps the vectorless snapshot with the warning while the service is still down. That repair is skipped without re-indexing while the breaker is open, and for 30 s after a repair that ended still vectorless. `manual` never refreshes automatically (use `index_workspace`). `watch` leaves refresh to `watch_workspace`'s poller, which suits long editor sessions. Under `manual` and `watch` a search never repairs a vectorless index: the next explicit `index_workspace`, or the watcher's reindex after a file change, embeds the chunks.
- The result's `index` object explains first-search latency: `action: created` (this request did the initial indexing), `waited_for_existing_job` (a concurrent request did), `refreshed_incrementally` (the search applied a staleness refresh), `reused` (a compatible, current-enough snapshot existed). `wait_ms` covers creation, refresh or waiting (near zero for plain reuse) and does not overload retrieval timings. Indexing is synchronous and ends when the new index is persisted, so allow a long client tool timeout for a first search, a refresh or an explicit indexing pass.
- Index writes are serialized in the running service with per-workspace read/write coordination. One service per data directory is intended; multiple clients connect to it. Commits are also serialized across processes by an OS file lock (`<data_dir>/index.lock`): a CLI `index`, `search` or `evaluate` next to a server on the same data directory waits for the other commit instead of interleaving LanceDB overwrites and manifest writes; reads never take the lock.
- Watching is opt-in for each server run: it polls only after `watch_workspace`, debounces a detected source change and calls the same safe indexing path. Registrations are not restored after a restart (indexes and manifests are). A failed automatic update is logged and retried after another poll while the prior snapshot stays searchable.

### Language-server lifecycle

The mechanics (start, priming, retry, stuck-server replacement, idle release, Windows job objects) are in `.agents/skills/lci-lsp-adapter/references/lifecycle.md`; the behaviour a client sees:

- The first applicable LSP request for a workspace starts one long-lived provider process per language server; later calls reuse it. `search_code` queries each applicable, enabled provider independently, only when filtered indexed chunks contain a language it navigates, and maps locations only to same-language chunks. A missing or disabled server leaves semantic and lexical retrieval available. Direct navigation rejects unsupported extensions before startup and returns an MCP error when the selected provider is disabled or unavailable. Definition/reference input lines are one-based; character offsets follow LSP (zero-based UTF-16).
- A request that fails because the server went away is retried once with a fresh provider; a server that answers with an error response is alive and is not restarted (an "ask again" answer is repeated on the same server up to twice; any other error is that provider's error, which `search_symbols` skips like any failed provider). A server that answers nothing but "ask again" errors for `lsp_stuck_seconds` is replaced; keep that value above the longest load you expect.
- A server nobody asked for in `lsp_idle_timeout_seconds` is released (a release takes about 4 seconds at most; a server still building its symbol index or serving a call is not released as idle). `POST /v1/release_workspace` releases a workspace's servers on demand; Ctrl+C on `serve` shuts every server down the same way within 5 seconds in all. After any release the next call starts a fresh server transparently, and the first `search_code` after it can hit `lsp_search_budget_ms` and report the informational `notes` entry, like the first search after the service starts.

| `lci_compose` | `POST /v1/lci_compose`, present only with `[compose] enabled` |

- Every `POST` takes the same JSON arguments as its MCP tool as the request body (REST `search_code` takes the plain search arguments; `mode`, `budget`, `steer` and `handle` are MCP-only). A success is HTTP 200 with the structured JSON an MCP `tools/call` would return, `profile_hash` included (`POST /v1/release_workspace` too; `/health` and `/ready` carry none); an application failure is HTTP 500 with `{"error": "<message>"}` and no `profile_hash`, instead of MCP's `isError` block. A request body the handler never sees is rejected earlier by the axum `Json` extractor with a plain-text body (not JSON): 400 for malformed JSON, 415 for a missing or wrong `Content-Type`, 422 for a body that does not deserialize, such as an unknown key (the text names the field, for example ``unknown field `include_path` ``) or a missing required one. The `search_code` query string accepts only the optional `search_profile` key; unknown or duplicate keys return HTTP 400 with plain-text errors naming the key, before any search runs. This also breaks clients that sent previously ignored extra query parameters: drop them and put supported filters in the JSON body.
- `curl -X POST http://127.0.0.1:8768/v1/search_code -H 'Content-Type: application/json' -d '{"workspace_path":"/path/to/local-code-intelligence","query":"plain REST JSON-over-HTTP mirror of the MCP tools"}'`.
- `POST /v1/search_code` also takes the optional query parameter `search_profile` (for example `/v1/search_code?search_profile=fast`); the body is unchanged and the result carries `"search_profile": "fast"`. An unknown name is the usual HTTP 500 listing the configured names (or saying none are configured).
- One endpoint has no MCP tool: `POST /v1/release_workspace` takes `{"workspace_path": ...}` and shuts down the language servers this service runs for that workspace (`shutdown`, then `exit`, about 4 seconds per server at most, then a kill; servers shut down side by side). It needs no index. The response is `{"workspace": {"id": ..., "path": ...}, "released": ["csharp-ls"]}`, `released` listing, sorted, the stopped servers (the names `analyzers_running` uses); a workspace with nothing running, or never indexed, answers HTTP 200 with `"released": []`; a nonexistent directory is the usual HTTP 500. The CLI has no equivalent (a CLI run owns no long-lived servers). MCP `tools/list` is unchanged.
- `GET /openapi.json` serves an OpenAPI 3.0.3 document of every endpoint above, including `release_workspace` and the `search_profile` parameter. Request schemas are generated from the same `schemars`-derived argument structs as the MCP tools, so they cannot drift; response bodies are documented as an open JSON object whose only required property is `profile_hash` (a string matching `^[0-9a-f]{64}$`).

## CLI

The CLI calls the same application logic and needs no editor. Its commits and a running server on the same data directory are serialized by the index lock; a separate `data_dir` (`--config` with its own) keeps CLI experiments from waiting on, or refreshing, the server's indexes. Subcommands: `serve`, `config`, `init`, `index`, `status`, `list-files`, `search`, `symbols`, `definition`, `references`, `evaluate`, `compare`, `replay`, `traverse`, `recipe`.

```bash
lci=./target/debug/local-code-intelligence   # local-code-intelligence.exe on Windows
repo=$PWD                                    # this repository: the walkthrough indexes LCI's own source
"$lci" index "$repo"
"$lci" status "$repo"
"$lci" list-files "$repo"
"$lci" search "$repo" 'plain REST JSON-over-HTTP mirror of the MCP tools'
"$lci" symbols "$repo" 'openapi_document#'
"$lci" definition "$repo" 'src/rest.rs' 351 64
"$lci" references "$repo" 'src/rest.rs' 172 3 --include-declaration
"$lci" references "$repo" 'lci-core/src/workspace.rs' 17 11 --include-declaration
"$lci" index "$repo"
```

- The walkthrough needs only a clone, a build and the model services ("Model services"); start it once `curl http://127.0.0.1:8768/ready` answers HTTP 200 (HTTP 503 names the missing dependency). `search` returns `openapi_document` in `src/rest.rs` as its top hit (the function building the document served at `/openapi.json`). `definition` starts from the call in the `/openapi.json` route at the end of `src/rest.rs` and resolves to that function's declaration; the first `references` starts from the declaration and returns it and the wiring; the second starts from `Workspace::resolve` and crosses crates (callers in `src/app/` and `tests/cases/`). Lines are one-based and characters zero-based UTF-16; the numbers are this repository's own, so if a file shifted, `grep -n openapi_document src/rest.rs` gives the current ones. The second `index` should report zero new embeddings when source and model configuration are unchanged. `cargo xtask acceptance core` runs the same index/search/repeat flow and checks that production implementation chunks, including `openapi_document`, dominate the top eight. Another repository is just a different first argument.
- `config` shows how the configuration resolves without opening the application: `"$lci" --config config.toml config [--json]`. `init` writes the overlay: `init --dry-run` (print only), `init` (write `config.local.toml` beside `config.toml`; exit 3 if it exists), `init --force --no-probe` (replace it, send no request).
- `config --json` prints one object: `valid` and `error`; `layers` (`file` with `path` and `named_by` (`--config` or `LCI_CONFIG`); `local` with `path`, `state` of `present`, `absent` or `disabled`, and `named_by`; `env`, the machine-set variables that were set; `flags`); `values`, every setting keyed by its dotted name (`port`, `typescript.path`, `index.freshness`; the `[search_profiles.<name>]` tables are one entry, `search_profiles`, when configured) with `value`, `source` (`default`, `file`, `local`, `env`, `flag`) and `from`; `config`, the whole resolved configuration; `derived` (`mcp_url`, `mcp_profile_urls`, `rest_base`, `health_url`, `ready_url`, `openapi_url`, `embedding_identity`, `run_profile_hash`); `environment.other` (whether `LCI_CANDIDATE_DUMP` is set). Exit status: 0 valid; 2 resolves but fails validation (for example a reserved `port`; the report is still printed with `valid` false); 1 when a layer cannot be read or parsed (a missing file, a non-machine key in the overlay, a malformed `LCI_*` value; only `valid` and `error` are printed with `--json`).
- `search` takes repeatable `--language`, `--include-path`, `--exclude-path`, `--source-role`, plus `--top-k` and `--search-profile <name>` (the profile's settings applied over `[channels]` and `rerank_candidate_count`; the response then carries `"search_profile"`; an unknown name exits with an error listing the configured names, before any index work). Path filters are case-sensitive repository-relative globs: `*` and `?` stay within one path component, `**` crosses directories. Absolute paths, backslashes, traversal components, empty patterns and malformed globs are rejected. An explicitly empty include list is a valid filter returning no results. Filters apply to every retrieval channel and are reported back as effective filters; no result may bypass them.
- Source roles are deterministic. Precedence: generated, test, benchmark, example, documentation, configuration, source. Tests are recognized by `test`/`tests`/`__tests__` directories, the Gradle/Android source sets `androidTest`/`integrationTest`/`testFixtures`, and per-language file names: Python `test_*.py`/`*_test.py`; JS/TS `*.test.*`/`*.spec.*`; C# `*Test(s).cs`; Go `*_test.go`; Rust `tests.rs`/`test_*.rs`/`*_test.rs`/`*_tests.rs` (a bare `test.rs` stays source, being a legitimate production module name; inline `#[cfg(test)] mod tests` cannot be told from the path); Java `*Test`/`*Tests`/`*TestCase`/`*IT.java`; C/C++ `*_test`/`*_tests`/`*_unittest(s)`/`test_*` on the C and C++ extensions. Layout directories (`examples`, `docs`, `config`, `scripts`, `tools`, `build`, ...) count only above a Maven/Gradle source root (under `src/<set>/java/`, or `kotlin`/`scala`/`groovy`, the remaining directories are package names, so `com/example/...` is not an example), and a `config`/`configs`/`configuration` directory marks only non-source files, so `internal/config/loader.go` stays source. Production source receives a small transparent `0.004` fusion prior; all other roles receive zero. Role and prior appear in result metadata; explicit role filters stay authoritative.
- Traversal and recipes (SCIP-backed, see [engine.md](docs/spike/multimap/engine.md)): `"$lci" traverse --scip <index> [--root <tree>] --question '<text>'` walks the code graph of a SCIP index (`rust-analyzer scip`) from the start nodes the question finds (with `--root`, the top hits of the hybrid search over that tree, mapped to the index's symbols; otherwise a stand-in matching the question's words against symbol names, reported as `seed_source`) and prints one JSON object (reached nodes, totals, handler decisions, and when it stopped to ask or ran out of budget a `handle` and `checkpoint`; continue with `--handle` and `--steer`). It ignores `[traverse] enabled` (which gates only the MCP mode) and is limited by the `[traverse]` caps. With `--root`, the graph also has an `implements` edge from each trait-impl member to its trait method declaration (read from the `impl .. for ..` headers; rust-analyzer writes no SCIP relationships), and `--maps scip.implements` adds the traits a type implements, the types that implement a trait and the members that implement a trait method; derives, `macro_rules!` impls and traits the index does not define give no edge. With `scip.implements` on, a trait path or `Trait::method` in a code span of the question (`` `tauri::Manager` ``, `` `Runtime::run` ``) starts the walk at that trait or trait method declaration (the response then has `trait_seeds`, how many start nodes they are, and `seed_source` `traits`, or `traits+hybrid`, `traits+hybrid+bm25`, `traits+bm25` or `traits+name_tokens` when the other start nodes stay behind them: they are replaced when the path matched with its qualifiers, kept when it matched by the last segment alone; `--seeds` still wins; `--trait-seeds replace|prepend|auto` (default `auto`, as described) picks the mode), and `--seeds` takes the node ids the map prints; without the map the start nodes are unchanged. Selectors include `--maps`, `--policy` (a preset: `explore`, `impact`, `flow`, `where-to`, `history`; or JSON; the policy is the router: it sets the walk or first-stage answer and the maps of the question type, see [engine.md](docs/spike/multimap/engine.md) Presets), `--first-stage`, `--pops`, `--max-depth`, `--top-k`, `--out`. `"$lci" recipe <name> --root <tree> [--scip <index>] [--args <json>]` runs one recipe (`config_readers`, `impact_rings`, `flow_path`, `flow_from`, `config_neighbours`, `lci_compose`); it ignores `[recipes] enabled` and `[compose] enabled`. `config_readers`, `config_neighbours` and an `lci_compose` `config.key` step need `rg` on `PATH`.
- Map freshness (`[run_profile.traverse] map_freshness = true`, default `false`): a traversal answer (MCP `mode = "traverse"`, `lci traverse`) then has `maps`, one entry `{id, observed, stale, lag}` for each map of the call that states its freshness, in registration order; with the key off the answer has no `maps` key and is unchanged. The SCIP-built maps (`graph.scip`, `structure.contains`, `seeds.scip_names`, `exact.closure`, `config.key`, `scip.impact`, `scip.implements`) have `observed = "snapshot"`. The maps that read the tree or git when they answer (`grep.live`, `lsp.live`, `git.history`, `exact.pickaxe`, `probe.compile`) have `observed = "live"`, `stale = false` and `lag = 0`; that label says they read current bytes (or the current git HEAD), not that their positions are current: `grep.live` and `lsp.live` place what they read by the index's positions, so a line shift since the index is not covered by their `live`. `lag` is a count of files, never wall time: the source files the language adapters index (prose, such as Markdown, is left out) that are newer than the index file (modified time after the index file's), plus those that changed since this process first saw the index's current stamp (modified time and length): a file whose content hash changed, added or removed, each file counted once however often it is edited. A touch without a content change does not count. `stale` is `true` when `lag` is above 0, so an index rewritten with a new stamp starts again from the files newer than it. `lag` is `null` and `stale` `false` (meaning not compared, never fresh) when the call has no tree (no `--root`), the tree could not be read, or the index file has no modified time; a note in the answer says which. Not seen: a change that left a file older than the index file before this process first saw the stamp, and a change that kept the file's content hash. Every call reads and hashes the tree's source files (no chunk is made), unless `[run_profile.freshness] stat_gate` is on (see "Stat gate" below). The maps `seeds.hybrid`, `search.lexical` and `search.vector` state nothing and are absent from `maps`, unless `[run_profile.freshness] verify_on_read` is also on (see "Verify on read" below). The key is read from the run profile the call is given, so the recipes (whose answers carry no `maps`) take it too: `flow_from`'s inner walk, with the key on, reads the tree and discards the comparison.
- Paths on cards (`[run_profile.traverse] card_paths = true`, default `false`): every card of a traversal answer's `results` and of the checkpoint's `answer` that the walk reached then has `kind`, the kind of the edge that discovered the node (`null` for a start node), and `path`, the route from its start node: one `{node, map, kind, witness}` entry per node (`depth + 1` entries, the first is the start node with `kind` and `witness` `null`, the last is the card itself and repeats its `via` and `witness`). The route is the walk's final one (a stronger route found later replaces a weaker one). The cards of `visited_cards` and `frontier`, the cards of the first stage (`origin` `exact` or `seed`), the trace and the checkpoint hash are unchanged; with the key off nothing in the answer, the trace, the checkpoint or the handle changes. A handle made with the key on also keeps each state's `kind` (an additive key; the handle format version is unchanged), so a continuation shows whole chains; a handle made with it off has no kinds for its earlier hops, which show `kind: null`, and a note says so. Size, measured as the answer's characters divided by 4: on the unit-test fixture (4 cards, depth up to 2, a complete walk) 616 tokens off, 856 on; on one real walk (`lci traverse` with `graph.scip` over an older index of this repository, one start node, 8 cards at depth up to 3, ended by the pop cap with a checkpoint) 3807 tokens off, 5160 on, 35.6 percent more, because the checkpoint's `answer` repeats the cards; the `results` list alone grows 87.5 percent (3095 to 5802 characters), about 85 tokens per card per list. Cards at greater depth cost more, one entry of about 25 tokens per hop.
- Language-server sessions of `lsp.live` (`[run_profile.lsp] sessions`, `"per_call"` default or `"shared"`; it matters only when a call runs `lsp.live`, which is opt-in): under `per_call` every traversal call starts its own language servers (a cold start and a version probe of each enabled server) and stops them when its walk ends, as before. Under `shared` the calls of one process use one set of servers, started by the first call that asks and kept for the next: the MCP and REST server uses its own manager, the one that navigation (`find_definition`, `find_references`, `search_symbols`) and the search channel use, so a server started by any of them serves the others; `lci traverse` is one call per process, so there `shared` differs from `per_call` only in that the servers stop cleanly when the walk ends. A shared server stops like any other of the service: when it has been idle for `lsp_idle_timeout_seconds`, on `release_workspace`, when its session is replaced (stuck or failed) and at service shutdown (Ctrl+C, SIGTERM); the end of a walk does not stop it. The version probe of a server binary runs once per manager under `shared` (a failed probe is run again by the next call). The recipes (`flow_from` and the other `lci_*` tools) walk only `graph.scip` and `structure.contains`, never `lsp.live`, so no language server starts under a recipe and they run the same under both values; the key still reaches them in their run profile, so the profile hash they carry is the one that ran. `[run_profile.lsp] implementations` (default `false`) adds a third request to each symbol node of an `lsp.live` expansion, `textDocument/implementation`, behind the same `max_external_calls` gate as the other two: its answers become `implements` edges from the node to the symbols (or files) at the places the server names, the direction `scip.implements` uses (an interface or trait member to the members that implement it). The place table is the SCIP index's, whose nodes are functions and methods, so the request is asked at an interface or trait member, not yet at the interface or trait itself. An error reply from the implementation request is noted and costs the other two requests' edges nothing (a hang trips the call's deadline and clears them all). The recipes ask no implementations either way. `[run_profile.lsp] call_hierarchy` (default `false`) adds up to three more requests to each symbol node, each behind the same gate and counted: `textDocument/prepareCallHierarchy` at the node's name, then `callHierarchy/incomingCalls` and `callHierarchy/outgoingCalls` of the item that answers (an empty prepare ends it, so one more call at least). Callers and callees become `calls_or_refs` edges (no new edge kind), one per destination, whichever way the call runs, seen at the call itself; a symbol or file that `definition` or `references` already named keeps that edge. An error reply (a server without call hierarchy answers -32601) is noted and costs the other edges nothing; a failed prepare ends the block and a failed incoming request still asks outgoing. Servers miss some calls (rust-analyzer's call hierarchy missed 16% of the call pairs the SCIP index has, in macro arguments), so this complements `graph.scip`. The recipes ask no call hierarchy either way.
- Verify on read (`[run_profile.freshness] verify_on_read = true`, default `false`): with `map_freshness` also on, a traversal answer checks what it cites against the working tree by content hash. It reads and labels; it never refreshes the index and never changes `[index].freshness` (under `manual` the snapshot stays as old as it was). It reuses the one read of the tree that `map_freshness` makes (no second scan), and with the key off every answer is byte-identical to before. What it adds: (1) the maps that answer from the index snapshot (`seeds.hybrid`, `search.lexical`, `search.vector`) get a `maps` entry `{id, observed: "snapshot", stale, lag}` whose `lag` counts the source files that differ between the snapshot's manifest and the tree (changed, added, or removed; the manifest's prose entries are not counted, as the tree scan leaves prose out). It is read after the walk, because the walk's first search may refresh the snapshot under `on-search` (a refresh that lands between a map's read and this manifest read, as under `[index].freshness = "watch"`, makes the answer look as current as the new snapshot); `null` (not compared) when the call has no tree or no manifest. (2) `grep.live` and `lsp.live` keep `observed: "live"` (they read current bytes) and gain `places: "index"`: where they put what they read comes from the SCIP index, so their `stale` and `lag` are the SCIP index's (the same count as the SCIP-built maps), and a line shift since the index shows as stale. They are the only entries with `places`. (3) Every card (`results`, and the checkpoint's `answer`, `visited_cards` and `frontier`) gets `file_changed`: `true` when the content hash of the file it cites (its `site.path`, else its node's path) now differs from the hash its maps read, `false` when it does not, `null` when no reference applies (a commit or other card with no file, a file that is not a source file, or no tree was read; one note says how many cards are `null`). `true` also covers a file that was newer than the index file when this process first saw the index's stamp: its hash at index time is unknown, so it counts as changed whatever its content is. The reference is the SCIP baseline for the maps built from the index, for `grep.live` and `lsp.live`, and for a symbol card (its site is the index's, whichever map reached it), the snapshot manifest for `seeds.hybrid`, `search.lexical` and `search.vector` and for a chunk card; a card that names both is `true` when either differs. A `search_code` / `search` report (JSON; the compact text output is unchanged) gets a `freshness` block with the key on, with or without `map_freshness`: `snapshot` (`{stale, lag}`: the source files that differ between the snapshot's manifest, read after the search, and the tree, which one read of the tree's content hashes gives, gated by `stat_gate` when it is on), `channels` (`{id, observed, stale, lag}` for the channels that ran, so a channel that was off or not reached (no language server applies, no vectors) is not listed, and one that failed is listed with a `note` (`failed; see warning`) and no lag, because it answered nothing: `vec.chunk.code` and `lexical` are `observed: "snapshot"` with the snapshot's lag; `lsp.symbols` is `observed: "session"` with `stale` and `lag` `null` and a `note`, because the language server's view of the tree is not compared), and `hits` (one `{path, file_changed}` per result in order; `file_changed` is `null` for a hit no snapshot channel returned (only the language server, or no channel named), or when the tree was not compared, which a note says). The block is read after the search, so a refresh of the snapshot that lands between the search and that read (`[index].freshness = "watch"`) is not seen: the answer then looks as current as the new snapshot. The scan costs `timings.verify_ms` (absent when the key is off), and only a search a caller asks for pays it: the searches that find a traversal's start nodes and the evaluation runner do not scan. Under `manual` or `watch` a search never refreshes the snapshot, so the block is how a caller sees that it is behind; under `on-search` the search has just refreshed it and the lag is 0. A search with the key off has no `freshness` key. The recipes take the key through the run profile but their answers carry none of this.
- Stat gate (`[run_profile.freshness] stat_gate = true`, default `false`: every read of the tree for `map_freshness` or `verify_on_read` reads and hashes every source file). With `true` the process keeps each source file's modified time, length and content hash per root, lists the tree without reading it, and reads and hashes only the files whose modified time or length is new or changed (a file with no modified time is always read; a file skipped by its content, such as a Qt Linguist catalog saved as `.ts`, stays skipped while its stamp stays). The labels and `file_changed` equal the full-hash path's, through the same hash function, with one known gap: a same-length edit that keeps a modified time older than 3 seconds before the previous read of the file (a deliberate `set_modified`, or a clock that went back) is not seen until that file's next edit. A file modified within 3 seconds of a read is not trusted and is read again on the next call, which covers a write in the same clock tick and the coarse stamps of FAT, exFAT and SMB shares. The table lives in the process and is rebuilt on the first call; the index scan is not gated. The key is in the profile hash.
- Outline cache of `lsp.live` (`[run_profile.lsp] outline_cache`, default `false`: every file outline the map needs, a `textDocument/documentSymbol` request, goes to the server). With `true` the cache works only for the servers that hold a file's current text at every request: pyright, gopls, jdtls and clangd, whose adapters send the file's text from disk in a `textDocument/didOpen` before each request, and which take that text even for a document they already have open (pyright logs the repeated open and applies it; gopls overwrites its overlay; jdtls replaces the working copy's buffer; clangd's open replaces the contents). For those the language-server manager reads and hashes the file (the content hash the index uses, sha-256 over up to 16 MiB, on every outline request) before it asks, and keeps each non-empty outline under that hash and the server session that answered; the same file is then answered from memory while its bytes and that session are unchanged. An edited file is asked again and gets the outline of the new text, and so is any file after the server was restarted, released, replaced or stopped idle. An empty outline or an error is never kept (a server still loading answers `[]`), and neither is an answer for a file whose bytes changed during the request, an answer from a session that is no longer the live one, a file that is not UTF-8 or one over the 16 MiB open limit. The other servers are asked every time, as without the key: rust-analyzer watches the disk itself and can answer from the text before an edit for a moment after it, csharp-ls is sent no document text, and typescript-language-server refuses a second `didOpen` for a document it already has open, so after the first request it keeps the text it was first sent. A manager keeps at most 4096 outlines; a new one past that clears them. The cache belongs to the manager: under `sessions = "per_call"` it lasts one walk, under `"shared"` it serves later calls too. The recipes never run `lsp.live` and run the same under both values.
- Language-server sync (`[run_profile.lsp] sync`, default `"off"`: a language server walks the tree when it starts and is told nothing after, so a long-lived session answers `search_symbols`, the search channel and a shared `lsp.live` from the tree it started on). With `"watch"` the service's language-server manager (the MCP and REST server's, which navigation, the search channel and `sessions = "shared"` traversals use; the one `lci traverse` builds under `"shared"`) watches each workspace that has a running session and sends every change of a source file to that workspace's servers as one `workspace/didChangeWatchedFiles` (created, changed or deleted, as the file is on disk), and drops the changed files' kept outlines. The watcher is the platform's (ReadDirectoryChangesW, inotify, FSEvents), or a poll every `watch_poll_milliseconds` when it cannot start (the poll compares modification times in whole seconds, so a second write within the same second is sent only with a later change). It starts with the workspace's first session, walks the tree once to know its files, walks again only when the platform reports lost events (inotify and FSEvents do; on Windows a watcher overflow during a large burst, such as a big checkout, is not reported and silently ends the watching until the workspace's sessions stop, roadmap N102), and stops when the workspace's last session stops. Single changes are not filtered by `.gitignore` (a source file written under an ignored directory, such as `target/`, is sent), and a renamed or moved directory is seen as the directory alone, so the files inside it are not sent. Before each request the manager sends what the watcher has already reported, so an edit the watcher saw is in the server's next answer; it never waits for a walk, and an edit the platform has not reported yet is in a later answer. Prose files are not sent, nor anything under `.git`. It is independent of index watching (`watch`): a workspace can be watched for the index, synced, both or neither. A per-call manager (`sessions = "per_call"`) never syncs: its servers start on the tree as it is and stop with the walk, so there the key changes nothing but the profile hash. The recipes never run `lsp.live` and run the same under both values.
- Place table of `lsp.live` (`[run_profile.lsp] places`, default `"scip"`: the SCIP index's table alone, so a symbol the index has no node for has no place, `lsp.live` asks nothing about it, and under `scip.mode = "off"` it asks nothing about any symbol; a file seed still gets its `textDocument/documentSymbol` outline, but its members are named only when the index defines them). With `"outline"` the table is the index's plus the language server's own outline of a file: the first time a walk expands a symbol the index places in a file, or expands the file, `lsp.live` asks the server for the file's `textDocument/documentSymbol` (one more external call per distinct file and walk; a failed request keeps the index's place and is not repeated) and from then on the outline's places win in that file, so lines inserted since the SCIP file was written no longer make it ask at the wrong line. An outline member takes the index's id for the same symbol when the index has one (same file and name, a function or method of either kind, nearest line; one symbol keeps one id across the layers), else an id of the file's real language with no container (`sym:csharp:Shapes.cs::Area/method`, equal names told apart in document order: `~1`, `~2`), so under `scip.mode = "off"` the functions, methods, types (class as `class`, struct as `struct`, interface as `interface`, except that rust-analyzer's trait stays `trait` in a Rust file), enums, modules, constants, fields (a property is a field) and variables of an outlined file have ids (`sym:csharp:Shapes.cs::Circle/class`). Enum members, impl blocks and type parameters have none. A file expansion lists the fields as `Contains` destinations too, and a reference on a field's line now resolves to the field; `lsp.live` asks a field or variable like any other symbol (a server may answer `implementation` for an interface property or a call hierarchy for a `const f = () => {}` it reports as a variable). A handle saved under `outline` by an earlier build holds `struct` and `trait` ids for class-language members, which no longer match a learned place. A seed that is a symbol id of a file this walk has not outlined still has no place. Every `documentSymbol` range now ends on the item's last line (the nested `DocumentSymbol` shape used to give the name's line), which `Contains` edges read from the name's own line first. The recipes never run `lsp.live` and run the same under both values.
- Entity seeds (`[run_profile.seeds] bm25`, default `false`: the map `seeds.bm25` does not run, naming it in `maps` gives a note and no seeds, and every answer is as without the key). With `true` the map is in the default set of a call that names no maps, and runs when named. It ranks the SCIP graph's functions and methods by BM25 (the scorer of the ripgrep channel, `lexical::score_chunks`) over three fields of each node: the tokens of its name, of its qualified path (the symbol's package, modules, types and member, and the file's path) and of its documentation (the `documentation` the index holds for the symbol, up to 1024 bytes; empty when the indexer writes none, and it is not verified that `rust-analyzer scip` writes any; it is read from the index file, a second parse, only when the map first runs for an index stamp, and never with the key off). A question word counts when it is a whole token (up to 4 characters) or inside one (longer); words under 3 characters and stop words are not terms, and a word in more than a quarter of the nodes is dropped unless no word would remain. Of the top `[traverse] seed_k` nodes, those the hybrid search did not already give (so possibly fewer) go after its nodes (`seed_source` `hybrid+bm25`, each with a `seed_hits` record `how: "bm25"`; `seed_source` `hybrid` stays when it adds none), or are the start nodes when the hybrid search gave none (`bm25`; the name-token stand-in then does not run, and `seed_fallback` says why the search did not answer). It reads the SCIP graph only (no `--root` needed), builds its index on the first call that wants it and keeps it with the graph for the index stamp. The recipes' seeds are given, so they run the same under both values.
- Literal seeds (`[run_profile.seeds] literal`, default `false`: the map `seeds.literal` does not run, naming it in `maps` gives a note and no seeds, ripgrep is not started for it, and every answer is as without the key). With `true` the map is in the default set of a call that names no maps, and runs when named. It searches the tree with `rg --fixed-strings --word-regexp` (case-sensitive, `_` counts as part of a word, the source files of the language adapters, at most 20 lines per file) for the names the question puts in code spans (the last segment of each `a::Name`, at least 2 characters, at most 4 names), and places each line in the SCIP graph: the symbol defined on that line (`how: "definition"`), else the innermost symbol around it (`occurrence`, counted per symbol), else, when the line declares the name (`trait`, `struct`, `fn`, `class` and the like right before it, or `impl .. for` it), the file's node (`file`: a type or trait the graph lacks, which `structure.contains` expands to the symbols it holds), else the line is dropped. Definitions (3 per name at most) come first, then occurrences (most lines first), then files; nodes the other sources gave are left out and the list is cut at `[traverse] seed_k`. They go after the hybrid search's and `seeds.bm25`'s nodes (`seed_source` `hybrid+literal`, `hybrid+bm25+literal`, `bm25+literal`), or are the start nodes when those gave none (`literal`). It is not `[traverse] exact_seeds`, which turns the first stage's exact cards into start nodes. It needs the application's ripgrep (a question with `--root`); a call without says so in `notes` and goes on. The recipes' seeds are given, so they run the same under both values.
- Every JSON result of `index`, `status`, `list-files`, `search`, `symbols`, `definition`, `references`, `evaluate` (the report, also when written with `--output`), `traverse` and `recipe` carries the same top-level `profile_hash` as the MCP and REST results (`derived.run_profile_hash` of `config --json`; `traverse` hashes the configuration after its command-line overrides). `config --json` reports the hash under `derived`; `compare`, `replay` and `init --json` run offline without a resolved configuration and carry none. An error prints no result.

## Retrieval evaluation

- `evaluate` runs a portable definition through the same application search path: `"$lci" evaluate ./evaluations/core.toml --workspace "self=$PWD" --workspace "gust=/path/to/gpu-dialect-v0" --output ./test-results/evaluation.json`. Workspace mappings are supplied at runtime, so checked-in definitions hold no machine paths. The GUST workspace is optional; its queries are skipped without a mapping. Without `--output`, JSON goes to stdout. A required missing workspace, search error, expected-path miss, wrong expected role or missing required snippet fails the query and gives a nonzero exit after the report is emitted; valid optional skips do not fail the run. `evaluate --baseline <report.json>` also embeds a `comparison` and prints its summary to stderr (`--seed`, `--resamples`, `--keep-failed`). With `[channels] lsp` on, `evaluate` first starts and primes every enabled language server for each workspace it queries (rust-analyzer is always enabled, so a missing binary is recorded as a failed warm-up), so no query pays a cold start; the outcome is the report's `priming` block (per workspace key and provider: `primed`, `ms`, `error`). `--no-prime` keeps the cold first query for a cold-start measurement. Priming changes which query pays the start, never a ranking.
- Arms: run `evaluate` once per configuration with `--config` and name the outputs by arm: the default, `[channels] reranker = false` (fusion order alone), or the grep-only baseline (see Channels). Reports do not record the switches, and the switches never invalidate an index, so arms can run one after another on one `data_dir`; never two at once on the same one.
- `compare` measures the difference between two saved reports without services, configuration or index: `"$lci" compare test-results/fusion.json test-results/semantic-only.json --output test-results/fusion-vs-semantic-only.json`. It pairs queries by workspace and query text (both reports must come from the same definition) and prints, for MRR, nDCG@10 and hit@1, the baseline and candidate means, the mean per-query delta (`candidate - baseline`) with a seeded 95% paired-bootstrap interval (`--resamples`, default 10,000; `--seed`), whether the interval excludes zero, and reciprocal-rank wins, losses and ties. Queries in only one report, or skipped in either, are excluded and counted; so is a query in which either side's language server missed `lsp_search_budget_ms` (`metrics.lsp_budget_hit`: it measured a cold start, not retrieval), counted as `budget_hit_*` on the pairs line and, for tagged definitions, per tag (`budget_hit_by_tag`), unless `--keep-failed` keeps it; a definition with `tags` also gets one block per tag. A regression is not an error: the exit code is nonzero only when a report cannot be read or parsed, or `--output` cannot be written (the summary is printed first). A delta whose interval contains zero is noise at that query count.
- Reports hold bounded path, line-range, role, rank, score and preview evidence; per-query hit@1, hit@3, hit@8, reciprocal rank, nDCG@10, recall@3/@8, file-level accuracy@5/@10, preference/disfavor counts, role distribution, reranker state, `lsp_budget_hit` (with `lsp_providers_over_budget` when set; a search response names them as `lsp_over_budget` only when a provider missed the budget), timings, lifecycle and effective filters; and aggregates: hit rates, MRR, means of the rank-aware metrics, `lsp_budget_hit_queries` (and per tag under `by_tag`), median/p95/max latency with sample count `n` (total and per stage; nearest-rank p95 hides the worst query at small `n`, for example it is the second-highest of 35, so read `max`), fallback count, and created/reused/waited/refreshed index counts. nDCG@10 uses graded gain (`expected_paths` match 2, `preferred_paths` only 1) and credits each gold pattern once; recall@k is the fraction of distinct expected patterns in the first k; file accuracy@k counts distinct files. The `@10` metrics are bounded by the query's `top_k`: hand-written `core.toml` uses 8 (effectively @8), the git-mined set 10; use `top_k >= 10` to compare with literature @10 numbers. Reports belong under `test-results` and are not committed. Evaluation reuses compatible persisted indexes and calls only the configured embedding and reranking services.
- Offline scoring: `evaluate --dump-candidates` records every query's whole fused candidate pool, the dumped configuration and the reranker's scores; `LCI_CANDIDATE_DUMP=<file>` appends the same pool per search of a running process to a JSON Lines file (read once at startup; MCP, REST and CLI responses are unchanged). `"$lci" replay test-results/dump.json --output test-results/replay-w12.json --window 12 --cap 2 --cap-stage results` then scores other windows, caps, fusion weights, `rrf_k`, priors and rerank modes from the dump without services, configuration (the `--config` file is not read) or index, and `compare` pairs the output with real reports. A query replay cannot score exactly is refused and counted, never approximated. Row format, replay semantics, the latency model and when to run live instead: `.agents/skills/lci-retrieval-evaluation/references/evaluation-workflow.md`.
- Git-mined query set: `cargo xtask mine-queries --repo <repo-root> --key <workspace-key> --out evaluations/mined/<key>.toml [--max 300]` turns qualifying commits from `git log` into queries (subject plus first body paragraph as the query, touched supported files as `expected_paths`, `top_k = 10`). `evaluations/mined/self.toml` (workspace key `self`) is the generated set for this repository: run it like `core.toml` (`--workspace "self=$PWD"`), regenerate rather than edit it, never use it to tune ranking. `core.toml` is the hand-written required set. Skip rules, labels and tags: same reference.
- Live acceptance: `cargo xtask acceptance core` and `acceptance lsp` default to this repository (`--profile gust --workspace /path/to/gpu-dialect-v0`, or `$LCI_ACCEPTANCE_GUST_WORKSPACE`, runs them against the optional external GUST example); `lsp` checks workspace-symbol, definition and reference navigation against the same symbol and saves each normalized response in `test-results`. With the real embedder and reranker running, `cargo xtask acceptance multilingual` creates a disposable fixture and data directory under `test-results`, uses the real debug binary; it verifies all supported language IDs, semantic and lexical retrieval with live reranking, production TypeScript, Python and C# ranking over test decoys, zero-work unchanged indexing, one-file invalidation, deletion, restart reuse, and prior-snapshot retrieval after an unreachable embedding endpoint makes an update fail (`test-results/multilingual-*.json`). Per language, `<lang>-lsp`, `<lang>-missing` and `<lang>-recovery` run a real server (options and prerequisites: `.agents/skills/lci-lsp-adapter/references/acceptance.md`, `docs/development/live-acceptance-ci.md`); each skips with `PREREQUISITE_UNAVAILABLE` when its server is not found.
- Metric tiers (method and status in [evaluation.md](docs/spike/multimap/evaluation.md)): agent runs are the ground truth but too costly to run regularly, so cheap proxies run constantly and are checked against agent runs now and then, and quality is reported together with cost.

| Tier | When | What |
| --- | --- | --- |
| 1 | every change, deterministic | hit@k, recall@k, span hit, MRR on the frozen sets; speed proxies (pops, hops, expansions); cost-aware recall (recall per 1k tokens returned); the simulated agent (design, not built) |
| 2 | milestones, cheap model in the loop | confidence calibration; a small fixed subset judged by a cheap model |
| 3 | rare, before releases | real agent A/B runs, mainly to validate the proxies |

## Retrieval behavior

The shipped search pipeline, in order; the code-level picture (types, constants, functions) is [docs/architecture.md](docs/architecture.md) "Chunks and the manifest", "Indexes and channels" and "Indexing flow and freshness". Traverse mode: [engine.md](docs/spike/multimap/engine.md).

1. Scan the eighteen extensions above (exact lowercase) recursively with `.gitignore`, nested ignores and standard `ignore` crate rules. The checked-in `.lciignore` is an additional ignore file that keeps agent control-plane material (`.agents`, `.github/agents`, `.github/instructions`, `.github/skills`, `.codex`, `.claude`, `.kilo`) and generated `test-results` out of this repository's searchable corpus while leaving them on disk for agents. Symlinks are not followed, `.git` is skipped, hidden source files are eligible when not ignored. A file that is not valid UTF-8 (for example Windows-1252 C source) is indexed from a lossy decoding (invalid bytes become U+FFFD, line structure kept) and reported in `lossy_decoded_files`; it never fails indexing or search. A Qt Linguist `.ts` catalog is left out and counted in `skipped_non_source_files`; it does not affect the staleness fingerprint, and a file that changes into one drops its chunks at the next refresh like a deleted file. A source file removed between the walk and its read, or whose path is not valid UTF-8, is skipped with a logged warning. Other read/traversal errors abort the update and preserve the previous index; under `on-search` freshness the search then reuses the previous snapshot with a warning.
2. Select a static language adapter and Tree-sitter grammar by extension. Chunks preserve: Rust, its original declaration boundaries; TypeScript/JavaScript, imports, executable top-level statements, exports, comments/decorators, functions, classes and methods, interfaces and signatures, type aliases, enums, variable-assigned arrow functions; Python, imports, assignments, executable top-level statements, sync and async functions, classes, methods, decorators and leading comments; C#, using directives, namespaces, top-level statements, types, members, attributes, XML documentation comments, local functions; Go, top-level functions, methods, type/const/var declarations and leading comments; Java, packages, imports, classes, interfaces, enums, records, methods, constructors, fields, annotations, Javadoc; C, functions, structs, unions, enums, typedefs, preprocessor macros, global declarations, leading comments; C++, namespaces, classes, structs, unions, templates, methods, fields, leading comments. Oversized syntax splits only at named syntax boundaries toward 6,000-byte groups, with declarations preserved up to 24,000 bytes; large indivisible leaves stay whole rather than truncated; parser error recovery remains searchable. Markdown (`.md`) is cut into heading sections: a heading line plus its own body up to the next heading of any level (ATX and setext headings), with fenced code blocks kept whole and never searched for headings, YAML front matter kept with the first section, and text before the first heading as its own chunk; a section over 6,000 bytes is packed by paragraph toward that size, and a fence stays whole.
3. Parsed chunks, language identifier and adapter version are persisted per file in the external manifest (fingerprints include path, content, language and adapter version), so a later manual or watched pass reparses only changed, new or adapter-version-changed files, also after restart. A missing, incompatible or malformed manifest safely causes a full parse.
4. Each exact source chunk is hashed; vectors from the current workspace snapshot are reused when content hashes and the stored embedding URL/model/document-format identity match, and duplicate new chunks are embedded once. Cached vectors whose width differs from what the embedding service now returns are embedded again: the width comes from the process's latest embedding response, or, in a process that has embedded nothing yet, from one single-attempt probe of a short prefix of the first chunk, sent only when cached vectors exist (a failed probe warns and keeps them). A width change no request has revealed since the process's last one is found by the next search, which serves no semantic hits and warns; the index run after it repairs the index. Parser adapter versions are decoupled from embedding compatibility, so unchanged chunk text keeps its vector. Documents are embedded as source, without a query instruction.
5. A complete workspace snapshot is built in memory and committed as a LanceDB table overwrite after embedding succeeds; the matching manifest is saved only after that commit. Removed chunks disappear from the snapshot; line-only changes update locations without re-embedding. This is a small/medium-repository design, not a streaming indexer for huge monorepos.
6. Queries are embedded with `embedding_query_template` (default `Instruct: Given a code search query, retrieve relevant code passages that answer the query` newline `Query: <query>`).
7. Candidates come from three channels. Semantic: LanceDB cosine distance, the `semantic_candidate_count` nearest chunks that pass the request's filters (the fetch is widened when filters reject rows, up to 10,240 rows; a search stopping at that cap warns that farther matching chunks were not considered). Lexical: ripgrep over all supported extensions in one pass, scored in process:
   - Terms are the query's tokens as written plus the sub-tokens of their camelCase, snake_case and letter/digit parts (`parseConfig` also searches `parse` and `config`), without generic English and commit-message words such as `add`, `fix`, `when`, at most 24 per query. A query with no usable term returns no lexical candidates, without a warning.
   - Matching lines are credited with the terms each really holds: a term of five or more characters counts as a case-insensitive substring, a shorter one only as a whole word (`add_item` and `addItem` hold `add`; `padding` does not). Lexical lines map to chunks of any indexed language.
   - Chunks score by IDF-weighted term evidence: a term's document frequency is the number of indexed files with a credited line; terms credited in more than a quarter of the indexed files are dropped (kept when every term is that common); the twelve rarest remain; a chunk scores the BM25 sum over them of `idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * length / average_length))` with `idf = ln((N - df + 0.5) / (df + 0.5) + 1)`, `tf` the chunk's credited lines of the term, `length` its line count, `average_length` the mean over the filtered index's chunks, `k1 = 1.2`, `b = 0.75`. Chunks matching only dropped terms are not candidates. The constants live in `lci-core/src/lexical.rs` and are not configurable.
   - LSP: for each language present in the filtered index, its enabled language server also searches workspace symbols; locations map only to same-language chunks.
8. Candidates are deduplicated and fused with Reciprocal Rank Fusion: each channel adds `weight / (rrf_k + rank)` for a chunk it returned, a chunk found by several channels sums the terms, and the source-role prior is added afterwards, unscaled. The `[fusion]` weights default to `1.0` (plain RRF); each must be finite and greater than zero (disabling a channel is `[channels]`' job). Weights change only `fusion_score` and through it the fusion order and shortlist, never ranks, scores or the reranker's per-document input. After the order is settled and before the shortlist is cut to `rerank_candidate_count`, `[fusion].max_chunks_per_file` (default `2`; `0` is unlimited and changes nothing) walks the fused order, keeps a chunk in the head while its file (by relative path) has fewer than that many kept, and moves the rest to a tail; the result is head then tail, each in original relative order. Nothing is removed, so `top_k` is still filled from demoted chunks when there are too few distinct files; `fusion_score` is not rescaled, so a demoted chunk can follow one with a lower score. The reranker sees the capped shortlist, reranker-off and reranker-failure results use the same capped order, and the reranker's output is not capped again. The cap and the weights were measured on the mined set and `core.toml` (numbers: [decisions](docs/decisions.md)). Results expose channel ranks, lexical match count and score, fusion score and channels; the lexical score never feeds the semantic or reranker scores. The full contract: `.agents/skills/lci-retrieval-evaluation/references/retrieval-contract.md`.
9. The fused shortlist is reranked, each candidate sent as its path plus at most `rerank_document_max_bytes` of its code (cut at a UTF-8 boundary, keeping the head); results always carry the full chunk. The three channels fail independently and available channels continue; an LSP provider that fails is skipped for the rest of that search. Each provider gets at most `lsp_search_budget_ms` of wall clock per search, alongside the other channels: a server still starting (rust-analyzer waits up to about ten seconds for its first indexing pass) or slow is skipped for that search, which reports an informational `notes` entry rather than a warning because nothing failed. The skipped server is not discarded: its start (spawned at most once per provider and workspace) keeps running in the background, followed by one priming `workspace/symbol` request that builds its symbol index (8-30 s on a large Rust workspace; searches during it also report the note, and no search budget cancels the priming), and a later search uses the server. A partial answer gathered before the budget ran out is kept; `lsp_search_ms` in the timings is the capped wait. Channels and the reranker can be switched off on purpose with `[channels]` (silent, unlike a failure). If reranking fails, the fusion order is returned with a warning appended to any earlier warnings.
10. Documentation lane. Markdown chunks (the prose extractor's, not every chunk with the `documentation` source role) are split off after the request's filters and never enter the code pipeline above, unless the request names `source_roles` (then the filters apply as stated and one list comes back). The code `results` list is therefore exactly what an index without the Markdown files returns: semantic search, lexical statistics (BM25 average length and document frequencies) and LSP mapping all see code chunks only. The documentation lane runs beside it with the same query vector: semantic over prose chunks only (`docs_lane.semantic_candidate_count`), lexical over prose chunks only, no LSP, the same fusion and per-file cap, a cut to `docs_lane.rerank_candidate_count`, a second rerank only when `docs_lane.reranker` (or the profile's `docs_reranker`) is on (default off, whatever `[channels].reranker` says), and the best `docs_lane.top_k` (default 2) come back in `docs.results` with `candidate_count`, `reranked`, its own timings and `warning`. `docs` is present exactly when the lane ran and the index holds prose chunks. The lane is fail-open: a semantic, lexical or reranker failure sets `docs.warning` and never changes the code list or its warning. The compact MCP view lists the docs after the results and shares its response ceiling.

- ripgrep resolution: with the default `rg` or `rg.exe`, `PATH` is checked first; on Windows without `rg` on `PATH` it also checks common per-user and system-wide VS Code, VS Code Insiders and VSCodium installations (including versioned application directories). Any other configured value is an explicit command or path, used unchanged. If ripgrep cannot start, lexical retrieval fails open and the warning explains how to set `ripgrep_path`.
- Model clients: embedding response indices are validated and reordered; vectors must have consistent dimensions, finite values and nonzero norm. Model HTTP errors include the status and a bounded response body. Index-time document embedding retries connection errors, timeouts and a connection the server closed or reset mid-request (typically a pooled keep-alive connection closed while idle), up to three attempts with backoff (a cold model may still be loading). The query embedding, the indexing width probe (step 4) and the reranker make a single attempt, so a hung service costs a search one timeout and a refused connection costs no backoff; after a refused connection the reranker is also skipped for 30 s, and the warning says so. When the embedding service rejects a batch's input itself (HTTP 400/413/422, typically one chunk longer than the model's context), indexing retries that batch one chunk at a time and embeds a rejected chunk from a progressively halved prefix (down to 512 bytes); the full chunk is still stored, returned and lexically searchable and is listed in `truncated_for_embedding`. Its vector is cached by content hash, so raising the server's context limit later needs a reindex into a new data directory to re-embed it in full. Changing an embedding URL/model requires reindexing; replacing a model behind an unchanged name/URL is not detectable unless its vector width differs (step 4), so use a distinct model name or a new data directory.
- Timing fields (milliseconds) cover query embedding, LanceDB search, lexical search, LSP search, fusion, reranking and total retrieval; total also includes validation and index access/wait time. The same timings appear in tracing logs on stderr; CLI JSON stays on stdout. The default log filter is `local_code_intelligence=info,lci_core=info`; `RUST_LOG` replaces it (for example `RUST_LOG=local_code_intelligence=debug,lci_core=debug`). A `RUST_LOG` made only of crate-scoped directives that do not name `lci_core` silences that crate; a bare level such as `RUST_LOG=debug` applies to every crate.

## Module boundaries and checks

- `config` / `workspace`: configuration, canonical identity, external storage boundary.
- `language` / `chunk` / `manifest`: static language adapters, ignore-aware incremental scan, Tree-sitter chunks (Markdown: heading sections), persistent per-file parse reuse.
- `models`: embedding and reranking HTTP clients. `lexical`: the ripgrep lexical channel.
- `lsp`: the shared `LspAdapter` trait and JSON-RPC transport, one adapter module per optional language server, normalized navigation locations.
- `store`: embedded LanceDB schema, snapshot writes, cosine candidates. `filter`: filter validation and source-role classification.
- `evaluate`: portable evaluation definitions, execution and metrics; it observes retrieval without changing ranking.
- `app`: indexing/cache coordination and the retrieval pipeline (also `traverse`, `recipes`, `compact`).
- `server`: MCP tools and HTTP transport. `rest`: the JSON-over-HTTP/OpenAPI mirror. `main`: CLI/server startup. The `lci-maps` crate holds the multimap (traversal) map definitions; the full module and crate picture is [docs/architecture.md](docs/architecture.md). Later candidate sources can join the same fusion boundary before reranking.

Checks: `cargo xtask build --test`, then `cargo xtask test --suite Full` once per completed change. `Full` runs `cargo xtask lint-machine-paths`, `cargo xtask docs check`, `cargo fmt --all -- --check`, `cargo test --workspace --locked --features local-code-intelligence/map-equivalence` and `cargo clippy --workspace --all-targets --locked --features local-code-intelligence/map-equivalence -- -D warnings` in sequence, setting `PROTOC` from `.tools/protoc` when the auto-downloaded copy is present. Focused suites (`Unit`, `Chunk`, `Filter`, `Config`, `Evaluation`, `Indexing`, `Readiness`, `Mcp`, `Watching`, `Lsp`, `Freshness`) and the change-to-suite map are in [docs/development/testing.md](docs/development/testing.md); every focused suite fails if its filter matches no tests.

Automated tests use a local mock model HTTP service and real embedded LanceDB. They cover Rust boundary regression, all eighteen language adapters (one per extension), schema-v1 migration, per-language parse compatibility, persistent parse/vector reuse across reopen, mixed-language metadata and retrieval, TS/JS-only LSP gating, stale detection, deleted files, failed-update preservation, watched refresh, embedding configuration changes, reranker failure and invalid replies, query instruction formatting, ignore handling, actual Streamable HTTP initialization and tool discovery, and the REST/OpenAPI mirror's success and error responses. Live self-workspace and multilingual acceptance use the real local model services separately.
